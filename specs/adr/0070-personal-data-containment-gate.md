# ADR-0070: Mechanize the Enumeration Half of the Personal-Data Containment Rule

## Status
Proposed

## Context and Problem Statement
[CLAUDE.md](../../CLAUDE.md)'s first rule confines personal health data to `specs/personal/`. Until now that rule was enforced by **prose**: a paragraph of git recipes in [`/land`](../../.claude/skills/land/SKILL.md) step 3 and another in [`/savepoint`](../../.claude/skills/savepoint/SKILL.md) step 1, run by hand each time. [ADR-0069](0069-local-checkpoint-commits.md) booked that as accepted debt in its Negative Consequences, and [open-questions.md](../open-questions.md) tracked it as the repo-invariants register's sixth seed row.

That row is the only one in the register with **measured repeated failure**, and the measurement is what motivates this ADR rather than a general preference for automation. Across the `chore/savepoint-skill` branch (2026-08-04/05), **repeated independent review passes each reported that prose clean, and these holes were in it the whole time** (how many passes, and how the holes distributed across them, is deliberately left unstated — including by implication, since "each hole found by a different pass" asserts a one-to-one mapping as firmly as a numeral would; that figure drifted across four documents and the contradiction was caught by a bot, so the enumerated holes below are what has to be right):

1. the scan read the *endpoint diff*, so a file added by one checkpoint and deleted by a later one was invisible at both ends while its blob rode every push;
2. the merge base was substituted **unguarded**, so an empty result left `..HEAD` — which git accepts and answers with silence at exit 0;
3. `git log --name-only` reports **no paths at all** for a merge commit, so a file force-added while resolving a merge passed unexamined;
4. the index reconciliation proved *paths*, never *content* — a `skip-worktree` entry keeps a dirty blob staged that every path check waves through;
5. the prose guard was case-sensitive and missed the bare path, while the repo's own *tested* launcher guard already casefolded and covered both;
6. the history scan listed paths while the content instruction inspected *current* files, so a value committed then sanitized rode the push invisibly.

Three fixes, three rounds, three new holes. **All six fall in the rule's _enumeration_ half — which paths does this change touch — and none in its _content_ half — is this value real or synthetic.** Recording them as one rule is what let six enumeration bugs read as an irreducibly manual control.

## Decision Drivers
- Enumeration is ordinary code with a decidable answer; content is judgement with none. The observed defect distribution (6–0) says exactly where mechanization pays.
- The failure mode of this control is **silence**, not noise. Every hole above produced a clean report, which is the one outcome no reviewer re-examines.
- Prevention and detection are different jobs. A CI gate fires after the push, by which time the blob is in the remote's object store; only a pre-push run prevents.
- Precedent bar: the repo's other `check_*.py` gates are stdlib-only, expose a `check()` for tests, and are exercised against synthetic fixtures that each break one precondition ([ADR-0061](0061-markdown-link-check-gate.md), [ADR-0062](0062-markdown-style-lint-gate.md)).
- [CLAUDE.md](../../CLAUDE.md) rule 1: this creates a new blocking enforcement surface and a CLI contract two skills and a CI job depend on, so it needs an ADR rather than a `Decisions: none` note.

## Considered Options
1. **Mechanize the enumeration half only** (chosen) vs. **mechanize the whole rule** vs. **keep it prose and fix the recipes again.** Mechanizing content would mean a gate deciding whether `Glucose 92 mg/dL` in a fixture is synthetic — it cannot, and a gate with false positives on every test fixture is one an operator disables. Fixing the prose again was the option taken three times already; the fourth attempt buys a fourth hole.
2. **Three explicit scopes** (chosen) vs. **one scope** vs. **two scripts.** `/savepoint` runs per checkpoint and must stay cheap, so it cannot pay for a history walk; `/land` is the whole-branch backstop; CI is the after-the-fact net over all refs. One scope forces the most expensive behaviour on the cheapest caller. Two scripts recreate the duplicated-prose problem this ADR exists to end — the deliberate non-duplication between the two skills becomes a **flag** rather than two texts that drift.
3. **Diff-based history walk** (chosen) vs. **object-based (`git rev-list --objects --all`).** The object walk is the natural-looking instrument and is **unsound**: it lists each *object* once, so files sharing content collapse to one line under one arbitrary path. Measured on a repo holding three identical-content files, one under `specs/personal/`: it named a different path and never mentioned the personal one, while the diff walk reproduced the per-commit `ls-tree` ground truth exactly.
4. **CI step in the `gitleaks` job** (chosen) vs. **in `docs-consistency`.** The scan walks every reachable commit, which needs `fetch-depth: 0`; only the `gitleaks` job checks out that way, and it is already the job that walks full history for the credential-shaped half of the same containment question. `docs-consistency` checks out shallow, where the scan would silently shrink.
5. **Refuse to run on a shallow clone** (chosen) vs. **run and report what is visible.** Measured on a `--depth 1` clone before the guard existed: `--scope history` exited **0** announcing "620 paths examined" while holding 4 commits of roughly 80. That is hole 2 reproduced inside the gate itself, so the shallow case fails loudly instead.

## Decision Outcome

### 1. A new stdlib script, `scripts/check_personal_containment.py`
It resolves a verified merge base, enumerates paths from the porcelain, the branch history, the tracked set, and the staged index, and fails on any path at or under `specs/personal/` — matched case-insensitively and covering the bare path as well as the directory prefix. Exit 0 only when the scan **ran** and found nothing; a precondition it cannot satisfy is a failure, never a pass. Every path list is read `-z`, because git quotes non-ASCII names in its line-oriented output and a leading `"` defeats a prefix test anchored at the start of the path.

### 2. Three scopes, one per caller
| Scope | Caller | Walks |
|---|---|---|
| `worktree` | [`/savepoint`](../../.claude/skills/savepoint/SKILL.md) step 1 | porcelain (`--untracked-files=all`), tracked set, staged-blob identity |
| `branch` | [`/land`](../../.claude/skills/land/SKILL.md) step 3 | the above plus `<merge-base>..HEAD` with `--diff-merges=first-parent` |
| `history` | CI's `gitleaks` job | every path in every commit reachable from any ref |

`--base` belongs to the `branch` scope alone and is **refused** with either other scope rather than ignored: `--scope history --base origin/release` once parsed cleanly, ran the unbounded `--all` walk, and exited 0 without ever resolving the ref, so an operator or a future CI step asking for a bounded walk silently got something else. The CI step above passes no `--base` and is unaffected. Recorded here because it is part of the CLI contract two skills and a CI job depend on, which is the reason this ADR exists at all rather than a `Decisions: none` note.

### 3. A clean run states its own evidence
The success line prints a **per-source breakdown** (`tracked-personal 0, worktree 12, branch-history 34`) rather than a total. A total is the one shape that hides hole 2: "1 path examined" reads as proof until you notice the 1 came from the working tree while the history walk contributed nothing. Naming each source gives a zero somewhere to show up.

### 4. The content half stays prose, deliberately
Both skills keep their content instruction, and `/land` step 3b is pointed at the branch's first-parent **patch stream** — the only view that sees a value committed by one checkpoint and sanitized by a later one. The script *names* that command with the resolved merge base already substituted, and does not read it. `origin/main..HEAD` is a different commit set from `<merge-base>..HEAD` on any branch that has merged its base back in, so the resolved value is what gets handed over.

### 5. Only a divergence git *hides* is a staged-content violation
The staged-blob check (hole 4) reports a path whose index blob is not the working-tree content, but **only where git's own commands conceal that difference** — a `skip-worktree` or `assume-unchanged` entry, identified from `git ls-files -v`. An ordinary "`git add`, then keep editing" state is reported as a **note** and does not fail the scan.

The first external review of this gate measured why. Reporting *every* divergence failed the whole scan on porcelain `MM`, the most common mid-session index there is, and named a `skip-worktree` entry that did not exist; both callers reach that state, since `/savepoint` step 1 runs before that skill stages anything. That is the same false-positive argument option 1 above used to refuse mechanizing the content half, and it applies here unchanged: a gate that fires on the normal case is one an operator turns off. What makes the downgrade safe is that nothing hides the visible case — `git status` shows the path, `git add` resolves it, and `/savepoint` step 2 reconciles `git diff --cached --name-only` against its enumerated path list and stops on any extra. The `skip-worktree` case defeats every one of those, which is what makes concealment the discriminator rather than divergence.

**That argument has to be made twice, because the `branch` scope has a different caller.** `/land` runs the same check and has no reconciliation of its own — it never stages and never commits. The reconciliation that covers it happens later: [`/ship`](../../.claude/skills/ship/SKILL.md) commits from three paths — the collapse, the tree-dirty commit-on-top, and the no-savepoints branch — and each reaches `/savepoint`'s scan and explicit path list before any bytes are committed. The two dirty-tree paths run it directly; the collapse path inherits it, because every savepoint it collapses was staged by that scan when it was made, and a dirty tree at collapse time is sent through a further `/savepoint` first. So no bytes reach a commit without passing that enumeration once. The guarantee holds by construction of `/ship`'s procedure rather than by anything `/land` does, which is worth stating because a reader of `/land` alone cannot see it. What `/land`'s note *does* carry is the instruction the content half needs: for a noted path, read `git show :0:<path>` rather than the file as it stands.

An **unmerged index** is a *"could not run"*, not a violation: a conflicted path has no single staged version to compare against, and `git commit` refuses until it is resolved. Reporting it as a violation collapsed the split `/land` step 3a states — "could not run" means fix the setup, not the tree.

### 6. Four gaps found while building it, closed here
None was among the six. This list is authoritative; three documents once named a *different* pair of "extra holes", which is what a running count of holes-closed produces. (1) `git status --porcelain` **collapses an untracked directory** to its parent, so a personal file whose parent is untracked is reported as `?? specs/` and no prefix match sees it — `--untracked-files=all` is the fix, and whether the collapse happens depends on whether some sibling directory is tracked, which is not a property a containment scan may rest on. (2) A **shallow clone** silently truncates every history-walking scope (§ Considered Options 5). (3) A **tracked but unmodified** personal file appears in neither the porcelain nor a `merge-base..HEAD` range once its commit predates the base, so `git ls-files -z -- ':(icase)specs/personal'` runs in every scope. (4) Git **quotes** non-ASCII path names in line-oriented output, so every path list is read `-z`.

A fifth is recorded with them because it is the same class, though it was found by the first external review rather than while building: **`log.showSignature`** — an ordinary user config — interleaves gpg's verification lines into `git log`'s stdout with no `-z` delimiter of their own, gluing them onto the front of the next path so that a containment path stops matching. A false negative produced by a setting the *scanned* repository chose, which is why the gate pins that one setting off rather than trusting the environment. It does **not** neutralize git config wholesale the way the test suite does: `safe.directory`, credential helpers and `core.longpaths` live there too, and the suite can neutralize only because it owns the repositories it builds.

A **sixth** was found by the second external review and is the most consequential of the set, because it defeats the gate's whole path vocabulary rather than one flag: **the scan must run at the repository's top level, and nothing checked that it did.** `REPO_ROOT` is derived from `__file__`, so a checkout vendored inside an outer repository — or the script invoked by absolute path from another tree — puts `root` below a top level it never chose. Git then answers inconsistently, in two directions at once (both measured): `status --porcelain` and every `log --name-only` walk answer **top-level**-relative, while `ls-files` answers **cwd**-relative *and* silently restricts itself to the cwd subtree. The first spelling makes `is_personal_path` return False for a path that is under the containment directory — so `--scope history`, CI's backstop, which runs no index comparison and would therefore raise nothing, **exits 0 over a real containment path**. `require_repository_root` refuses instead of translating the paths: rebasing them onto the top level would silently scan a *different* repository from the one the caller named, and this module's rule is that a precondition it cannot satisfy is a failure and never a pass.

### 7. What the second external review settled about failure ordering

Three of its findings were one shape — an invariant or a payload placed in the layer that could not honour it — and the resolutions are recorded together because each constrains where a future check may go.

**An index problem must not cost the walks that need no index.** The staged-content sub-check refuses on an unresolved merge, which is an ordinary state (`/land` merges `origin/main` before landing). Raising where it occurred aborted `check()` on the spot, so the branch-history walk never ran and a personal file force-added by an earlier savepoint was reported by nothing — in exactly the state that most warrants a scan. The refusal is now **deferred**: recorded, the index-free walks run, and it is raised once they have. Simply moving the sub-check last was tried and rejected — notes would then be produced only by the last thing that runs, so no note could ever reach the could-not-run path, trading one silent loss for another.

**`ContainmentError` carries `notes` and `examined`, not just `found`.** The `found` payload was added so a refusal could still name what it had already found; its two siblings were dropped on the identical path, so a run that both refused *and* held a note lost the content half's only instruction for that path. `main()` prints all three on every exit path that has them, violation included.

**`--base`-beside-the-wrong-scope is refused in `check()`, not in `main()`.** A guard in the CLI layer protects only CLI callers, and this module is imported — by its own tests, and by whatever CI grows next — so `check(scope="history", base_ref=...)` reproduced the silent-ignore the guard was added to end, with a green suite. Relatedly, `main()` no longer writes `args.base or DEFAULT_BASE_REF`: the `or` collapsed the `None`/empty distinction that `default=None` had just been introduced to create, so `--base ""` — an unset shell variable interpolated into a command, hole 2's exact shape — reported clean against a base the operator never named.

### 8. What the third external review settled about precondition ordering

Its sharpest finding was §7's own argument left half-applied. `tracked_personal` was hoisted above `require_full_history` because a *history* precondition must not cost a source that reads no history — and the worktree walk, which reads no history either, was left below it. Measured on a `--depth 1` clone whose working tree held an untracked personal file: `--scope branch` refused at the shallow guard and reported `found: []` while `worktree_paths` was naming the violation. The guard now runs after every index-free source. One consequence is load-bearing and worth stating carefully: a shallow refusal can now carry `Note:` lines, where it previously could not — which had made a promise in `/land` false.

**Both skills now state the rule rather than the roster**, and that choice is itself a finding. Every attempt to say *which* refusals are note-free has been wrong, each one the correction of the last: "an unresolved merge is the one exception"; then "unmerged and non-top-level are the whole list at this scope"; then a supporting count in this very paragraph, which claimed a single raise site could carry a note and was contradicted both by the sentence above it and by a passing test. (This sentence first said "four" and the history holds three, which is the same defect a fourth time — hence no number in it now.)

The mechanism is what makes all of those wrong, and stating it is cheaper than any roster: `check()` accumulates notes as it goes and merges whatever it holds onto **whichever** exception propagates. So whether a refusal carries notes is a fact about *how far the scan got before it fired*, not about which raise site it came from — and that changes whenever the order of the scan changes, which this ADR has now done twice. The operator-useful invariant follows directly and needs no enumeration: **a missing `Note:` line is never information.** It is not vacuous — it rules out the specific wrong inference that no note means nothing was noteworthy — and unlike a roster it cannot be invalidated by reordering the scan.

Three smaller asymmetries of the same family were closed with it. The staged loop's mid-loop raise discarded mismatches it had already confirmed, so a real `skip-worktree` violation could be lost to a later path's index inconsistency. `base` was the one `ScanResult` field a refusal dropped, so a deferred refusal — which fires *after* the base resolves — withheld the patch-stream command the content half needs. And the violation exit was the only one printing no evidence line, on the exit where `/land`'s "read the evidence line" instruction matters most.

**The `examined` annotation was also inverted into an allowlist.** It began as a denylist naming the one source that is not a containment test, which leaves a *future* source unannotated by default and read as "paths cleared for containment" — the exact misreading the annotation was added to end, reproduced by omission instead of by drift. Sources that enumerate paths are now named explicitly and everything else is annotated automatically.

Finally, the evidence line now annotates `staged-content` as `(bytes verified)`. It is the one `examined` source that is not a containment test: the others enumerate paths and ask `is_personal_path` of each, while it counts staged paths whose *bytes* were checked, over a set that overlaps `worktree`. Both skills described all the counts alike, and the success sentence folded it into "none of the paths … is under `specs/personal/`" — a test it never ran. The annotation travels in the output rather than in prose, so the line no longer depends on a paragraph elsewhere being read.

## Consequences

### Positive
- All six measured holes are closed, and each is pinned as a negative fixture in `tests/test_check_personal_containment.py` that must fail if the corresponding flag is removed. Verified by mutation in four passes: **25/25** (2026-08-06, after the first external review), **13/13** and **5/5** (2026-08-07, covering the second review and its own smoke rounds), and **9/9** (2026-08-07, covering the third review). Deliberately **not** summed into one figure — the passes overlap, and inventing a total nobody measured is precisely the failure the next bullet records. Re-run the harness rather than restating any of the four.
- **One of the second pass's 13 was not new: it was a mutant the first pass had killed, silently returned to life.** Bypassing `git hash-object`'s filters (`--no-filters`) left all 82 tests passing, because a short-circuit added *after* that pass meant only entries git is told to hide still reached the comparison — and the one test pinning it staged an ordinary visible file. So the behaviour was still correct, still documented, and no longer pinned by anything, while two documents went on asserting it had been verified. **A mutation count is a claim with a shelf life**, invalidated by any later change to a path the harness reached; it dates from a tree, not from a module. That is the argument for re-running rather than citing, stated here because this ADR previously carried the citation.
- **The third pass caught the same shape a fourth time, inside the fix for the third.** Carrying a losing precondition failure on `ContainmentError.also_failed` was pinned by a test that asserted on the exception object, so silencing `main()`'s printing of it left that test green: the payload was proven, the output nobody would otherwise see was not. Every one of these — the deleted `check()` call that left 59 tests green, the `--no-filters` short-circuit, the live-repository test that stopped calling `check()`, and this — is the same defect, which is why the mutation harness keeps earning its cost while reading the tests does not.
- The mutation passes are worth more than the figures. The first found **two survivors nothing else had**: `--diff-merges=first-parent` was pinned on the `branch` walk but not the `history` one — so CI's backstop could have stopped seeing files introduced by a merge commit with the suite green — and the empty-merge-base guard was unreachable from any natural fixture, because both of `git merge-base`'s real failure modes exit non-zero and raise first. Neither is visible by reading; both are now pinned.
- The register's most-failed row moves from *nothing* to *mechanized (enumeration half)* — the first row in that register to change state on evidence rather than on principle.
- The two skills' containment sections stop being two prose copies that can drift; the scope split is a flag over one implementation with one test suite.
- The CI step is self-defending: if anyone drops `fetch-depth: 0` or copies the step into a shallow job, the gate fails loudly instead of passing over a truncated history.

### Negative / Tradeoffs
- The rule now lives in two places for real — this script and `scripts/review_worktree.py`'s guard for the reviewer worktrees. Importing the launcher into the gate was rejected (the containment gate should not stop working because the reviewer launcher is mid-edit), so **both** copies of the rule are pinned against drift: the path *predicate* by a test comparing the two functions over a table of inputs, and the `:(icase)` *pathspec* by a test requiring the two `ls-files` queries to return the same answer on a repository holding every shape the rule has to sort. The pathspec was unpinned when this ADR first claimed otherwise; widening the launcher's query would have left the gate narrower with a green suite.
- `--scope history` uses `--all`, so a personal file on **any** pushed branch fails **every** PR until it is removed. That is the correct strength for a backstop on this rule and is stated here so it is not rediscovered as a bug.
- The gate cannot run in a shallow checkout, which is a real constraint on where the CI step may be placed.
- The gate cannot run anywhere but a repository's own top level, which is the same class of constraint and is stated beside the shallow-clone one deliberately: both are "refuse rather than degrade", and listing only one made the pair look like a special case rather than a policy. It rules out vendoring this checkout inside an outer repository, and it means invoking the script by absolute path from another tree fails loudly instead of scanning whichever repository the caller happened to be standing in. Confirmed to hold inside a **linked worktree** — `git rev-parse --show-toplevel` answers with the worktree's own root — so the reviewer-isolation worktrees of [ADR-0068](0068-reviewer-isolation-worktrees.md) are unaffected.
- The content half remains exactly as strong as the reader, which is the honest residual: this ADR shrinks the manual control, it does not retire it.
