# ADR-0069: Local Checkpoint Commits via /savepoint

## Status
Proposed

## Context and Problem Statement
The skill chain has no verb for a local commit. `/land` runs the gates and proposes a commit message, then stops; `/ship` commits, pushes, and opens the PR in one motion. The only way to get a commit is to publish, so nothing gets committed until the work item is finished. The branch that introduced ADR-0068 ran its entire review program — eleven external passes and dozens of local smoke passes — at **zero commits**, and the costs were measured rather than hypothesized ([open-questions.md](../open-questions.md), "Align the tooling, agents, and skills to WIP commits before review"): every review pass re-read the whole multi-thousand-line tree instead of a diff; `/apply-review`'s drift check compares the report's pinned `HEAD` against the current `HEAD`, and with no commits `HEAD` never moves, so a live safety check was structurally incapable of firing; the working tree was the only copy of thousands of lines of new work; and the eventual squash commit was 8,868 lines — roughly nine times past the ~1,000-line threshold where published measurements put the collapse of review defect detection (≈70% drop).

The one recorded objection to intermediate commits — personal data could enter the commit object and survive `--amend` and `reset` in the reflog — was scoped to one specific mechanism: an **automatic `git add -A` fired at reviewer launch**, where automation picks the file set and no containment check runs first. That objection was allowed to stand as a blanket veto, and it cost over a week of zero-commit work. It says nothing about a deliberate commit made behind the same containment scan `/land` already runs, over an explicitly enumerated path list.

Two `/land` defects surfaced by the same branch belong to this decision because they bite at exactly the boundary it creates — a work item that spans sessions:

1. `/land`'s report quoted a tree hash measured **before its own later edits** (the step-5 decision-capture records and a subsequent fix), presenting a reviewed-round hash as the hash of the tree being proposed. The number was true when taken and false where it was printed; clearing it cost a full investigation before anyone was willing to commit.
2. The composed commit message survived **only in the conversation transcript**. When the session ended before `/ship`, the approved text had to be recovered by parsing the session's `.jsonl` line by line.

## Decision Drivers
- The checkpoint must be cheap — no test gates, no message ceremony — or it will not get run, and the status quo above returns
- Nothing personal may enter **any** commit object, even a local one: reflog persistence outlives `--amend` and `reset`, so the scan must run before every commit, not only before the push
- Public history must be unchanged: one composed commit per PR, which is what `/squash-merge` produces today
- The commit boundary should land where the next smoke pass wants to start its diff, and the drift check should gain something to fire on
- The name must not collide: `/wip` is one character from the existing `/wi` skill; a `wip:` subject is also what commit-message linters in the wider ecosystem reject by default (the external `commit-check` tool ships `allow_wip_commits = false` — no such gate exists in this repo today, but adopting one must not invalidate the checkpoint subjects); "checkpoint" is Claude Code's built-in session-scoped feature; "snapshot" already means `git stash create` inside `scripts/review_worktree.py`

## Considered Options
1. Status quo — no commits until `/ship`
2. Side-ref auto-snapshots (the Magit WIP-mode pattern: commits to `refs/wip/*`, branch history untouched)
3. Auto-commit at reviewer launch (`git add -A` before each round)
4. **A deliberate three-step checkpoint skill, local-only, collapsed by `/ship` before the first push** (chosen)
5. Option 4 without the collapse — push the checkpoints as they are and point `/squash-merge` at the carrier file (`commit-msg/<branch>.txt`) instead of the branch's first commit body (raised by the external review of this ADR's own implementing branch, which observed that the collapse's entire guard apparatus — the remote push-probe, the verified merge base, the sole-first-pusher precondition — exists only to protect a rewrite whose sole consumer is that one extraction)
6. Option 4 with the composed message in a **repo-scoped** carrier rather than the session scratchpad — `$(git rev-parse --git-common-dir)/land-msg/<branch>`, or a `refs/`-namespaced blob (raised by the third external review of the same branch, which observed that option 5 is rejected on properties of the scratchpad *location* rather than of file carriers as such)

## Decision Outcome
Chosen: **option 4**. Option 1 is the measured status quo in the problem statement. Option 2 is the mature prior art, and its two documented limitations are exactly this repository's case — untracked files are never saved, and nothing is saved before the first commit; the ADR-0068 branch had seven untracked files (including its largest one) and zero commits, so the strongest side-ref implementation would have protected nothing at all. Option 3 is the mechanism the containment objection correctly kills: automation picks the file set, no scan runs first, and the object persists in the reflog.

Option 5 is rejected on durability and visibility, deliberately — its accounting of what the collapse costs is accurate, and the guards it would delete are kept because they are already written and cost nothing per run. The carrier file lives in a session-scoped scratchpad, a temp directory with no survival guarantee, while a PR's review lifetime here spans days, bot rounds, and sessions; resting the merge message on that file re-creates the exact loss class defect 2 in the problem statement records (the approved text gone when it is finally needed), discovered at merge time. And the composed message would never appear on the PR at all: as the branch's first commit it is durable by construction, reviewable by every lens the PR gets, and what `/squash-merge` verifiably extracts — the merged message provably matches what was pushed and reviewed, a property no machine-local file can offer. Revisit trigger: if `/squash-merge` ever gains a durable, PR-visible carrier for the composed message (a pinned PR comment, a committed file), this rejection's grounds dissolve and option 5 becomes the simpler design.

Option 6 is not taken either, and its accounting is worth writing down because it reads cheaper than it is. It genuinely dissolves the **durability** half of option 5's rejection: a carrier inside the repo's own git directory survives session end and compaction, and it would retire `/ship`'s cross-session precondition ("if `/land` ran in an earlier session, the file is under *that* session's scratchpad — ask the user for the path"). It leaves the **visibility** half untouched, and that half stands alone — the message would still be machine-local, still absent from the PR, and `/squash-merge` still could not prove the merged body matches what was pushed and reviewed. The plain-path spelling also retires neither the Windows collision analysis nor the `.branch` sidecar: `.git/land-msg/feat/x` is an ordinary filesystem path, so it inherits the whole API-dependent mess described in §4 unchanged. The `refs/` spelling genuinely does remove the silent case — though not by git's directory/file rules, which never engage since both `refs/land-msg/a./b` and `refs/land-msg/a/b` pass `git check-ref-format`; what happens is that git's own loose-ref write refuses the mangled component and **fails closed**, exit 128, in *both* write orders (measured — creating the colliding ref first or second makes no difference, so it is a property of the write rather than of what is already on disk).

The honest ledger is therefore narrow: one precondition retired, and — only in the `refs/` spelling — one silent failure traded for a loud one. Against that sits a subtlety of its own, since `git rev-parse --git-dir` resolves to a *linked* worktree's gitdir inside ADR-0068's reviewer worktrees, so the recipe would have to specify `--git-common-dir`. And the durability being bought is smaller than it first appears: the carrier is load-bearing only in the window between `/land` and the **first** `/ship`, because the collapse in §2 puts the message into the branch's first commit and `/squash-merge` reads it from there forever after. A carrier lost after that window costs nothing; a carrier lost inside it costs one `/land` re-run. Revisit alongside option 5 rather than separately — the visibility argument decides both, and it is untouched by any of this. The deferral, its trigger, and the recommendation carried into whoever takes it up are recorded in [open-questions.md](../open-questions.md), "Where the two branch-keyed carriers live", because `/review-prep`'s carrier has the identical problem and the two are one design question.

### 1. The skill — three steps, nothing else
`/savepoint` — named for the SQL construct with the same lifecycle: a named intermediate point inside a transaction, released when the transaction commits. Its whole procedure:

1. **Containment scan** — the working-tree half of `/land` step 3 (whose whole-branch history clause stays `/land`-only, as the backstop over every accumulated savepoint): `git status --porcelain` shows no `specs/personal/` path (it is gitignored; its appearance means the ignore broke — critical), and every added or modified file outside it is checked for personal health values, lab results, diagnoses, medications, or owner-identifying information. No ruff, no pyright, no pytest — the scan is the one step that is never optional, and the absent gates are what keep the skill cheap enough to run.
2. **An explicit path list** — echo the set of files this checkpoint covers, then `git add` exactly those paths. Never `git add -A`, never `git add .`, never `git commit -a`. The enumeration is the entire distinction from rejected option 3: a person (or the session, deliberately) names what enters the object, after the scan has seen it — and because `git commit` commits the whole index, the skill reconciles `git diff --cached --name-only` against the echoed list and stops on any extra path, so pre-staged content cannot ride along unenumerated. The reconciliation is on **paths and content both**, which is part of this decision rather than an implementation detail: a path check alone proves what is staged, never that it holds the bytes the scan read, and `git add` declines silently to update a `skip-worktree` or `assume-unchanged` entry — measured, leaving a personal-data blob in the index behind a path list that passes. Each enumerated path therefore has `git rev-parse :<path>` compared against `git hash-object -- <path>` before the commit — a blob-level comparison, which survives the repo's `eol=lf` normalization because `git hash-object` applies the path's attributes by default (`--no-filters` is the opt-out; measured, the plain form reproduces the staged blob while `--no-filters` does not, so no `--path` is needed). A path staged as a **deletion** is exempt and must be, not as a convenience: it has neither an index blob nor a working-tree file, so both halves of the comparison fail outright, and a deletion contributes no bytes to the object in the first place. The path list still governs it. A **rename or copy** record carries two paths (`R100  old  new` — measured), so the reconciliation reads the record's fields rather than assuming one path per line and compares the *destination*, which is where the staged bytes live; the source is governed as a deletion is. Raised by the Greptile review of this ADR's own PR (#80), whose stated mechanism — an already-staged enumerated file — is in fact closed by the `git add`, while its conclusion that the control was path-only held by another route.
3. **Commit** — a bracketed phase tag plus a plain imperative one-line subject describing the chunk. No `Decisions:` section, no co-author trailer — those belong to the landing commit that `/land` composes.

   The tag encodes **phase and round**: `[b]` build, `[bs<M>]` a smoke pass during the build, `[x<N>]` applying external review `N`, `[x<N>s<M>]` a smoke pass inside that apply, `[g]` a standalone gate fix, `[l]` land prep. It is a reading aid rather than a marker for locating checkpoints — `/ship` collapses `merge-base..HEAD` by definition and never needs to find them — and it is deliberately not `wip:`, which says only "unfinished", true of every checkpoint and therefore distinguishing nothing. The requirement came from the owner reading a mid-iteration branch (2026-08-04): eighteen subjects that all looked like ordinary commits, with nothing separating the original build from the fourth correction of a single review finding. `[x2s4]` carries exactly that, which is also why a guessed number is worse than none.

   **The vocabulary split is part of the decision.** A **review** is a round of the purchased external loop; a **smoke** is a local `spec-reviewer`/`test-reviewer` pass, free and uncounted. Both were called "review" until this tag put two counters in one string and made every spoken sentence about them ambiguous (owner, 2026-08-05). The external loop keeps the word because it is anchored on `/code-review`, a built-in command that cannot be renamed, so the local side is what moves; the agent names stay, since the ambiguity was in the round noun rather than in the agents. It also encodes the owner's standing rule that only the external loop is convergence evidence — a vocabulary that separates them stops a ledger being padded with passes nobody bought.

   **The rename's scope is this decision's own vocabulary** — the tag, `/savepoint`, `/apply-review`'s checkpoint sites, and this ADR — and stopping there is deliberate rather than missed. `.claude/reviewer-isolation.md`, `/ship` and `.claude/bot-review-triage.md` still say "reviewer round" for the same thing, and they read correctly where they stand: the ambiguity this decision fixes arises where a *number* is attached and two counters share one string, which is true of the tag and of nothing else. Sweeping those would be churn rather than clarity; fold them in whenever one of them is next opened for its own reasons.

The skill refuses to run unless HEAD is on a branch other than `main`, and never pushes. `main` is refused because a checkpoint there cannot be collapsed by `/ship`, which refuses `main` itself. A **detached HEAD** is refused for a stronger reason: none of the three steps is branch-aware, so all of them succeed and leave a commit on no branch — orphaned by the next checkout, unreachable to any `merge-base..HEAD` collapse, and rejected by `/ship` step 1, whose sidecar comparison meets the literal `HEAD` that `git rev-parse --abbrev-ref` returns there. The scan would run and the work would be committed while the single property the checkpoint exists for is void. `git symbolic-ref -q HEAD` (exit 1 when detached) is the test, since `--abbrev-ref` reports a plausible-looking string rather than failing.

### 2. Lifetime — local until /ship collapses
Checkpoints never leave the machine as themselves. `/ship`, **before the first push only**, collapses the branch: a final `/savepoint` if anything is uncommitted, then `git fetch origin`, then `git reset --soft` to the verified merge base with `origin/main`, then `git commit -F` with the `/land`-composed message file. The fetch is part of the decision, not hygiene: `git merge-base` reads the local tracking ref, and a stale `origin/main` resolves the base too far back, folding commits that are already upstream into the PR's one composed commit. Public history is therefore unchanged from today — one commit per PR, which is also what `/squash-merge` produces at merge. The reflog keeps the chunks for local archaeology.

Three properties of that sequence are decided here rather than left to the skill's prose, because each of them is the difference between a collapse and a loss:

- **The pre-collapse checkpoint triggers on any uncommitted state, untracked files included** — `git status --porcelain` printing any line at all. This is deliberately *not* the tracked-modified discriminator `/land` step 7 uses for tree hashes; that one exists because `git stash create` cannot hash untracked state, and importing it here would read an untracked-only tree as nothing-to-do and collapse a branch whose new files were never staged. The problem statement above records that exact tree: the ADR-0068 branch carried seven untracked files, including its largest.
- **The reset and the commit are not atomic, so the rewrite gets a named recovery.** `git reset --soft` succeeds and `git commit -F` then exits 1 whenever the savepoints net to no diff against the merge base (a file added by one checkpoint and removed by a later one), leaving the branch at the merge base with every checkpoint off the tip. `git reset --soft ORIG_HEAD` restores it. "The reflog keeps the chunks" is archaeology, not recovery, and the one moment an operator needs the command is the moment the branch looks destroyed.
- **The push-probe is anchored and three-valued.** `git ls-remote --exit-code --heads origin "refs/heads/<branch>"` — the full ref, because a bare branch name matches on the ref *tail*, so a local branch whose name equals the last segment of any remote branch probes as already-pushed (measured against this repo's own origin) and skips the collapse. Exit 0 is present, exit 2 absent, and **any other exit is no evidence either way** — 128 covers an unreachable host, an unknown remote name, and an expired credential — so it fails closed rather than being read in either direction.

If the branch has ever been pushed — decided by that probe, never a local tracking ref, since a pruned or never-created tracking ref reading as "never pushed" is what would aim the rewrite at published history — `/ship` does not rewrite, and what it does instead depends on where the new work sits: uncommitted work is staged the savepoint way and committed on top, while work already sitting in savepoint commits is **pushed as it stands**. That second case is the ordinary second ship of any branch, and there is nothing left to commit — `git commit -F` against an empty index exits 1. The savepoint subjects then appear in the PR's history, which costs nothing: `/squash-merge` composes the merge from the *first* commit's body, and that is still the message the first ship landed. The consequence that must be *reported* rather than merely tolerated is that the message `/land` composed for this second ship is verified and then unused: invoking `/ship` is the user's approval of that text, so leaving the divergence silent lets an approved message read as landed when the merge body still comes from the first ship's.

Containment consequence: a stray caught at any point before `/ship` never leaves the machine, because `/land` still gates `/ship` and `/ship` still gates the only push. The residual risk is a stray blob persisting in machine-local objects and reflog until garbage collection even after the collapse — accepted, with the scan-before-every-commit as the control that keeps the case from arising.

### 3. Insertion points
In descending order of leverage:

- **Inside `/apply-review`, after each finding batch and at the end of each smoke pass** — the writing happens there, and a per-pass checkpoint puts the commit boundary exactly where the next one wants to start its diff.
- **Before a smoke pass** — not as refusal-on-dirty-tree (too strict; the launcher exists precisely to review uncommitted state), but as a recorded `git rev-parse HEAD` alongside the setup manifest, giving `/apply-review`'s drift check and any later session a stable anchor.
- **End of session** — insurance against the context exhaustion that split the ADR-0068 work item across sessions with nothing committed.

### 4. What changes in /land and /ship
- `/land`'s survey (step 1) extends to `merge-base..HEAD` plus the uncommitted tree, and its containment scan (step 3) covers **every path the branch's history ever touched** (`git log --name-only`, not the endpoint diff — a file committed by one savepoint and deleted by a later one is invisible at both endpoints while its blob rides every push of those commits). With checkpoints, the branch's files no longer appear in `git status --porcelain` — the pre-push containment gate must read the history or go structurally blind to everything already checkpointed. That history scan takes **`--diff-merges=first-parent`**, which is part of this decision rather than an invocation detail: `git log` reports no paths at all for a merge commit by default, so a file introduced by the merge itself — resolving a conflict in favour of keeping an added file, on a long-running branch that merges `origin/main` — is examined by nothing and pushed (measured). The flag makes each merge report its diff against the tip it was merged into. It over-lists paths that arrived from the merged-in side and are already upstream, which is the correct direction to err: a file scanned needlessly costs a read, a file skipped costs the invariant. The backstop covers **blob contents as well as paths**, via the branch's first-parent patch stream (`git log -p`) rather than the current files: a value committed by one savepoint and sanitized by a later one is clean in every present file while the dirty blob stays reachable in history and rides the push — the same intermediate-state argument as the deleted-file case, applied to content. Every line any savepoint added appears as a `+` line in that stream, so it covers the intermediate blobs without enumerating them.
- `/land` measures the tree hash **last**, after every edit it makes (its step-5 decision-capture records included), and labels it as the hash of the tree it is proposing — stating that the hash covers tracked state only, with untracked files hashed separately (the split `.claude/reviewer-isolation.md` states under § The two invariants, invariant 1). Byte-identity to a reviewed snapshot is a separate claim that must name the delta. This closes defect 1 in the problem statement.
- `/land` writes the composed commit message to `<scratchpad>/commit-msg/<branch>.txt` — branch-qualified so `/ship` can refuse another work item's leftover file, with the branch name carried **as a path rather than flattened** to `-`, and the exact branch name written beside it in a `<branch>.branch` sidecar. Flattening is not injective: `feat/x` and `feat-x` collide on one filename, and either one's stale file would then pass the check and ship the wrong `Decisions:` links. The path form removes that collision but is **not** a uniqueness guarantee, and the decision is not to pretend otherwise. What a branch-derived path names on Windows depends on which API resolves it, and the chain from `/land` to `/ship` crosses three: for the legal branches `a./b` and `a/b`, a .NET write normalizes the trailing dot and silently overwrites, a Node write keeps both files while a later .NET read of `a./b` silently returns `a/b`'s contents, and `git commit -F` — the operation `/ship` actually performs on this file — exits 128 with `could not read log file … No such file or directory` while the file sits on disk. All measured; reserved-device names such as `nul` write as ordinary files rather than failing, as a fourth case. These deliberately are **not** ranked into safe and unsafe: only git's read halts at its own point of failure, while the .NET write completes silently and is safe purely because the sidecar catches it downstream — a property of the mechanism rather than of the write, so a ranking would license trusting a layer to be loud. There is no single true statement about the filesystem for this to rest on, which is the argument for a checked value: whichever layer produces the wrong bytes, the result is a branch name that does not match `git rev-parse --abbrev-ref HEAD`. Ownership therefore rests on a checked value rather than a filesystem property — `/ship` compares the sidecar's line against `git rev-parse --abbrev-ref HEAD` (trimmed, since a Windows tool may emit CRLF and a correct ship must not be blocked by a line ending), so a collision becomes a loud mismatch instead of another work item's message. The sidecar is written **after** the message, and that ordering carries the guarantee: interrupted between the two writes it leaves a stale sidecar, which mismatches and stops; reversed, it would leave a correct sidecar vouching for a stale message. The ordering therefore binds every *rewrite* of the message too, not only the first write — revising the message after the sidecar exists reaches the reversed state without anyone reversing anything, and that case fires far more often than the interruption the rule was designed for, since `/land` corrects its own proposal as a matter of course. Dogfooding this decision produced it twice inside the run that landed it. The guarantee is scoped to cross-branch contamination — a same-branch re-run meets a sidecar already naming that branch — and the residual is accepted, since `/ship` also requires a message the user has seen. UTF-8 without BOM, LF line endings, and the path is printed; `/ship` verifies the file's branch and co-author trailer, consumes it with `git commit -F`, and diffs the landed message back against the file (`git commit -F` applies whitespace cleanup, so fidelity is verified, not assumed). This closes defect 2, and the same file is what the collapse in §2 commits.

### 5. The drift check flips from cannot-fire to fires-routinely
Which *branch* a report belongs to is checked first and on its own, because the classification below answers only where HEAD sits. A report pinned on one branch and applied in a session sitting on a sibling branched off the same commit passes every step of it and comes out classified as the expected steady state — reassuring output for findings being applied to the wrong branch, and the only place the mismatch can surface, since nothing downstream consumes the branch name.

`/apply-review` step 1's `HEAD` comparison now fires whenever savepoints have landed since the report was pinned — which is the intended steady state, not an alarm. The response is a three-step classification with real detectors, because `git log <sha>..HEAD` alone runs happily from a dangling SHA and fails toward "explained": (1) `git cat-file -e` — an unknown or gc'd anchor is reported as unresolvable; (2) `git merge-base --is-ancestor` — an ancestor means savepoints landed since: enumerate `git log <report-sha>..HEAD --oneline`, report what the intervening checkpoints touched, and treat findings citing those files with extra care during re-verification; (3) otherwise compare the report's recorded **tree hash** against `HEAD^{tree}` — a match is `/ship`'s collapse (explained, the per-commit SHAs are gone by design), a *recorded* hash that differs is real drift to warn about, and **no recorded hash at all is a third outcome**: unclassifiable, reported as such, deferred to per-finding re-verification. Reading absence as drift would fire the false alarm this mechanism exists to remove on every report predating the field. That the field exists at all is part of this decision: `/review-prep` captures the tree hash into its carrier and `/review-handoff` records it in the report header, next to the SHA and under the same never-fabricate rule. Without that, the fallback keys on a field no report was obliged to carry, and the classification's third step is unreachable by construction. Two consequences follow for how that field is read. A report carrying the sentinel `unknown — prep skipped` — what `/review-handoff` writes when it cannot honestly anchor the hash — is the **third** outcome and not a mismatch: it is not a hash, it can never match, and classifying it as recorded-but-different fires the drift alarm on exactly the reports that already declared they could not anchor themselves. And the carrier's ownership rests on the `Branch` field it records, not on its filename, which flattens `/` to `-` and therefore cannot separate `feat/x` from `feat-x`; `/review-handoff` compares that field against the current branch before trusting anything in the file, because a foreign carrier holds real values from a real branch and would answer this classification confidently and wrongly rather than failing. This is a behavior change in a check that belongs to the review mechanism ADR-0068 governs, which is why this decision is an ADR rather than a skill edit alone.

The classification's commands, and the collapse's guards, are **Bash**. Git's extended revision syntax does not survive PowerShell's parser: `{tree}` is taken for a script block and serialized into `-encodedCommand <base64>`, so `<sha>^{tree}` arrives as three arguments and `git rev-parse` answers the first, printing a *commit* hash where a tree hash was asked for (exit 128). The exit code is the diagnostic, not the value — which commit comes back depends on where the quotes fall, and three spellings of the same intent return three different commits, all exiting 128. `^{commit}` mangles identically, and what it costs depends on the command: `git rev-parse` exits 128 again, while `git cat-file -e` reads the injected switch as a bundle of short flags and exits **129**. All measured on this machine, which runs PowerShell as its primary shell. A liveness probe that misparses reports a live anchor as gc'd, and a guard that misparses does not guard. The affected skills declare the shell, and revisions are quoted whole (`"$sha^{tree}"`) so the recipes survive either parser.

### Positive Consequences
- Revert and diff points per chunk; a smoke pass can diff against the previous one's checkpoint instead of re-reading the tree
- The drift check becomes a live check with a defined firing behavior
- An untracked file's between-rounds history becomes provable with `git diff <sha> <sha>` — cost 4 of the open-questions entry, closed by definition
- A clean checkpointed tree takes `scripts/review_worktree.py`'s already-tested branch-diff path (`test_branch_diff_alone_is_enough_to_review`) — no launcher change is needed to start
- The open question of whether commit-first makes Claude Code's built-in `isolation: worktree` viable becomes answerable with practice data, which is the stated prerequisite of the retirement sweep

### Negative Consequences / Tradeoffs
- `git reset --soft` is history rewriting — deliberately confined to never-pushed commits, with "does `origin/<branch>` exist" as the guard
- A stray blob in a local checkpoint persists in machine-local git objects until gc even after the collapse — accepted; the per-commit scan is the control, and the object never leaves the machine
- The containment scan is prose-run, not mechanized — the same status `/land` step 3 has today; the repo-invariants register (open-questions.md) books this enforcement class. **Partly discharged 2026-08-06** (this ADR is still Proposed, so the line is corrected in place rather than superseded): the scan's *enumeration* half is now `scripts/check_personal_containment.py`, which both skills invoke and which CI runs over full history. The *content* half — whether a value is synthetic — remains prose-run in both skills, so the tradeoff this line records is reduced rather than retired
- `/apply-review`'s "do not commit" rule needs a carve-out: savepoints yes, landing commits no — a distinction that must stay legible in that skill's text
- More commits means more subjects to write — kept cheap by the no-gates and no-trailer rules; if per-batch granularity proves too coarse, Aider's per-edit-turn granularity is the documented finer setting
