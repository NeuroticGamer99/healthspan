# ADR-0061: Markdown Link-Check Gate for the Docs-Consistency Job

## Status
Proposed

## Context and Problem Statement
The docs-consistency CI gate ([ADR-0045](0045-repository-workflow-and-ci-enforcement.md) §6) runs one script, [`check_adr_index.py`](../../scripts/check_adr_index.py), which validates the ADR *index table* against the files on disk. It does **not** validate the cross-file markdown *links* that thread the spec corpus together. The Phase-3.5 review-doc relocation into [reviews/](../reviews/) (PR #38) rewrote ~200 relative links by hand and verified them with a one-off script that was then discarded. Nothing now prevents a future PR from reintroducing a dead link — a reference to an old `specs/architecture-review-*.md` path, a moved script, a renamed ADR — and passing CI green. A 404 that lands inside an immutable Accepted ADR is doubly costly: [CLAUDE.md](../../CLAUDE.md) rule 5 permits the corrective link edit without a superseding ADR, but it is governance friction that a gate would prevent outright.

[testing-strategy.md](../testing-strategy.md) (CI Gates) frames every gate as mechanizing "requirements that would otherwise depend on code-review vigilance," and [ADR-0045](0045-repository-workflow-and-ci-enforcement.md) §6 casts the docs gate as the "generate-or-test" item. Link integrity sits squarely in that mandate. This ADR **extends [ADR-0045](0045-repository-workflow-and-ci-enforcement.md) §6** — it adds a second script to the existing docs-consistency job — and reverses none of ADR-0045's decisions.

## Decision Drivers
- A dead link inside an Accepted ADR is easy to introduce (any file move) and carries governance ceremony to fix; the asymmetry argues for prevention over cure.
- The corpus is link-dense and cross-referential; manual vigilance held on PR #38 *only* because someone wrote and then threw away a checker — that is exactly the review-dependence a gate exists to remove.
- [ADR-0045](0045-repository-workflow-and-ci-enforcement.md) §4: a new gate joins the `ci-ok` fan-in and never touches branch protection, so the marginal cost is one script plus one CI step.
- Precedent: [`check_adr_index.py`](../../scripts/check_adr_index.py) is stdlib-only with no runtime dependency; a link checker should meet the same bar. (Met at inception; the 2026-08-08 scope revision relaxed it to "stdlib + a git subprocess for source enumeration", and the 2026-08-22 revision relaxed it again to add `markdown-it-py` — both tradeoffs are recorded under Consequences. The bar was the right *default* and the wrong *invariant*: hand-rolled CommonMark parsing was written to hold it and corrected repeatedly, each time for a defect that failed silently. No generation count is given, and that is a 2026-08-23 correction — the family read "four generations" / "a fifth private copy" in six places across the source and twice in this ADR until a review measured it against `git log --follow`, which shows two landed commits on `check_spec_links.py` before the parser change; the number described the abandoned branch's own iteration rather than this file's history.)

## Considered Options
1. **A new blocking gate authorized by this extension ADR** (chosen) vs. **wiring the gate under [ADR-0045](0045-repository-workflow-and-ci-enforcement.md) §4's "adding a gate is routine" mechanism with only a PR `Decisions:` note.** §8's no-ADR precedent ("report-only coverage may be added later without an ADR") is explicitly scoped to a *report-only* gate. This gate is *blocking* — it fails the docs-consistency job, which fans into `ci-ok` and stops the merge — and it changes what §6 documents the docs gate as running. A new blocking enforcement surface is a stronger step than report-only coverage, so [CLAUDE.md](../../CLAUDE.md) rule 1 fires and the extension ADR is required; the `Decisions:` note supplements but does not substitute for it.
2. **File-existence validation only** (chosen) vs. **also validating `#fragment` anchors.** A `#L123` line anchor cannot be meaningfully validated against a file whose lines shift; heading anchors could be, but the dead-*file* link is the failure mode observed and worth the low false-positive risk. Anchor validation is deferred, not rejected.
3. **Crawl all repo markdown — tracked plus untracked-but-not-ignored** (chosen, revised 2026-08-08) vs. **scope to the specs/ tree** (the original choice). The original scoping reasoned that the observed failure mode lived under specs/ and root-level sources could wait "if a need appears." The need appeared: the `.claude/**` tree grew to 17 tracked markdown files — skills and agent definitions whose prose the review pipeline executes as instructions — outside every docs gate, and an audit (finding J8) showed a durable rule copied into those files could rot with CI green. Rather than adding `.claude/` to an enumerated list (the mechanism that just went stale), the source set becomes **every `*.md` git considers part of the repo** — tracked plus untracked-but-not-ignored (`git ls-files --cached --others --exclude-standard`), the same file-set contract as the repo's other tree-walking gates — so a new markdown file is gated from the moment it is written, not the moment it is tracked; `/land` runs this gate *before* staging, which is exactly when a fresh doc's dead links would otherwise escape it. `specs/personal/` remains excluded — by the script's explicit `PERSONAL_DIR` filter, which holds even for a force-added tracked personal file (`--cached` would list one); gitignore makes that case abnormal but is not the exclusion mechanism.

## Decision Outcome

### 1. A new script, `scripts/check_spec_links.py`
It crawls every `*.md` git considers part of the repo — tracked plus untracked-but-not-ignored (enumerated by `git ls-files --cached --others --exclude-standard`; originally the specs/ tree only — see option 3) except `specs/personal/`, extracts each `[text](target)` link, and resolves every **relative** target against the linking file's directory, reporting any that does not exist. External (`http(s)://`, `mailto:`) and pure `#anchor` targets are skipped; a `#fragment` is stripped before resolving (file existence is checked, anchors are not); targets that resolve under `specs/personal/` are skipped as unvalidatable. Code is removed before scanning, so an example link quoted in code — the arc42-cell reference `[adr/](adr/)` in [architecture-review-2026-07-06.md](../reviews/architecture-review-2026-07-06.md) is the live case — is not mistaken for a navigable link. Exit 0 when every link resolves, 1 with one line per problem found, **2 when the check could not run at all** (2026-08-23: a missing `markdown-it-py`, a `git ls-files` failure, or a mask that broke its own line invariant). The third code was added when a review pointed out that the `ImportError` guard's own comment justified it as making a could-not-run distinguishable from a dead link, and then returned 1 — leaving a caller that reads the exit status alone in exactly the position the guard was written to prevent.

**Revised 2026-08-22: what counts as code is decided by a CommonMark parser, not by regexes.** The script now parses with `markdown-it-py` and exposes `code_masked_lines` — one line per source line, code blanked — as the single place that decision is made. The regexes it replaced were wrong in both directions and silently: a fence indented under a list item (and a tab-led fence) opened nothing, so every link inside such a block was scanned as live prose; and an inline code span could not cross a line break, so a span written across one stopped being a span. A span may now cross one, but the block-wide pairing that finds it is a *candidate* finder rather than the decision: every span it proposes is checked against the parser's own `code_inline` tokens, and the block drops back to line-local blanking on any disagreement. Left to decide alone it contradicted the parser it was adopted to agree with — measured, a backtick inside a link destination paired with the one opening the real span and blanked a genuinely dead link out of the gate's sight, and a backslash-escaped backtick, which CommonMark says opens nothing, did the same. Both are silent, which is the direction this gate cannot afford. An HTML block is blanked outright for a different reason: its content is raw HTML rather than markdown, so nothing quoted inside one — including a whole fenced block, which markdown-it emits no `fence` token for — is a live link. Indented code blocks are now masked too, which the regex walk never did. Cross-line span tracking had been declined here for years because an unterminated backtick could swallow the rest of the file — a block parser removes that hazard rather than accepting it, because a span is blanked *within one block* whose bounds the parser supplies. Measured old-vs-new over the whole corpus at adoption: **130 markdown files, 0 divergence**, with the constructed defect shapes each changing as intended — the run reported `147 inputs, 141 identical, 6 diverged`, every one of the six being a fixture (a fence in a list item, a fence in a nested list, a tab-led fence, an indented code block, a span across a newline, and a span inside an HTML block), and every real file agreeing. That measurement is **reproducible rather than asserted** — [`scripts/diff_check_spec_links.py`](../../scripts/diff_check_spec_links.py) runs both revisions' `link_targets` over the adversarial fixtures in its own `FIXTURES` table — **no count here, and its absence is the third instance of one lesson** — plus every markdown file git considers part of the repo, and `uv run --locked python scripts/diff_check_spec_links.py --base <pre-adoption rev>` re-derives it. Its snapshot machinery — materialise both revisions, import each under a name of its own, diff — lives in [`diff_harness.py`](../../scripts/diff_harness.py), which is written to be shared from the start rather than copied by the next harness; the rule it carries, *snapshot the dependency closure per revision and not the file*, is in that module's docstring where the next author will read it. `code_masked_lines` is public for the same reason the measurement is committed: the next checker over this corpus imports it rather than growing a private parser of its own. (The deleted count said "17 at this revision" *inside the clause explaining that a count is what rots*, and then rotted: measured across this file's history, every committed state of the sentence read 17, while `FIXTURES` went from 17 to 18 when a later round added the `span-across-hard-break` fixture — so the claim was true when written and false from that commit on, and a reviewer caught it rather than the discipline the sentence was preaching. The clause also narrated an earlier "it read 16 while the hunk rewriting this sentence was adding the 17th"; that is the original author's account of an *uncommitted* intermediate state and no committed revision shows it, so it is repeated here as their account rather than as something re-measured. The number is now gone rather than corrected a second time — `len(FIXTURES)` is one command away. The past-tense figures elsewhere in this paragraph stay, because each records what a specific run printed on a specific day rather than claiming anything about now; the corpus has grown since, so none of them would survive being read as current.)

### 2. Wired into the existing docs-consistency job
The script runs as a second step of the `docs-consistency` job in [`ci.yml`](../../.github/workflows/ci.yml), alongside the ADR-index check. Both feed the `ci-ok` aggregate ([ADR-0045](0045-repository-workflow-and-ci-enforcement.md) §4), so a dead link fails the PR without any change to the branch-protection ruleset or the set of required checks.

**Revised 2026-08-22: this step runs under `uv run python`, not bare `python3`.** The dependency in §1 has to come from somewhere, and the job already installs `uv` for its pinned-version steps, so the move is one line in `ci.yml` and one entry in [`run_gates.py`](../../scripts/run_gates.py)'s registry — no new CI step and no new setup action. It is a down payment on putting every repository script under a controlled interpreter, not that whole change: the sibling docs gates still run bare, because they still only need the stdlib. Under a bare interpreter this gate now fails **loudly** — `main` catches the `ImportError`, names it, and exits non-zero, which is the correct direction for a gate but is why the invocation had to move in the same change rather than after it. (It reported a raw `ModuleNotFoundError` traceback until external review round 4; a traceback is loud to a human and indistinguishable from a real dead link to a caller reading only the exit status.)

**Two knobs go with that move, recorded here rather than left in the runner** (CLAUDE.md decision-capture rule 4). The invocation is `uv run --locked`, not a bare `uv run`: without `--locked`, `uv run` re-locks and re-syncs whenever `pyproject.toml` has moved ahead of `uv.lock`, which rewrites a *tracked* file from a gate that reads as read-only — and locally this gate runs **before** the `lockfile` gate, so it would repair the `uv.lock` that `uv lock --check` then certifies. Local green, CI red on a clean checkout. (The relation is what the argument rests on; the ordinal is not, and this sentence carried an invented one — "runs sixth" — until a reviewer measured it. No position is quoted in its place: an ordinal into a registry that gains entries is wrong the moment one is inserted above it. `tests/test_run_gates.py` pins the ordering relation instead.) In CI the same flag covers a different gap: `docs-consistency` is the only job that invokes `uv run` **against the project environment** without either a preceding `uv sync --locked` or `--locked` on the invocation itself, so without it the one gate whose verdict *is* parser behaviour would re-resolve `markdown-it-py` against a lockfile that already pins a version. That scoping is load-bearing rather than pedantic, and the two words doing the work are `uv run`. Measured over every uv invocation in `ci.yml`: `typecheck` and `test` both run `uv run` and both sync first; `lint` runs only `uvx`, which resolves an isolated ephemeral tool and never touches the project lockfile; `pip-audit` runs `uvx` **and** a `uv export --locked`, which does resolve the lockfile but is not `uv run` and carries `--locked` itself. So a claim about "uv-using jobs" is false — `uv export` is a counter-example on both halves — where the claim about `uv run` against the project environment holds. Second, the gate carries `tool_pin="UV_VERSION"` in the runner's registry — uv's version is now a real dependency of this gate's verdict, the same reason the lockfile gate carries it, and `--list` should say so beside both.

### 3. Deliberate scope boundaries
File existence only, not anchor validity (option 2); every `*.md` git considers part of the repo — tracked plus untracked-but-not-ignored — as the source set (option 3, as revised); `specs/personal/` neither crawled nor validated as a target (containment plus CI absence; enforced by the script's explicit filter over both the tracked and untracked-but-not-ignored halves of the source set, not by gitignore). Inline `[text](target)` links are matched, including a standalone image's `![alt](target)` target (a dead local image is a real defect worth catching); reference-style links and an escaped `]` in link text are silently unmatched. **The image-badge nesting `[![alt](img.png)](target.md)` inverted with the balanced-bracket revision above, and this sentence stated the old direction until a review measured it:** the flat `\[[^\]]*\]` captured `img.png` and left the outer `target.md` unmatched; the balanced pattern captures `target.md` and leaves the nested `img.png` unmatched. One of the two is checked either way — which one changed, and the recorded boundary was backwards in both directions until this revision. **Revised 2026-08-23: a target only Windows would resolve is reported loudly on every platform.** Two spellings carried the identical signature to the `c:CLAUDE.md` case the drive-relative guard below was written for and were left open by it — a backslash anywhere in the path, and a path component ending in a dot or space, both of which Win32 normalizes away. Measured on Windows, `adr\0061-markdown-link-check-gate.md` and `adr/0061-markdown-link-check-gate.md.` each resolved with `exists() == True` while naming a file that does not exist on Linux; the docs-consistency job is ubuntu-only, so local is the only place they are ever seen, and the next Windows-authored `specs\foo.md` link would pass every local gate and redden `ci-ok`. They join the *loud* list rather than the skipped one because neither is a valid relative link on the platform that decides the verdict, so reporting them dead is not a false positive. **Revised 2026-08-23 (second pass): that last clause was false for one class, and the rule now asks its question of the rendered destination rather than the written one.** A CommonMark backslash *escape* means the same thing on every platform — `[t](a\_b.md)` renders `<a href="a_b.md">`, measured against markdown-it's own renderer — so the gate reported a valid link dead, and the remedy it printed ("write it with `/`") turns `a\_b.md` into `a/_b.md`, which is genuinely dead. `windows_only_spelling` is therefore asked of the destination with CommonMark's escapes resolved (`unescape_link_destination`), which keeps the justification true: an *escaped backslash* (`a\\b.md`) still renders a real backslash and is still reported, and a backslash before a non-punctuation character (`adr\0061.md`) was never an escape and is likewise still reported. `relative_path_part` was split out of `resolve_target` so the question is asked before `Path` normalization erases the difference it looks for; the escape step sits inside it, **ahead of every other step it performs** — the anchor and scheme tests, the `#`-fragment split, and the root-absolute and drive-relative guards — so all of them, and the existence check after them, see the same rendered path. That placement is itself a correction: the step first sat one line *below* the fragment split, so the split was the one thing still reading raw text, and `[t](foo\#bar.md)` was cut at the raw `\#` and came back as `foo\` — a trailing backslash nothing wrote, which the rule above then reported as a Windows-only spelling. Measured, markdown-it gives that link and its unescaped twin the same href (`foo#bar.md`, not percent-encoded), so the correct path part is `foo` for both. Only the *title* strip stays above the escape step. **That justification was itself wrong on first writing and is recorded corrected**, since it is the third instance on this gate of a claim repaired into another false claim: it said decoding first would let an escaped `\"` "end the title early" under `TITLE_RE`'s flat `[^"]*` run, and measurement showed that pattern matched *neither* spelling of `path.md "a\"b"` — so the order changed nothing and the title went unstripped either way, turning a link markdown-it renders as `href="path.md"` into the unresolvable path `path.md "a"b"`. `TITLE_RE` is now escape-aware in its quoted run, which both removes that false positive and makes the ordering genuinely load-bearing: escape-aware, the pattern captures `path.md` from the raw form and matches nothing once the escape has been resolved to a bare quote. `.`/`..` are excluded explicitly, without which every `./x.md` in the repository would be rejected. **The report also runs behind the `specs/personal/` skip rather than ahead of it** — it was the first error path written past that filter, and a link spelled `personal\<name>.md` printed a personal filename to stdout and into CI's docs-consistency log while its forward-slash sibling was skipped correctly; the skip now asks under both separators, since `Path` reads a backslash as one on Windows and not on Linux, and Linux is the authoritative leg. Corpus impact today is 0. Root-absolute (`/x`), protocol-relative (`//host/x`) and drive-relative (`c:x`) targets are skipped as out-of-scope (GitHub resolves the first two against the repo root, which this gate does not model; the third is a Windows path spelling, left to `DRIVE_RELATIVE_RE` by the two-character minimum in `SCHEME_RE` and likewise absent from this list until the same review). The corpus uses none of these. Source *enumeration* is git truth — `git ls-files` (the 2026-08-08 revision adopted the enhancement this paragraph originally recorded as a candidate, because widening the crawl to the repo root made a filesystem walk unsound: an rglob from the root would sweep `.venv/` and other untracked trees; outside a git checkout, i.e. the unit suite's tmp trees, the script falls back to an rglob with the same personal/ exclusion). Target *existence* is still checked against the working-tree filesystem, which equals the git checkout in CI (the authoritative run); a *local* run may diverge on an untracked linked file or a case-only filesystem mismatch. The full list of parser approximations, including those that fail *loudly* (a target containing an **unescaped** `)`, a space, `<...>`, or a `%20` escape — a backslash-escaped `\)` is read as one character, as CommonMark does, the unqualified form having truncated `[t](foo\(bar\).md)` to the fragment `foo\(bar\` and reported *that* dead; a link split across a line wrap; a link inside a multi-line inline code span the parser did not itself pair, which the 2026-08-22 revision made the loud case deliberately), lives in the `check_spec_links.py` docstring. **"A link inside an HTML comment" was in that loud list until a review measured it, and it is now neither loud nor an approximation:** an HTML block's contents are raw HTML rather than markdown, so such a target is not a link at all — measured against the renderer, `<!-- [a](x.md) -->`, a link after a bare `<br>` line, and a link on the line following `</div>` each render zero `<a>` tags, while the same link one blank line later renders one and is checked. Skipping it silently is the correct verdict here rather than a tolerated gap. **Where the block ends depends on which kind it is, and this sentence said "the next blank line, not the closing tag" without qualification until a second review measured it.** That holds for the type-6 and type-7 blocks the evidence above exercises — every measured case there was a `<div>` or a `<br>` — and is false for CommonMark's **condition 1**: `<pre>`, `<script>`, `<style>` and `<textarea>` run to their closing tag and swallow blank lines. Measured: `<pre>\n[a](x.md)\n\n[b](y.md)\n</pre>\n\n[c](z.md)\n` reports only `z.md`, while the same shape written with `<div>` reports `y.md` too. The masking is correct in both cases; the unqualified claim was wrong in the silent direction, since a reader who believed it would expect a target a blank line inside a `<pre>` fold to be checked, so one that later dies is never reported and the gate stays green. These are recorded so a future widening is a conscious extension, not a silent rediscovery.

## Consequences

### Positive
- A dead cross-file link fails CI at PR time instead of landing inside an immutable ADR; the manual verification PR #38 needed becomes mechanical.
- The gate is self-justifying on its first run: any dead link already in the corpus surfaces immediately (the same way `check_adr_index.py` earned its place by catching two drifts on first run).
- No new required status check and no branch-protection change. (The "no new dependency" this bullet also claimed at inception stopped being true on 2026-08-22 — see §1 and the tradeoff below.)
- One CommonMark model for the repository, in a public function rather than in a private helper. The four hand-rolled parsers that preceded this each drifted silently from the others; the next checker over this corpus now has something to import instead of something to copy.

### Negative / Tradeoffs
- Anchor drift (a `#L123` link surviving a target's line shift) is not caught — accepted; line anchors are not validatable against a moving file.
- Source enumeration now shells out to `git ls-files`, so the script is no longer dependency-free in the strictest sense (subprocess + git); accepted, since every environment that runs it — CI, `/land`, the unit suite's fallback path — already assumes git or avoids it.
- A legitimate file rename still requires updating every referencing link for CI to pass — which is the point, but it is real work the gate now enforces rather than trusts to review.
- **A declared dependency (`markdown-it-py`), and an interpreter the gate now depends on** (2026-08-22). It is in the `dev` group and was already resolving transitively through `typer -> rich`, so adoption added no package to the lock; it is declared anyway so that a `rich` change cannot break the docs gate blaming an unrelated PR. The real cost is the invocation: this gate no longer runs under a bare `python3`, which makes it the first script to need a controlled interpreter and leaves the repository with two invocation styles among its docs gates until the rest follow.
- **The declaration is upper-bounded — `>=3,<5` — and that is a third pinning mechanism in this repository** (2026-08-23, added when a review pointed out that this was the one verdict-determining tool with no ceiling). The tools in `ci.yml`'s `env` block are pinned to exact versions because CI invokes them by version; `markdown-it-py` is a project dependency, so the lockfile plus `--locked` is what holds it — and only until something re-locks. `.github/dependabot.yml`'s grouped `patterns: ["*"]` update is exactly that, and a bump across a major boundary changes which CommonMark revision the tokenizer implements, therefore what counts as code, therefore this gate's verdict — inside a routine dependency PR nobody is reading as a parser change. The bound makes crossing that boundary an explicit edit to `pyproject.toml`. It does **not** make the parser's version visible in `--list`, which still shows only `uv`; [`diff_check_spec_links.py`](../../scripts/diff_check_spec_links.py) diffs *revisions of the checker* rather than versions of its parser, so the committed instrument does not cover this axis either.
- **`scripts/ledger.py` keeps its own fence model, and this change moved the other side of a pair [ADR-0072](0072-review-pipeline-and-ledgers.md) binds together.** Measured at adoption over every markdown file git considers part of the repo: the fence verdict agrees line for line on **130 of 130**, with no disagreement anywhere in the corpus. The models do still differ on shapes the corpus does not contain — a fence indented under a list item, a tab-led fence, and an indented code block are code to this parser and prose to the composer — but that difference is **inert, not merely latent**, and the reason is worth stating because the obvious reading is the wrong one: the same indent that makes those shapes code is what stops `ledger.py`'s `ATX_HEADING_RE` (`{0,3}` spaces, no tab) matching a `#` inside them. Measured — `demote_headings` returns a `# comment` in all three unchanged. The shape that *does* rewrite a heading inside code is an **HTML block**, which this parser masks and the composer does not model at all: `<!--` / `# comment` / `-->` composes to `## comment`. That one is present in the corpus today — 7 lines in [`0000-template.md`](0000-template.md), none of them a heading — so it is live-and-harmless rather than absent, which is a weaker guarantee than the three-shape reading it replaces. Recorded in [open-questions.md](../open-questions.md) with the trigger that would make it bite.
