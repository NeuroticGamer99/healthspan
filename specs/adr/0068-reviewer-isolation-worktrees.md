# ADR-0068: Reviewer Isolation via Stash-Snapshot Worktrees

## Status
Proposed

## Context and Problem Statement
The local review subagents (`spec-reviewer`, `test-reviewer`) review **uncommitted** work — that is their purpose in the session workflow, running between implementation and `/land`. Their agent definitions claimed "Read-only; reports findings, never edits" while granting `Bash`, an unrestricted write channel; the claim was false in practice, and usefully so: `test-reviewer`'s most valuable contribution is **mutation testing** — editing a file to prove a guard clause is genuinely pinned by a test, or that a new test adds detection power rather than just a name.

On 2026-07-27 both reviewers ran in parallel against the live working tree while `test-reviewer` was mid-mutation. `spec-reviewer` read the half-mutated tree and reported a named test, a real assertion error, and a coherent "order-dependent test pollution" diagnosis — entirely fictitious, and four consecutive green runs to disprove. A subtly wrong reviewer finding costs more than no finding, because reviewer output is built to be believed.

The first response was a **restore-in-place protocol**: mutate the live tree, but pin the review scope first, hash before mutating, copy aside outside the repo, restore on every exit path, prove restoration by re-hash, sweep for strays, and serialize the two reviewers at every call site. Across one working session that protocol accumulated **seven hand-follow obligations, every one discovered by a failure** — including an empirical demonstration (by `test-reviewer`, run against its own draft protocol) that a tool-level timeout kills the process before any trap or in-band cleanup fires, so a killed run cannot restore itself. A `max`-effort review then found six more defects in the protocol's mechanics and observed that its entire protection model was *instruction*, enforced by nothing — the same property that had let "Read-only" stand false. It also identified the alternative this ADR adopts.

The blocking assumption was that worktree isolation cannot work here: "a fresh worktree contains only committed state, and these reviewers exist to review uncommitted work." That assumption is **false**, and `specs/testing-strategy.md` carried the same false claim.

## Decision Drivers
- The tree under review is often the **only copy** of the work: a failed restore destroys content that exists nowhere in git. A false finding costs a review round; data loss is a different risk class.
- Mutation testing must be preserved — it is the reviewers' highest-value evidence, not the hazard. The hazard is mutating the *shared* tree.
- Protection should be **mechanism, not instruction**: a protocol only as strong as a Sonnet subagent's perfect compliance with 200 words of sequencing discipline is safety-shaped, not safe.
- Personal-data containment (`CLAUDE.md`): review tooling must not create paths that move `specs/personal/` content, and `specs/open-questions.md` (local agent CLI evaluation) already records the posture that containment should hold **by construction** — "review from a throwaway worktree or clean clone, where the gitignored personal directory simply does not exist" — as a recommendation for adopting changes to confirm.
- Serializing the reviewers (the interim mitigation) costs wall-clock at every call site and had already leaked into four documents with drift between the copies.

## Considered Options
1. Restore-in-place protocol — mutate the live tree under a hash/copy/restore/prove discipline, reviewers serialized
2. Forbid mutation testing entirely — make "read-only" true by fiat
3. **Per-reviewer disposable worktrees materialized from a `git stash create` snapshot of the uncommitted state** (chosen)
4. Claude Code's built-in subagent worktree isolation (`isolation: worktree` frontmatter) — rejected; see below

### Why the built-in isolation cannot serve this purpose under the current workflow
Claude Code ships subagent worktree isolation, and a future reader will reasonably ask why this ADR builds anything. The answer is that it solves the **opposite** problem, and adopting it here would fail *silently*.

Per its documentation as of **2026-07-30** (*Run parallel sessions with worktrees*, *Create custom subagents*; vendor behavior changes without notice, so those docs are authoritative over this paragraph, not the reverse), a subagent worktree branches from the repository's **default branch** (`worktree.baseRef: "fresh"`, the default), or at most from the session's local `HEAD` (`"head"`), and "checks out only tracked files". Every one of those carries **committed** state. This ADR exists because the reviewers' subject is **uncommitted** state — that is their slot in the session workflow, between implementation and `/land`.

The failure is not degraded review, it is a false pass. On the branch that introduced this ADR, `HEAD` *is* `origin/main` and the entire work item lives in the working tree, so a reviewer launched with `isolation: worktree` would review a tree containing **none of the work** under either `baseRef` setting — and report clean. That is precisely the silently-wrong-reviewer class the 2026-07-27 incident opened, arriving through the mechanism that looks like the obvious simplification. **Do not add `isolation: worktree` to `spec-reviewer.md` or `test-reviewer.md`.** The two are not interchangeable and the wrong one cannot be detected from its output.

The adjacent built-in `.worktreeinclude` mechanism is likewise inverted for this purpose: it copies files that are *gitignored*, whereas the untracked copy-in here deliberately excludes gitignored content — that exclusion is what makes `specs/personal/` containment hold by construction (§4).

None of this argues against the built-in for its own purpose: isolating a subagent that **writes**, from a clean base. That is a different job, and the `worktree.baseRef: "head"` setting is the right tool for a writing subagent that needs in-progress commits.

**This rejection is scoped to the commit-after-review workflow and must be revisited if that changes.** The sole disqualifier above is that the built-in reaches only committed state — so the WIP-commit sweep booked in [open-questions.md](../open-questions.md) § Development Workflow would remove it, and option 4 becomes a real candidate for the *materialization* half of this mechanism. What it would still not supply, and what that sweep must weigh rather than assume: the launch manifest the reviewers are prompted from, a teardown that verifies nothing it created is still registered, the per-agent venv redirect, the tracked-`specs/personal/` precondition check (§4), and the exit-code contract that stops a launch failure reading as a sanctioned skip. Until that sweep runs, the prohibition above stands as written.

## Decision Outcome
Chosen: **option 3**. Option 1 was implemented and failed its own review: seven obligations each discovered by a failure, protection by unenforced instruction, and the residual risk landing on the only copy of the work. Option 2 discards the strongest evidence the reviewers produce — on 2026-07-27 mutation testing proved three guard clauses were each killed by a distinct test and caught a test that added a name but no detection power; reading alone finds none of that. Option 3 was verified end-to-end on the development machine (2026-07-28) before adoption.

### 1. The mechanism
The launching session (never the agents) runs **`scripts/review_worktree.py`**. Its `setup` subcommand snapshots the uncommitted tracked state with `git stash create` (aborting on any stash failure rather than falling back to `HEAD` — a mid-merge tree prints garbage to stdout, an intent-to-add entry fails with empty stdout, and either fallback would materialize the wrong state), materializes one detached worktree **per reviewer** from that snapshot in the session scratchpad, replicates the untracked files (`--exclude-standard`, so gitignored content stays out) with **identical bytes into every worktree** from a single read of each live file, and prints the launch manifest: snapshot SHA, base ref, worktree paths, per-reviewer venv paths (exported as `UV_PROJECT_ENVIRONMENT` so reviewer venvs land outside the worktrees), untracked list, and fidelity warnings. Setup **aborts** when the staged index diverges from the worktree — the snapshot reviews worktree bytes while a plain `git commit` (without `-a`) publishes the index, and no advisory warning can make that gap safe. Its `teardown` subcommand removes every worktree and venv dir it recorded — acting on the repo root the state file records, not the invocation cwd — has each recorded path de-register itself rather than running a repo-global `git worktree prune` (which takes no path filter and would de-register unrelated worktrees), and fails loudly if anything remains. The reviewers launch **in parallel**, each told its worktree path, the SHA, **the base ref**, its venv path, and the untracked list, and each reports the SHA as the identity of the state it reviewed.

Inside a worktree the snapshot commit is `HEAD`, so `git diff origin/main...HEAD` *is* the tracked diff under review — the scope is pinned by construction and cannot be contaminated by any agent's edits, including the agent's own.

**Defaults and the exit-code contract** (recorded here per CLAUDE.md decision-capture rule 4, which routes config knobs and defaults to the owning ADR):

| Knob | Default | Why it is a decision |
| --- | --- | --- |
| `--base` | `origin/main` | Decides both the "nothing to review" verdict and the diff scope the reviewers are told; a session reviewing against anything else must pass it, and the reviewers silently fall back to this same value when a prompt omits it. |
| `--agents` | `spec-reviewer,test-reviewer` | One worktree and one venv per name; the names become path components, so they are validated (letters, digits, `_`, `-`) and duplicate-checked case-insensitively. |
| state file | `<scratch>/review-worktrees.json` | The only durable record of what setup created. The recovery procedure in `.claude/reviewer-isolation.md` tells an operator to delete it, so the name has to be findable once the setup manifest has scrolled out of a transcript. |
| state-file `nonce` | `secrets.token_hex(8)`, written at setup | Identifies which round wrote the file, so teardown can tell "gone" from "a different round's" before unlinking. Without it `unlink(missing_ok=True)` cannot distinguish the two, and the launch procedure makes two teardowns on one scratch dir ordinary by instructing a teardown on every exit path — so a slow teardown could delete a *later* round's record and orphan its worktrees silently (§4). |
| pipe-drain grace | 5s, shared across both streams | How long the output readers get once nothing should still be writing. Spent against one deadline rather than per stream — per-stream multiplies by the stream count, measured at 10.2s for the two here — which is what bounds a whole call at `timeout + 2 × grace`. A knob because it trades how long a straggler delays a round against how much output a slow but healthy git may still be flushing. |
| reviewer keychain backend | `keyring.backends.fail.Keyring` | Setup prints it per agent as an `env[<agent>]:` line for the reviewer to export. Must equal the value `tests/conftest.py` assigns: the two are one belt, and this is the copy that lives *outside* the tree test-reviewer is chartered to mutate (§3). A knob rather than an implementation detail because the two copies drifting apart is silent — the in-tree one would still pass every test. |
| warning list cap | 20 paths, then `+N more` | Bounds the multi-path warnings that go through the capping helper. It does **not** bound every message that names a path, and reading it that way is how a new unbounded one gets added: the stray list in `_cleanup_worktrees` and the per-file aborts in `_copy_untracked` name paths without it. Those are bounded by other means today (one path each; at most one stray per agent), which is why the over-broad claim survived a round. |
| minimum Python | 3.12 | `shutil.rmtree(onexc=)` and `Path.is_junction` are both 3.12+, and both are on the *delete* paths — so an older interpreter runs `setup` normally and dies inside `teardown` by an exception no `except` clause owns, leaving both worktrees registered and every later setup refused. This is **not** `pyproject.toml`'s `requires-python`, which constrains `uv`: `.claude/reviewer-isolation.md` launches this script with a bare `python`, commonly a Store shim or system interpreter on Windows. A real constraint on every future edit to the file, learnable nowhere but the source until now. |
| git command timeout | 120s | Matches `COMMAND_TIMEOUT` in `scripts/bot_review.py`. A hung git child — a post-checkout hook, fsmonitor — must not block a setup forever; the abort names the subcommand that hung so the operator can act on it. |

Exit codes: **0** ready (setup) or clean (teardown); **2** nothing to review, setup only; **1** abort, usage error, or verification failure. Exit 2 is the load-bearing one — it is the only code that sanctions skipping the reviewers, so argparse's own usage-error 2 is remapped to 1, and a caller treats an exit 2 without a `nothing to review:` line on stdout as a launch failure rather than a sanctioned skip.

**Exit 2 requires that "nothing" be *establishable*, not merely that the three positive checks came back empty.** A tree the launcher holds positive evidence the snapshot is blind to, or whose only content was filtered out of review, aborts instead. Three conditions promote: a `skip-worktree` / `assume-unchanged` entry (its modifications are invisible to `git stash create` by the very definition of the flag, and for `--assume-unchanged` the hidden edit can still land, because an explicitly named `git add <path>` stages it); an untracked-symlink-only change; and untracked content that all resolves out of the tree. The first was added in the seventh pass — the gate consulted the other two and not it, so the only code that sanctions skipping the reviewers was reachable on evidence that the tree was not clean. Consequence for callers: the machine-local-ignore warning is now the only fidelity warning that can accompany a genuine exit 2, which `.claude/reviewer-isolation.md`'s exit-2 triage states.

The script is the governing implementation, pinned by `tests/test_review_worktree.py`; `.claude/reviewer-isolation.md` is the operational procedure around it (invariants, fallback, fidelity summary), and the skills cite that file rather than restating it. Mechanization is itself a decision this ADR records: the first, hand-run version of the procedure accumulated five silent failure modes before its first commit — a "nothing to review" guard that did not stop, a teardown scoped to a dead loop variable, unchecked `git worktree add` and `git stash create`, and cwd-sensitive pipelines — the class of silently-failing glue this repo already routes to tested scripts (`scripts/bot_review.py`, `scripts/check_adr_index.py`).

The launch invariant: **launching a review may read anything, and may write outside the repo plus two named places inside it** — git's own worktree administration under `.git/worktrees/`, which `git worktree add` necessarily creates and teardown removes one recorded path at a time; and the commit, tree and blob objects `git stash create` writes into `.git/objects`, which teardown deliberately does not clean because they become unreachable when the worktrees go and a later `gc` collects them. No file in the working tree is written and **nothing the index stages is changed** — the content wording is deliberate, since read-only git commands refresh the index's stat cache in place and so rewrite `.git/index` on every setup without altering a staged byte. That content distinction is what disqualifies both alternatives for the untracked-file gap, in favor of copy-in: `git stash push -u` removes untracked files from the live tree, where a failed pop is data loss, and `git add -N` stages a new entry — changing what a plain `git commit` would publish, which the stat-cache refresh never does. When setup fails, the defined fallback is sequential, read-only, **disclosed** live-tree review (`.claude/reviewer-isolation.md` § Launch) — never improvised parallelism.

### 2. Division of the mutation charter
- **`test-reviewer` keeps mutation testing**, exercised freely inside its private worktree with no restore obligation — the worktree is disposable. It must prove a mutation *landed* before trusting any suite result — a no-match `sed` exits 0, observed during verification; the operational procedure for that proof lives in `test-reviewer.md` § Mutation testing, not here.
- **`spec-reviewer` returns to read-only.** Its five checks are documentary; mutation evidence has no slot in its report format. Where enforcement (vs. documentation) of an invariant is in question, it reports the question rather than running the experiment.

### 3. The boundary isolation does not move
The worktree isolates the **tree, not the machine** — a mutated suite run still shares the OS, and the machine holds a real encrypted health database. The operational out-of-bounds rules live in `test-reviewer.md` § Mutation testing, in the agent definition because no tree-level mechanism can reach them; the decision here is that they exist and where they live. Two layers do back them up: `tests/conftest.py` **assigns** `PYTHON_KEYRING_BACKEND=keyring.backends.fail.Keyring` at import time for every suite run (a mechanism, though one living in the mutable tree), and the reviewer additionally exports the same variable per invocation from outside the tree — verified in this project's environment to raise `NoKeyringError` on any path reaching a real backend, so even a damaged isolation fixture cannot touch the OS credential store. The assignment is unconditional rather than a `setdefault`: keyring's `load_env()` reads the variable at backend-resolution time and consults it first, so an inherited value naming a real backend — another tool's, an old shell profile's — would silently win and put the OS store back in reach on the machine that holds the real database. No legitimate suite run against a real backend exists to protect — `specs/testing-strategy.md` § Cross-Platform Testing, the section that owns keychain policy, requires the mocked backend on every platform and names an explicit `keyring.set_keyring(<real backend>)` call as the only sanctioned way past the belt — not `set_keyring` as such, which is how the autouse fixture installs the in-memory fake on every test. That section is corrected in this same change: it previously read "must run on each platform **or** mock", which this assignment makes impossible; it described the suite as calling `set_keyring` nowhere when the autouse fixture calls it twice per test; and both this paragraph and `conftest.py`'s comment cited § Parallel execution instead — a section about xdist worker-collision safety, two headings below the one that decides the question. Because `set_keyring()` assigns the backend directly, this variable is consulted once per process, so the belt covers the pre-fixture window and every spawned subprocess rather than the inside of a test body. The rationale is unchanged; the citation now points at a sentence that supports it. The reviewer's out-of-tree export sets the same value, so its role — surviving a conftest a mutation broke — is unaffected.

The belt's guarantee is also **positional**, which the first version of this section did not say: `keyring.core.init_backend()` resolves lazily on the first `get_keyring()`, so the assignment decides the backend only while nothing imported above it in `conftest.py` has already resolved one, and it is not the file's first statement. `tests/test_keychain_isolation.py` pins the property that makes the position irrelevant — that nothing resolves a backend during conftest's import at all — because the two probes that assert the final value and the final effect stay green with the assignment moved anywhere in the file.

### 4. Verification record (2026-07-28, development machine)
- Snapshot of a 5-file uncommitted change: tree and stash reflog untouched; materialized worktree **byte-identical** to the live files (`cmp`). Scope of that claim: identity is **content modulo git's configured EOL normalization** — with `core.autocrlf`/`.gitattributes eol` active, a file that is CRLF on disk materializes normalized, so a raw byte assertion can differ while every `git diff` text agrees (the live files in the verification run were already LF).
- `specs/personal/` absent from the worktree — gitignored content never enters the snapshot or the untracked copy-in. **Precondition:** this holds only while nothing under `specs/personal/` is *tracked* (gitignore does not affect tracked files); the launcher asserts that precondition and refuses to snapshot when it fails.
- `uv run` inside the worktree built a private venv in single-digit seconds (3–6 s across runs) and resolved `import healthspan` to the **worktree's** `src/` (the editable-install objection dissolves).
- A real mutation in the worktree failed 7 tests **there** while the live tree stayed clean throughout; teardown left no residue.
- The launcher's mechanics — clean-tree early exit, tracked and untracked snapshot fidelity, identical replication across worktrees, the `specs/personal/` guard, abort on unmergeable index, cwd independence, teardown completeness — are pinned by `tests/test_review_worktree.py` rather than re-verified by hand. A mutation-testing pass by `test-reviewer` (run under this ADR's own charter) proved the first test batch could not detect removal of the stash-abort guard or the teardown stray check, driving four additions: the two abort scenarios that fail for different reasons (a merge conflict makes stash emit garbage a later git call chokes on; an intent-to-add entry makes stash fail with *empty* stdout, which only an exit-status check catches), the teardown stray-registration failure path, and the skip-worktree warning. Writing the stray test then exposed that the stray check was not merely untested but **vacuous on Windows** — it substring-compared OS-native paths against git's forward-slash porcelain output, so it could never fire on this platform (fixed by resolved-`Path` comparison); and first live use exposed `git worktree remove` failing on Windows MAX_PATH once a worktree contains a venv — i.e., on every reviewer round.

That MAX_PATH failure was first worked around (an extended-length-path delete fallback, plus the manifest's per-reviewer venv redirect to keep venvs out of the worktrees) before its root cause was tested. A later review asked whether `core.longpaths` had ever been tried; it had not. **Measured on this machine (2026-07-30, git 2.45.1.windows.1, with the OS's own long-path support already enabled):** `git worktree remove --force` on a worktree holding a 400-character path fails `Filename too long` (exit 255, tree left on disk) without `-c core.longpaths=true` and succeeds cleanly with it, read-only leaf files included — and `git worktree add` fails the same way at **265** characters, which is the call that actually *writes* the deepest paths, so scoping the flag to removal is exactly how the add went uncovered. The flag is accepted and inert on POSIX git (2.53.0). This paragraph is the single copy of the measurement; the script and its tests cite it rather than restating it. The launcher now passes it, which returns git to being the single owner of both the deletion and the registration and closes the split-brain window (tree deleted, registration still live until prune) that existed only because deletion had been taken away from git. The hand-rolled delete stack is kept as a genuine backstop — it is required regardless for the reviewer **venv** directories, which are not worktrees and which git therefore cannot remove.

That paragraph originally went on to re-found the venv redirect on a *different* reason — that a venv inside a worktree "materializes thousands of untracked files in the tree under review", noise in the reconciliation each reviewer runs — and stated "that reason, not MAX_PATH, is now what the redirect is documented as being for". **Both halves of that replacement were measured false** (2026-08-01, same machine) and it had already been copied into four other documents:

- A venv inside a worktree produces **zero** `??` entries. `uv` writes a `.gitignore` containing `*` into every environment it creates, and `.venv/` is ignored by this repo's own tracked `.gitignore` — which materializes in every worktree. `git status --porcelain --untracked-files=all`, the exact command the reviewers are told to run, reports nothing.
- `git worktree remove --force` deletes a worktree containing an ignored venv in **one** pass, exit 0, read-only leaf files included — so the redirect is not what makes deletion possible either.

The redirect stands on the reason it started with, correctly scoped: **MAX_PATH headroom for `uv`**. `-c core.longpaths=true` buys long-path support for *git* only; `uv` has no equivalent switch, and a worktree path already ~135 characters deep plus `.venv/Lib/site-packages/…` is how a build lands past MAX_PATH on a host without the OS-wide flag. The scratch-level `venv-<agent>` name is ~20 characters shorter and, sitting outside the worktree, cannot grow with it. The cost the redirect does *not* avoid is the per-worktree build — one venv per agent either way. Dropping the redirect entirely — letting each venv live at `<worktree>/.venv` — is a live option that this measurement makes viable and that is **not** taken here; it is a change of shape, not a correction, and belongs with the WIP-commit sweep that already has to re-slice this module.

What that would actually retire is smaller than first recorded, and the error ran in the direction that preserves the machinery, so it is corrected here rather than left to be inherited. The claim was that it would also retire `_force_delete_tree`, `_extended_length`, `_remove_plain_dir` and the `venvs` state key. **`_force_delete_tree` and `_extended_length`/`_os_path` do not retire**: `_force_delete_tree` is the fallback deleter `_remove_worktree` reaches for when git cannot remove a worktree, and `_os_path` is what makes `_copy_untracked` survive a past-MAX_PATH untracked path — neither has anything to do with venvs. What retires is `_remove_plain_dir` (~50 lines), the `venvs` state key, `_recorded_paths`'s `required=False` branch, a few manifest lines, and the teardown tests that cover them. The surviving benefit — MAX_PATH headroom for `uv` — is also cheaper to buy than assumed: the 33-character `wt-<agent>-<sha9>-<hex6>` component carries a SHA already recorded in both the state file and the manifest, so shortening the name recovers most of the same headroom for nothing. Two of the redirect's three original rationales were already measured false; a retirement list that overstates removal cost is how a mechanism outlives every reason it was built for. This reprices the decision; it does not reverse it.

Two external review passes hardened the mechanism further. The first: the outside-scratch refusal validated **before** git runs (a registered worktree would otherwise be force-removable wherever it lives), the scratch dir itself rejected as a recorded path, teardown acting on the state file's recorded repo root instead of the invocation cwd, and usage errors exiting 1 so a typo'd flag can never impersonate the "nothing to review" exit 2. The second: the fallback deleter's retry narrowed to the callbacks that actually delete (`shutil.rmtree` reports whichever function raised, so retrying `os.scandir` deleted nothing while swallowing the failure the caller's error was supposed to name, and retrying the POSIX walker's `os.open`/`os.close` raised an uncaught `TypeError`); the launch manifest's scope line composed from what is genuinely in scope, since a tree whose only change is new files was being described as "reviewing branch diff only" while the untracked files were listed directly beneath it; the reviewers' reconciliation command given `--untracked-files=all`, without which git collapses a wholly-untracked directory to one entry while the manifest lists it per-file, manufacturing a discrepancy on a perfectly replicated snapshot; and the agent-name duplicate check case-folded, since case variants share one venv directory on Windows and macOS. Each of those is pinned by its own test — except the reconciliation command's two flags (`--untracked-files=all` and `-c core.quotePath=false`), which live only in the reviewer prompts and have no code path a test could reach.

A third pass, briefed to hunt prose that claims more than the code delivers, returned fifteen findings and is the reason several claims above now read narrower. The material ones: `_cleanup_worktrees` ran a repo-global `git worktree prune`, which takes no path filter and so de-registered **any** worktree whose directory was momentarily missing — reproduced end-to-end against an unrelated worktree left needing `git worktree repair`, a write on someone else's work that invariant 2 never sanctioned (each path now de-registers itself, and `git worktree remove --force` on an already-deleted directory was measured to do exactly that). The venv-side containment guard — the only thing between a tampered state file and a force-delete of the repository — had **no test at all**; disabling it left the whole suite green. `personal_tracked` proved only that `specs/personal/` was untracked, while containment-by-construction also requires it stay *ignored*, so a deleted `.gitignore` rule would have replicated it into both agent-readable worktrees; the manifest is now checked directly. The machine-local-ignore warning redacted filenames but printed their parent directories, which for a provider-named directory is precisely the provenance CLAUDE.md protects. `core.longpaths` was on `worktree remove` but not `worktree add` — the call that writes the deepest paths — so every git invocation now carries it from one builder. Path lists were parsed with `str.splitlines()` against raw `--porcelain` output, which silently zeroed the fail-loud stray check. And the keychain probe overwrote the reviewer's out-of-tree export with a *real* backend name, so a broken belt made it read this machine's live credential vault — measured returning a value before any assertion ran; the hostile value is now an unresolvable module, which fails loudly and touches nothing.

A fourth pass, run at `max` effort across eleven independent angles, returned the largest yield of any round and is the reason the corrections above exist. The data-loss-class findings: `teardown` applied **neither** of the two scratch-vs-repo overlap guards `setup` enforces, and it is the half that deletes — with a scratch dir naming an ancestor of the repository, every path inside the repo satisfies the containment predicate, so a recorded venv path of the repo root was force-deleted while teardown printed success (reproduced; both guards now live in one helper both subcommands call). The tracked-`specs/personal/` guard matched with a **case-sensitive** git pathspec while its untracked twin was case-folded, so a force-added `Specs/Personal/labs.md` was invisible to it and would have been checked out into both agent-readable worktrees — the load-bearing precondition of §4's containment claim, defeated by casing alone (reproduced; now `:(icase)`). And the same abort **printed the filenames** it found, contradicting the count-only redaction its two sibling guards apply for exactly the provenance reason CLAUDE.md names.

The correctness findings: a staged deletion of a file still on disk escaped the divergence abort entirely (`git rm --cached` drops the path from the index, so it stops appearing in `git diff` and reappears as untracked — reviewers then see a file the commit is about to delete); `git worktree remove` on a **missing** directory string-matches its own forward-slashed registry rather than canonicalizing, so the OS-native spelling fails `is not a working tree` and the de-registration retry worked only while a parent directory happened to survive (measured; git is now handed back its own spelling); the outside-scratch tolerance required *gone AND unregistered*, which the renamed-scratch case it cited as its own justification can never satisfy, wedging teardown on every retry with the state file undeletable; `Path.resolve()` made the venv deleter's symlink branch unreachable and aimed the delete at a link's **target**; `_run`'s timeout message sliced the built argv and so never named the subcommand that hung; agent names admitted a trailing `.`, which Win32 strips, collapsing two names into one venv directory — the very race the case-fold check exists to prevent; `nonstandard_index_flags` and `personal_tracked` still parsed path lists with `str.splitlines()`, which this ADR had already recorded as closed; the long-path hardening covered git but not the `copy2` immediately after it; and `teardown`'s cleanup call was unguarded where `setup`'s identical one is.

Three claims in this ADR were themselves wrong and are corrected above rather than defended: the launch invariant said "nothing in the working tree or the index" while every setup rewrites `.git/index` through a read-only stat-cache refresh (narrowed to index *content*, which is what actually disqualifies `git add -N`); the exit-1 triage in `.claude/reviewer-isolation.md` called its two cause lists exhaustive when at least five reachable aborts were in neither; and the venv-redirect rationale recorded above was false in both of its halves.

The local reviewer pair then caught a defect in the fourth pass's own fixes, which is the pattern every round on this branch has repeated: the new tolerance for an untracked file that vanishes mid-copy also swallowed the **non-UTF-8 filename** case, because the manifest decodes such a name with `errors="replace"` and the resulting string matches nothing on disk either. A deliberate hard abort silently became an advisory warning, and only on POSIX — the Windows leg skips those tests, so a Windows-only run reported green. The two are now discriminated explicitly (an undecodable name is deterministic and aborts; a vanished file is transient and warns), and the `surrogateescape` override that keeps stray detection working across the same decode boundary gained the test it never had.

A fifth pass, again at `max` effort across ten angles, found the containment claim §4 opens with was defeated on the primary platform in two independent ways, both reproduced end to end. **A directory junction** anywhere in the tree replicated content from *outside the repository* into both agent-readable worktrees with **no warning emitted at all**: Windows git walks straight through a junction and reports the files beneath it as ordinary untracked paths, while `is_symlink()` answers False for the junction and the leaf alike — so every guard here written against symlinks was open on the link form that needs no privilege to create (`mklink /J`), which is to say the one a Windows user can produce by accident. The same blind spot ran through teardown: a junction recorded as a venv path had its **target** force-deleted from outside the scratch dir while teardown printed success, exited 0 and unlinked the state file, and `_force_delete_tree`'s own last-line refusal — the backstop for exactly that — shared the defect, so the property this ADR describes as proven in three helpers was proven in none. Detection is now a resolved-path containment test rather than a leaf-level link check, because the junction is an *ancestor* component of everything git reports beneath it and no leaf-level test can see it. Separately, **`.gitignore`'s `specs/personal/` rule is directory-only**, so a plain file at exactly `specs/personal` is not ignored, and neither guard caught it: the untracked one tested a `specs/personal/` prefix, and the tracked one passed git a `:(icase)specs/personal/` pathspec — measured, both miss the bare path, and setup exited 0 having copied it into both worktrees. Both now match the bare path as well as the prefix. Three more of that round's findings are recorded where they belong rather than here: the divergence abort was the fourth guard printing filenames that `git rm --cached specs/personal/<file>` routes a personal path into (now a count, as its three siblings already were); teardown treated a **renamed scratch dir** as "nothing left on disk to protect" when the trees had merely moved, leaking two full copies of the repository — uncommitted work and mutation edits included — while printing success; and the exit-2 gate ran *before* the vanished-file filter, so an untracked-only round whose files all vanished mid-copy printed `snapshot: HEAD (reviewing )` and returned **0**, launching both reviewers against worktrees identical to the base for a guaranteed false pass, which is strictly worse than the skip exit 2 sanctions.

The local pair caught this round's fixes leaking in turn, which is now the branch's most reliable pattern: the copy-time containment abort added to backstop the junction filter **named the offending path**, and its leaf components come from the far side of the link — outside the repository. It runs only when the setup-time filter has been bypassed, so no test reached it and the redaction discipline every sibling guard follows had simply not been applied there. The Windows leg also read green on two new tests that assert a Windows-only mechanism, because git reports a POSIX symlinked directory as a single entry rather than walking through it; the tests now assert the shared invariant on both legs and the mechanism per platform.

A sixth pass, again at `max` effort, found the containment claim defeated a third and fourth way, and both are the *same* one-line gap read from opposite platforms: a link **inside** the repository pointing at `specs/personal/`. Every guard here was built to catch a link *leaving* the tree, and one landing in the protected directory resolves to a path still inside the repo, so the escape filter answers False while the prefix tests see only the innocuous name the link wears. On **Windows** a directory junction (`mklink /J`, no privilege) makes git report `notes/labs.md` as ordinary untracked content — reproduced end to end: setup exited **0**, printed it in the manifest as in-scope, and put the file in both agent-readable worktrees. `git add notes` on the same junction stages `notes/labs.md` as an ordinary *tracked* path that `personal_tracked`'s pathspec cannot match, and `git worktree add` then checks it out from the snapshot with no copy step to intercept — a route the untracked guard cannot reach at all. On **POSIX** the link is instead recorded as a symlink entry (mode `120000`) and recreated faithfully in every worktree; with an absolute target it points at the **live** repository's `specs/personal/`, and the real data is readable straight through it from inside the worktree (measured under WSL). Detection is now one predicate applied to two listings — the unique directory components of every tracked and untracked path, plus every tracked entry git records as a symlink — because the junction is an ancestor component that never appears under its own name, while the POSIX symlink *is* the leaf and has no component to inspect. A *relative* symlink target is harmless: it points inside the worktree, where the gitignored directory was never checked out, and resolving is what distinguishes the two rather than a rule about link targets.

A seventh pass, again at `max` effort and again across eleven angle sets, held the pattern a fourth consecutive time: every reproduced top-tier defect sat inside the *previous* pass's fixes. Four are worth recording because each disproves something the code or its prose asserted.

**The command timeout did not bound wall-clock, and the failure is platform-split in a way the finding that raised it did not describe.** `subprocess.run(timeout=)` reads its pipes to EOF, and EOF does not arrive until every holder of the write ends closes them — git's descendants inherit those handles, so a post-checkout hook that backgrounds an indexer or an fsmonitor daemon keeps the call blocked after git itself has gone. Measured against a 60s straggler at `timeout=3`, both legs: **Windows 60.2s, unbounded**, because `run`'s timeout handler kills the direct child and then calls `communicate()` a second time with no deadline; **POSIX 3.0s, bounded but wrong**, because that branch only waits — a git call that exited 0 comes back as `TimeoutExpired` and aborts a healthy round. So the hang is Windows-only and the wrong answer is on both. The replacement spawns through one site that owns a killable container for the whole tree (a session on POSIX, a job object on Windows), drains the pipes on daemon threads so no inherited handle blocks the waiter, and kills a straggler on the **success** path too, where the timeout never fires because the process being waited on is already gone. The Windows container has two limits that POSIX's does not, both measured rather than assumed; they are permanent rather than pending, so they are booked under Consequences and named here only as what the measurement found.

**Two personal-data guards and the divergence abort were blind to any path git emits in raw bytes.** `_git_z` decodes with `errors="replace"` by default, mapping every undecodable byte to U+FFFD — a string that names nothing on disk. `os.scandir` uses surrogateescape (PEP 383), so `b"a\xffb"` is `"a�b"` on the git side and `"a\udcffb"` on the scandir side and the two can never compare equal. Three consequences, measured on the POSIX legs: `_exists_cased` answered False for every component after the bad byte, so a staged deletion of a still-present file shipped unreviewed; and `_leaks_personal` and `_linked_dirs`, which build filesystem paths from those strings, answered False for a **tracked symlink into `specs/personal/` whose own name is not valid UTF-8** — it passed every guard and was checked out into both worktrees. The queries whose results become paths now override the decode, as `_registered_paths` already did for the same reason. The containment half was caught downstream by the artifact walk even with the guards blind, which is the argument for the walk rather than a reason to leave them blind: the walk refuses the round, a working guard names the cause. The divergence half had no backstop at all.

**Teardown could delete a state file it never read.** `unlink(missing_ok=True)` cannot distinguish "gone" from "a different round's", and the launch procedure makes two teardowns on one scratch dir ordinary by instructing a teardown on every exit path. Sequence: T1 finishes and unlinks; a new setup finds no state file, proceeds, and materializes two worktrees; T2 — still inside a several-hundred-MB venv delete, tens of seconds — finishes clean and unlinks the **new** round's file, leaving its worktrees on disk and registered with no record anywhere. The state file now carries a nonce and teardown re-reads before unlinking. The same pass took the reverse hazard: `_deregister_missing`'s safety argument ("there is nothing on disk left to destroy") accounted for the tree and not for the **registration**, which is what that call actually destroys — the repo-global write invariant 2 does not sanction, and the reason `git worktree prune` was removed. It now refuses a registered path that is both outside the scratch dir and not carrying a launcher-generated name, the one property that survives a scratch-dir rename.

**Exit 2 could be earned on a tree the launcher knew the snapshot was blind to.** `nonstandard_index_flags` exists precisely because skip-worktree and assume-unchanged modifications are invisible to `git stash create`, and the "nothing to review" gate never consulted it — so the only exit code that sanctions skipping the reviewers was reachable on positive evidence of hidden changes. Its two neighbours in the same gate had already been promoted from exit 2 to hard aborts on the reasoning "everything reviewable was filtered out, not absent"; this is that shape with tracked source rather than a symlink behind it, and the test asserting exit 2 for exactly this tree was pinning the false pass.

This section names private functions and internal shapes because it is a **verification record** — what was measured, what the measurement disproved, and what each round's own fixes then broke — not an index of the implementation. It describes the code as it stood when each finding was made; the governing description of what exists is the module and its tests. Neither a later refactor that renames or removes any of these, nor a later defect found and fixed after a paragraph was written, falsifies this record or owes it an edit — though a correction that disproves a *claim made here* is added, as the venv-rationale and launch-invariant entries above were.

## Consequences
- **Positive:** the live tree is never touched by review, eliminating the restore-failure and cross-reader-contamination classes outright; parallel reviewer invocation is safe (the serialization discipline adopted in-session after the incident is not carried into the repo — every call site instead cites the parallel-safe launch procedure); the review scope is pinned by construction; containment holds by construction under the tracked-personal-files precondition the launcher asserts, confirming the `specs/open-questions.md` posture for the first-party case; `spec-reviewer`'s `description` returns to read-only — a claim still carried by charter and prose rather than tool grant (`Bash` remains granted), with isolation bounding what a violation could reach.
- **Negative / accepted:** a few seconds of venv build plus worktree add/remove per reviewer per round; teardown is the launcher's obligation, and a skipped teardown leaves a stale copy of the repo plus prunable registrations under `.git/worktrees/` — which is why the teardown subcommand verifies removal and exits nonzero on strays rather than shrugging; untracked-file fidelity depends on the copy-in step, so a launcher that skips the script reviews a state missing never-`git add`-ed files — the manifest's untracked list is the audit trail, and the agents are instructed to reconcile it against the worktree's actual `??` entries.
- **Closed in the seventh pass — a hard link into `specs/personal/` (recorded above as an accepted gap):** a hard link defeats both kinds of guard §4 records, for two different reasons. `mklink /H`, or POSIX `ln`, gives one file a second name that git reports like any other content, so the **name-matching** guards (`personal_tracked`'s pathspec, `_is_personal`'s case-folded prefix test) see an alias outside `specs/personal/` and a `specs/personal/` rule does not match it; and the **resolving** guard added for links (`_leaks_personal`, over `_linked_dirs` and `tracked_entries`) has nothing to resolve, because a hard link is not a link to anything — it is a second directory entry for the same inode. **`.gitignore` is not the fallback either**, and claiming it were would invert §4's whole finding — an ignore rule is a name-matching guard like the two above, which is exactly why a junction was measured being replicated with setup exiting 0. The gap was accepted on likelihood rather than severity, on the stated cost of "a file-identity comparison against a walk of the owner's real data directory on every setup". That cost was re-examined and taken: `specs/personal/` is small, so one `os.walk` yields the `(st_dev, st_ino)` set and every manifest entry is compared against it. It was not merely theoretical — measured, the content of a hard link into `specs/personal/` landed in **both** worktrees with setup exiting 0. The comparison runs on the **source** side deliberately: `copy2` and `git checkout` each write a fresh file, so the copy shares the content and not the identity, and an artifact-side identity check answers False on the very case it would be written for (also measured).
- **Accepted gap — the Windows process-tree kill is best-effort, and the launcher fails closed when it misses.** The spawn puts each git child in a container so a hook's backgrounded daemon cannot hold the output pipes open (§4). On POSIX that container is a session, established before the child runs and outliving it, so it always holds. On Windows it is a job object assigned after `CreateProcess` returns, which leaves two windows nothing can close from Python: `AssignProcessToJobObject` refuses a process that has **already exited**, and a parent that is itself inside a job may not be able to nest one (an xdist worker, measured). A short git command that leaves a straggler is therefore unkillable on that platform. The consequence is bounded deliberately: the spawn **aborts rather than return a partial read**, because a truncated path list is indistinguishable from a genuinely short one and `personal_tracked` reading `[]` means "nothing personal is tracked, proceed". Closing the gap properly needs the child spawned suspended, which `subprocess.Popen` forecloses by closing the thread handle before returning; the cost of a private `CreateProcess` wrapper is not worth a failure mode that already fails safe.
- **Scoped by a workflow choice, not a constraint (recorded debt):** the uncommitted-state machinery — the stash snapshot, the untracked copy-in, the divergence abort, the fidelity warnings — exists because this workflow commits *after* review. Against WIP commits none of it is load-bearing, and the "only copy of the work" driver above disappears entirely; the isolation itself still is, since invariant 1 and the mutation sandbox are indifferent to commit state. Booked as a sweep across the tooling, agents, and skills in [open-questions.md](../open-questions.md) § Development Workflow rather than reopened here.
- **Unenforced (recorded debt):** the script is tested, but nothing mechanically verifies that a session *uses* it — launch-procedure compliance is still a stated contract with no gate, the class the repo-invariants register (queued in [open-questions.md](../open-questions.md) § Development Workflow) exists to catalogue; this ADR becomes rows there when the register lands.
