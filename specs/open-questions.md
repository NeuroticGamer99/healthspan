**Exclusive vs inclusive range bounds ([ADR-0005](adr/0005-reference-range-frameworks.md), [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §3/§5)**
`framework_ranges` bounds are **inclusive** on both ends ([ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §3: `T = [L, H]`), but real clinical cutoffs are frequently **exclusive**: MedlinePlus desirable cholesterol is *"less than 200"* (200 is borderline-high, not desirable), ADA prediabetes *begins at* A1C 5.7 and FPG 100, AHA/CDC low-risk hs-CRP is *"<1.0"*. The current seed works around the mismatch two different ways, and the inconsistency is real (CodeRabbit, PR #28): continuous measures store the threshold itself (200/100/150/1.0), which is the best inclusive approximation of "< threshold" but classifies the exact threshold value as `in_range`; glucose/A1c store threshold-minus-a-unit (99/5.6), correct for their reporting granularity but wrong for a fractional value in the gap. **Subtracting a display unit is explicitly not the fix** — it buries an unstated precision assumption in the data and breaks for any lab reporting finer precision.

**Owner's design steer (2026-07-17), to drive the range-model PR:** the comparison engine should use **standard mathematical interval notation with per-bound closure** — `(1, 10]` is not `[1, 10]` — rather than assuming both ends inclusive. And the inclusive/exclusive choice per bound should be a **user-verified layer**, not silently baked into a magnitude: the stored range carries its own closure (a per-bound open/closed flag, or a comparator per bound), the owner confirms it, and cited sources inform which end is open. This composes with — and is a strict generalization of — [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §3's existing open/closed handling on the *result* interval (a censored `<0.5` is already `(-inf, 0.5)`); today only the *target* interval is forced closed. Mechanism candidates: `range_low_closed`/`range_high_closed` boolean columns (default true = today's behaviour, so additive and back-compatible), or a comparator per bound mirroring the ADR-0030 result-value comparator domain. This is the same **range-model-expressiveness** theme as the cohort-dimension and `physical_min` entries below/above and should very likely land in one range-model PR with them; the comparison core (`ranges.py`) already has the open/closed interval machinery, so most of the change is schema + seed + the resolution read. Trigger: the range-model PR, or the first time a value landing exactly on a stored threshold is flagged visibly wrong to the owner.

**Reference ranges that depend on more than the biomarker — sex, age, fasting state ([ADR-0005](adr/0005-reference-range-frameworks.md), [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §5)**
`framework_ranges` is keyed by `(framework_id, biomarker_id, effective_date)`. It can therefore hold **one target per biomarker per framework per date** — and real reference data routinely needs several, differing along dimensions the table cannot express. Three concrete instances surfaced in Phase 3 WI-3, all in a seed of only six rows (seven counting the HDL range left unseeded over exactly this gap):

- **Sex.** NIH MedlinePlus states HDL's low cutoff as `< 40 mg/dL` (men) and `< 50 mg/dL` (women). Not representable; picking one silently is not acceptable.
- **Age.** The same source states different lipid targets for age ≤ 19 (TC < 170, LDL < 110) than for 20+ (TC < 200, LDL < 100). The adult values are seeded — correct for this platform's single adult owner, but an assumption the schema cannot state.
- **Fasting state.** The ADA glucose thresholds are *fasting* plasma glucose. One `Glucose` biomarker with no fasting dimension means a normal post-meal 130 mg/dL flags `above` (see the separate entry below).

**The sharper form of the problem, and the reason this is not a curation detail:** HDL alone wants **three** ranges — male-normal, female-normal, and optimal — and *optimal* is a different axis from *sex*, not a third sibling on the same one (a sex-specific optimum is perfectly coherent). So the dimensionality is at least two-deep, and the axes are not interchangeable. HDL was left unseeded in WI-3 rather than resolve this under time pressure; **hormone panels make it unavoidable** — testosterone, estradiol, FSH, and LH reference ranges are strongly sex-specific and often age- or menopausal-status-specific, and the catalog already carries all four.

Candidate mechanisms, none decided:
1. **Cohort columns on `framework_ranges`** (`sex`, `age_min`/`age_max`, `fasting`), extending the natural key. Expressive; complicates the point-in-time resolution rule ([ADR-0005](adr/0005-reference-range-frameworks.md)), which is currently provably single-valued — a property [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §3 leans on hard — and demands the *reader* know the owner's sex/age, which no read path does today.
2. **Sibling frameworks** (`nih_medlineplus_lipids_male` / `_female`). No schema change; multiplies frameworks combinatorially and makes "compare against MedlinePlus" ambiguous for a client.
3. **Split the biomarker** (`Glucose (fasting)`), which is right where the *measurement* differs rather than the population — the fasting case, not the sex case.
4. **A cohort/applicability table** the ranges reference. Most general; most machinery.

Note the platform stores what a mechanism would need: `lab_draws.fasting` exists, and owner sex/age would come from a profile concept that does not exist yet — worth noticing that (1) implies inventing one. Trigger: **the first hormone-panel range entry** (the point where omitting is no longer an option), or any second real instance of a sex-specific range the owner wants flagged. Until then the honest behaviour is `no_range` — say nothing rather than something misleading — and a range is one catalog import away whenever the owner accepts a given interpretation ([ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §6).

**Fasting-state glucose — one biomarker or several? ([ADR-0030](adr/0030-biomarker-identity.md), [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §5)**
The ADA thresholds seeded for `Glucose` are **fasting** plasma glucose (`FPG`), but the catalog has a single `Glucose` biomarker and the comparison never reads `lab_draws.fasting`, so a normal post-meal 130 mg/dL flags `above`. It errs conservative (a false "out of range", not a false "normal" — unlike the hypoglycemia floor, which was the dangerous direction and is fixed), so it is a wrong flag rather than a hazard. Owner's leaning (2026-07-17): make it a **distinct biomarker, `Glucose (fasting)`**, for known-fasted draws — the measurement, its reference range, and its clinical meaning all differ, which is a biomarker-identity distinction rather than a range dimension, and it gives CGM (Phase 7) somewhere natural to live instead of contorting the same row. Open: what plain `Glucose` then means (random/unknown), whether CGM is a third entity, whether the resolver should treat the names as aliases (it must not — they are different measurements), and whether existing `Glucose` rows need migrating. Trigger: WI-4's CLI (the first surface entering glucose by hand), or the first CGM adapter. Related to the cohort entry above, but the proposed mechanism differs — split the entity, not the range. **WI-4 shipped 2026-07-17 without folding this in** ([ADR-0059](adr/0059-cli-manual-entry-implementation-decisions.md) §5): the seeded ADA range is fasting plasma `Glucose` (FPG), so a fasting `Glucose` draw flags correctly; the split only matters once non-fasting/CGM input arrives, and the trigger is now live for that case.

**Physically one-sided quantities — a floor datum on `biomarkers` ([ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §3)**
Range comparison deliberately assumes nothing about a quantity's sign: a censored `<0.1` is the interval `(-inf, 0.1)`, so against an explicit `[0, 10]` target it is `indeterminate` rather than `in_range`. That is the fail-safe reading — the engine has no basis to invent a floor — but it is *wrong* for the many catalog biomarkers that are physically non-negative (concentrations, counts, enzyme activities), where the true answer is knowable. Owner's proposal (2026-07-17): store the fact rather than assume it. Candidate shape is a nullable **`biomarkers.physical_min REAL`** — `NULL` = "no known floor" (today's behaviour, unchanged, so the change is additive and safe by default), `0` = "cannot be negative" — which generalizes past a boolean to a non-zero floor if one ever appears, and mirrors the `range_low = NULL` idiom already in use. Then `<0.1` becomes `[0, 0.1)` and lands `in_range` correctly, while the engine still assumes nothing where the owner has not spoken. Open: the column vs. a boolean; which biomarkers get seeded `0`; whether an *upper* physical bound (e.g. percentages ≤ 100) is worth the symmetry; and whether import should validate stored values against it. Trigger: the first censored result whose `indeterminate` verdict is visibly wrong to the owner — most likely in WI-4, when real below-detection results start arriving. **WI-4 shipped 2026-07-17 without folding this in** ([ADR-0059](adr/0059-cli-manual-entry-implementation-decisions.md) §5): a below-detection `<0.1` flags `indeterminate` (conservative, never wrong-dangerous), so it stays deferred; the owner's revisit condition is the first such verdict that reads as visibly wrong during real entry.

**Non-numeric reference comparison — qualitative, ordinal, and count results ([ADR-0030](adr/0030-biomarker-identity.md), [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §2)**
The value model stores non-numeric results faithfully — `value_text` for qualitative ("NEGATIVE", "YELLOW") and semi-quantitative grades ("trace"/"1+"/"2+"), with `reference_text` the schema slot for the lab's own non-numeric range ("NONE SEEN", "< OR = 5 /HPF") where a caller supplies one (import carries it; `enter` does not yet — the Phase 3.5 fidelity gap); but comparison has no path for any of them: [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §2 short-circuits to `not_comparable` the moment `value_num IS NULL`. A urinalysis — the first specimen type to arrive that is dominantly non-numeric — therefore stores correctly but never flags: a "1+" result the lab itself marked abnormal comes back `not_comparable`. Three sub-shapes, increasingly hard: (1) **binary/categorical** — the expected value is a literal ("NEGATIVE"), flag on inequality; (2) **ordinal grade** — "trace < 1+ < 2+ < 3+" is an ordered scale, needing a declared ordering to say "above expected"; (3) **count-with-threshold** — "NONE SEEN" against "< OR = 5 /HPF" mixes a qualitative value, a numeric threshold, and a microscopy unit. This is the **non-numeric axis of the range-model-expressiveness theme** (the cohort-dimension, exclusive-bound, and `physical_min` entries above are the numeric axes) and should be weighed alongside them in the range-model PR — though the honest interim (`not_comparable`, say nothing) is correct and safe, exactly as for a missing numeric range. Surfaced 2026-07-18 by the first urinalysis panel; see [lab-data-dimensions.md](lab-data-dimensions.md) §1. Trigger: the first qualitative panel the owner wants *flagged* rather than merely stored, or its consolidation into the range-model PR.

**One draw, multiple performing labs ([data-model.md](data-model.md), [ADR-0027](adr/0027-audit-trail-and-corrections.md), [ADR-0018](adr/0018-fhir-interoperability.md))**
`lab_draws` carries a single `lab_id` — the "one blood-draw event at one lab" model ([ADR-0027](adr/0027-audit-trail-and-corrections.md)). Real reports break it: one collection/accession is routinely split across multiple *performing* labs (the ordering lab's main facility runs most panels; a specialty panel — a fatty-acid profile, say — is sent to a reference lab), each result line carrying its own performing-lab code. Manual entry records the whole draw under one lab (the ordering/source lab) and the per-result performing lab is lost — acceptable for a single-user longitudinal store, but a real fidelity gap and a distinction FHIR export ([ADR-0018](adr/0018-fhir-interoperability.md)) would want. Candidate shapes when taken up: a nullable per-result `performing_lab_id`, or treating the draw-level lab as the *ordering* lab with performing labs as result metadata. Surfaced 2026-07-18; see [lab-data-dimensions.md](lab-data-dimensions.md) §5. Trigger: the first Phase-7 ingestion adapter parsing a multi-lab report where the split is machine-available, or the first owner need to distinguish them.

**Independent verification of the tier-B molar masses ([molar-mass-provenance.md](molar-mass-provenance.md), [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §4)**
Twelve of the nineteen seeded `biomarkers.molar_mass` values are **tier B**: fetched from PubChem by a subagent and reconciled against a quoted clinical conversion factor, but not confirmed at source by a human or by the reviewing session. Seven are tier A (PubChem fetched live in-session). The full table, the sources, and the four counter-intuitive values (BUN 28.014 as urea-nitrogen not urea; Triglycerides/Folate assay-calibration proxies; Cortisol's adapted unit basis) are documented in [molar-mass-provenance.md](molar-mass-provenance.md) — that document is the record; this entry is the outstanding action.

Why it stays open rather than being closed as "checked": the tier-B cross-check is that the value reproduces the published factor, but the factor is essentially `10/MW`, so the check is near-tautological *if the factor was back-computed from the MW rather than quoted*. The evidence against that is a citation (`PMC11132569`) nobody has opened. Nothing is suspected wrong — the point is that "verified" and "reported as verified" are different claims, and a wrong molar mass is **silent**: it produces a plausible number and therefore a wrong range flag, which is the failure class [ADR-0005](adr/0005-reference-range-frameworks.md) exists to close.

Scope of the exposure is narrow today: a molar mass is only read when a result's unit and its range's unit differ by a mass↔substance factor, and every currently seeded range is stated in the biomarker's own `canonical_unit`. So no seeded comparison uses one yet. Trigger: **the first result imported in molar units** (mmol/L cholesterol or glucose from a non-US lab, a CGM feed in mmol/L), or WI-4's CLI making molar entry routine — either turns a documented gap into a live one. Cheapest closure is opening PMC11132569 and confirming the twelve factors against the table.

**Snapshot consistency of an enriched read ([ADR-0053](adr/0053-read-endpoint-surface-and-pagination.md), [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §1, [ADR-0037](adr/0037-core-service-concurrency-and-driver.md))**
`GET /v1/lab-results?framework=` performs four reads on one connection in autocommit — resolve the framework, fetch the page, look up the page's biomarkers, resolve their ranges — so each sees its own implicit transaction. A catalog import committing between them can mix pre- and post-import state within a single response: a range from the new state compared against a `canonical_unit`/`molar_mass` from the old. Raised by CodeRabbit on PR #28 and verified as real. It is deliberately not fixed there: this is a single-user local platform with one Core Service process, the interleaving window is milliseconds, and both writers are the owner — so the realistic outcome is one page reflecting a mid-flight import the owner just triggered, not a wrong answer anyone would act on. (The `RuntimeError` path the finding also cites is unreachable — it needs a framework *delete*, and no delete path exists.) The fix is to wrap each enriched read in one deferred read transaction, giving SQLite's WAL snapshot semantics a boundary to hold; the cost is transaction management in the read path, which currently has none, and it wants a concurrency regression test to be worth anything. Trigger: a second concurrent writer (Phase 4a's job/event surface, where an import is no longer owner-initiated and no longer obviously mid-flight), or the first observed mixed-state read.

**UCUM validation at the import boundary ([ADR-0031](adr/0031-units-and-ucum.md), [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §6)**
No import path validates that a unit string is well-formed UCUM. `biomarkers.canonical_unit`, `lab_results.unit`, and — as of Phase 3 WI-3 — `framework_ranges.unit` are all accepted as free text; `imports.py` does not import `healthspan.units` at all. This is deliberate rather than overlooked: singling out one column would be inconsistent, and an unparseable unit is fail-safe rather than silently wrong — it surfaces as a named `error` flag on every comparison ([ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §2), never a bad number. The cost is that the error surfaces at read time, far from the import that caused it, and `units.is_valid_unit` already exists to close it. Open: whether to validate all three columns at the boundary (consistent, fail-early, and a new `imports.py` → `units.py` dependency that pulls the UCUM grammar into the import path), or keep the read-time `error` flag as the only signal. Trigger: WI-4's CLI (the first interactive surface where a fail-early message is worth more than a late flag), or the first real unit typo that costs debugging time. **WI-4 shipped 2026-07-17 without folding this in** ([ADR-0059](adr/0059-cli-manual-entry-implementation-decisions.md) §5): the CLI defaults each result's unit to the biomarker's `canonical_unit` and does not validate UCUM client-side (consistent with the import boundary); an unparseable unit still surfaces as a named `error` flag, so it stays deferred pending the first typo that costs debugging time. Also a candidate check for the consolidated **Database integrity & sanity check** audit below.

**`draw_utc` format validation at the import boundary and schema ([ADR-0005](adr/0005-reference-range-frameworks.md), [ADR-0053](adr/0053-read-endpoint-surface-and-pagination.md), [ADR-0059](adr/0059-cli-manual-entry-implementation-decisions.md) §2)**
`lab_draws.draw_utc` is stored as free `TEXT NOT NULL` with no format check at the import boundary (`imports._domain_errors` validates only `draw_tz_inferred`/`fasting`) or in the schema (migration 0001 has no CHECK). But the whole date-handling scheme keys on it being a well-formed **hyphenated `YYYY-MM-DD` prefix**: point-in-time range resolution slices `draw_utc[:10]` and compares it *lexically* against `framework_ranges.effective_date` ([ADR-0005](adr/0005-reference-range-frameworks.md) §2, `ranges.resolve_ranges`), and the `draw_from`/`draw_to` read filters compare lexically too ([ADR-0053](adr/0053-read-endpoint-surface-and-pagination.md)). Lexical comparison is correct *because* ISO-8601 `YYYY-MM-DD` sorts chronologically — but only if the value actually is that form. A basic-format ISO-8601 value (`20260115`, or the timestamp `20260115T083000Z` — valid ISO-8601, but its first ten characters are `20260115T0`) or any malformed date stored verbatim silently mis-resolves the range with no error. **This is the write-boundary sibling of the UCUM-at-import question above** — the same "validate free text at the boundary vs. rely on a downstream signal" theme — except a bad `draw_utc` is *silently wrong* (a mis-dated flag), not fail-safe like an unparseable unit (a named `error`), so it is the stronger case for closing.

WI-4 closed this at the **CLI** surface only ([ADR-0059](adr/0059-cli-manual-entry-implementation-decisions.md) §2, `_validate_draw_utc`); `POST /v1/import` and any future adapter can still store a malformed `draw_utc`. Two **complementary, not either-or** controls — layered exactly as the codebase already layers the ADR-0030 value model and the `molar_mass` guard ([ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §4): boundary validation for a collected, named error, and a schema CHECK as the can't-happen backstop:
1. **Import-boundary validation** in `imports._domain_errors`, mirroring the `framework_ranges.effective_date` check already there: a collected `422` naming the offending row *before any write*, with full semantic rigor (real calendar date, UTC-only timestamp). Covers only import paths.
2. **Schema shape-CHECK** on `draw_utc` (e.g. `GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]*'`): a malformed value cannot exist regardless of which code path wrote it. SQLite CHECK can only enforce the **shape** (first ten chars are `dddd-dd-dd`), not calendar validity or the UTC designator — but the shape *is* exactly the substr-safety invariant the lexical comparison depends on, so it is a well-targeted backstop. Its cost is an opaque apply-time `IntegrityError` rather than a per-row message, which is why #1 carries the UX and #2 is only the backstop.

Neither subsumes the other; both are worth landing (belt-and-suspenders, same as the value model). Trigger: pair it with the UCUM-at-import work above (same import-boundary-validation theme), or the first malformed `draw_utc` from a non-CLI writer. Also a candidate check for the consolidated **Database integrity & sanity check** audit below.

**Additive `ALTER TABLE` migrations must recreate the affected `*_current` view ([data-model.md](data-model.md), [ADR-0027](adr/0027-audit-trail-and-corrections.md))**
The migration-0001 `*_current` views are `SELECT * FROM <table> WHERE superseded_by IS NULL`, and SQLite binds `SELECT *` to the base table's columns at `CREATE VIEW` time. A later migration that does `ALTER TABLE … ADD COLUMN` will therefore not surface the new column through the current-state view until the view is dropped and recreated. Convention to adopt when the first additive migration lands: any migration adding a column to a content table also `DROP VIEW`/`CREATE VIEW`s that table's `*_current` view (and a schema-integrity test asserts the view column set matches the base table). Surfaced by the 2026-07-11 end-of-Phase-1 holistic review.

**Trigger update (2026-07-16, Phase 3 WI-3).** Migration 0005 is the first `ALTER TABLE … ADD COLUMN` to ship (`biomarkers.molar_mass`, [ADR-0058](adr/0058-range-comparison-implementation-decisions.md) §4) — but the hazard did **not** materialize, because `biomarkers` is a catalog table: it has no `superseded_by` column and therefore no `biomarkers_current` view to go stale. The question stays open with a sharpened trigger: **the first `ALTER TABLE … ADD COLUMN` on a *content* table (one carrying `superseded_by`, and thus a `*_current` view)** — `lab_results`, `lab_draws`, `body_composition`, `cgm_readings`, `wearable_daily`, `events`, `interventions`, `intervention_dose_history`, `subjective_observations`, `clinical_documents`, `analyses`. The general schema-integrity test proposed above (every `*_current` view's column set matches its base table) remains the durable fix and is worth landing with — or before — that migration, since it converts a silent wrong-answer bug into a failing test. That same view/base-table column-set check is also a candidate for the consolidated **Database integrity & sanity check** audit below.

**Database integrity & sanity check — a deliberate, user-invoked audit ([ADR-0038](adr/0038-backup-execution-and-verification.md), [ADR-0027](adr/0027-audit-trail-and-corrections.md), [ADR-0035](adr/0035-migration-execution-semantics.md))**
There is no on-demand, report-only audit of the live database — a `chkdsk`-for-the-`.db` the owner can run deliberately. The primitives exist (`db.integrity_check` / `db.foreign_key_check`, wrapping `PRAGMA integrity_check` and `PRAGMA foreign_key_check`) but only as **gates inside other operations**: backup/restore verification ([ADR-0038](adr/0038-backup-execution-and-verification.md)'s "verified" definition), the migration runner's pre-commit `foreign_key_check` ([ADR-0035](adr/0035-migration-execution-semantics.md)), and the pre-rekey verified backup ([ADR-0028](adr/0028-key-derivation-and-rotation.md)). Startup `service.verify_schema` is narrower still (`schema_version` + the reserved `not_assigned` row). The `db` CLI exposes `migrate`/`backup`/`restore` — no `check`.

The concept is a deliberate `healthspan db check` that audits the whole database and **reports** (never silently gates, never auto-repairs), read-only by default — any future `--fix` a separate, backup-first escalation, since repairing a health database is the irreversible-action class the platform makes the owner confirm. Two layers:
1. **Physical + referential** — run [ADR-0038](adr/0038-backup-execution-and-verification.md)'s already-defined verification (`integrity_check` + `foreign_key_check` + `schema_version`) against the *live* database on demand, rather than only when producing a backup. High reuse; the machinery exists.
2. **Application / domain invariants ("sanity")** — the promises **no `CHECK` or foreign key can express**, which are therefore *silently wrong* if violated: `draw_utc`/`effective_date` format (the entries above), UCUM unit validity (above), `*_current` view column-sets matching their base tables (above), supersession-chain consistency (exactly one current row per natural key, `superseded_by` → a real newer row, no cycles — [ADR-0027](adr/0027-audit-trail-and-corrections.md)), `alias_normalized` disjoint from normalized `canonical_name` ([ADR-0054](adr/0054-biomarker-name-alias-fallback.md)), the reserved `not_assigned` row ([ADR-0055](adr/0055-biomarker-category-taxonomy.md)), audit-log coverage. This is the **consolidation point** for those scattered invariant items — they stop being one-off deferrals and become the initial check suite of one deliverable. Until that suite is scoped, the standalone entries above remain the authoritative deferral records: each keeps its own trigger and may resolve independently (e.g. as write-path validation) before `db check` exists — this entry consolidates them, it does not supersede them.

Why it earns its place even alongside write-time validation and schema CHECKs (the belt-and-suspenders of the `draw_utc` entry above): an on-demand audit is the only thing that catches a row written *before* a constraint existed, a migration bug, a direct-database edit, or bit-rot — failures no write-path guard can see. Architecturally it is a new command + subsystem (a new `db check` surface, a new invariant-audit module), so it warrants its **own Proposed ADR when scoped**; this entry is the lightweight capture until then. Trigger: when the subsumed invariant items above accumulate enough to warrant building the suite rather than closing them one at a time, or the first real integrity/invariant-violation incident, or the post-Phase-3 real-data-accumulation milestone where "is my data actually consistent?" becomes a question the owner asks.

~~**Clinical documents — full-text search strategy**~~ → Resolved (FTS5 external-content over `body`) — see Resolved section and [ADR-0041](adr/0041-clinical-document-fts.md).

**Subjective observation vocabulary ([data-model.md](data-model.md), Subjective Observations)**
The journal type starts freeform — `body` text only. Should a structured vocabulary (tags; 1–10 scales for energy, mood, pain, sleep quality) be added, and when? **Derived data points — deferred schema ([ADR-0044](adr/0044-derived-data-points.md))**
ADR-0044 fixes the principle (derived values are a distinct content class, never stored in source-data tables; interim home is the `result_data` attachment on analyses) and deliberately defers the derived-series table. Sub-questions recorded for when it is designed: (1) internally computed (formula stored, rebuildable) vs. externally computed (opaque snapshot) — the two subtypes behave differently under the [ADR-0027](adr/0027-audit-trail-and-corrections.md) correction model; (2) does a derived series get a `biomarker_id` ([ADR-0030](adr/0030-biomarker-identity.md))? (3) may derived series be range-compared ([ADR-0005](adr/0005-reference-range-frameworks.md)) — HOMA-IR has published ranges, so a blanket "never" is wrong; (4) staleness marking when a source row feeding a derived point is superseded. Design trigger: the analyses table exists in a running system and accumulated attachments show which subtype dominates.

**Accumulation evidence (2026-07-14, Phase 3 D1 discussion).** Two concrete *externally-computed* instances from the owner's Function Health data, recorded to inform sub-questions (1) and (3): **Biological Age** (opaque composite, unit years) and the IGF-1 **Z-Score** (opaque, unit SD, **published reference range −2 to +2**). Both are values the owner cannot recompute but wants imported for longitudinal analysis. They sharpen the deferral in two ways: (1) the externally-computed subtype behaves like *received source data* under the correction model — correcting the owner's stored IGF-1 does not invalidate a Z-Score Function computed from its own measurement, so the "never in source tables" hazard (rebuildable staleness) does not apply to it the way it does to internally-computed HOMA-IR; (3) the Z-Score's −2..+2 range is a live counterexample to any blanket "derived values are never range-compared." These do **not** resolve the deferral (still Phase-5-triggered) and are explicitly **not** Phase 3 biomarkers — importing them is ADR-0044-gated, not part of the [ADR-0055](adr/0055-biomarker-category-taxonomy.md) taxonomy.

**Accumulation evidence (2026-07-18, a comprehensive metabolic + lipid panel).** Such a panel surfaces *both* subtypes at once, sharpening sub-questions (1) and (3): **internally-computed, reproducible** calcs — Non-HDL (`Total − HDL`), Globulin (`Total Protein − Albumin`), A/G ratio, Chol/HDL ratio — whose formula and inputs are all stored, so they recompute exactly and need never be stored as source rows; and an **externally-opaque** one — LDL-C by the Martin-Hopkins method, which unlike Friedewald cannot be reproduced without the published divisor table, so it behaves like received source data (the same class as the Biological Age / IGF-1 Z-Score examples above). The discriminator is *reproducibility, not arithmetic difficulty*: Globulin (`Total Protein − Albumin`) is as reproducible as Non-HDL, so both defer identically; only LDL-C is the genuine opaque snapshot. The interim rule holds and is now written into the manual-entry policy ([development-plan.md](development-plan.md), Phase 3.5; [lab-data-dimensions.md](lab-data-dimensions.md) §8): **derived values are not entered** — the reproducible ones reconstruct from components, the opaque one from its stored inputs when the method lands — so deferring the schema costs no information.

## Product Scope

**Internationalization and localization — deliberately out of scope for 1.0 ([ADR-0059](adr/0059-cli-manual-entry-implementation-decisions.md) §2, [ADR-0031](adr/0031-units-and-ucum.md), [ADR-0041](adr/0041-clinical-document-fts.md), [ADR-0054](adr/0054-biomarker-name-alias-fallback.md))**
1.0 ships US-English, single-locale. Until this entry, the only recorded trace of that stance was a parenthetical in [ADR-0059](adr/0059-cli-manual-entry-implementation-decisions.md) §2 — "the locale is not established in-repo", the reason comma-decimal input warns rather than guesses. This entry makes the scope decision explicit and inventories what it touches, so the remaining phases inherit disciplines instead of rediscovering them.

**What is already locale-invariant by existing decision (conventions to hold, not open questions):** storage and wire formats are locale-neutral — ISO-8601 UTC timestamps ([design-rationale.md](design-rationale.md)), dot-decimal numbers, UCUM unit strings ([ADR-0031](adr/0031-units-and-ucum.md)) — and machine-readable fields (status codes, enum values like `in_range`, structured error fields) are the contract while English free text (`detail` messages, CLI notices) is presentation only. Restated normatively in [api-reference.md](api-reference.md) Conventions so Phase 4b's MCP tool-output work inherits it. SI-vs-conventional units — the localization axis that actually matters in health data — is likewise absorbed at the data layer: comparison unit-normalizes through the UCUM engine ([ADR-0058](adr/0058-range-comparison-implementation-decisions.md)), and SI-default entry is tracked as *known-needed but unexercised* in [lab-data-dimensions.md](lab-data-dimensions.md).

**Known English couplings** — the inventory a future i18n effort would work through:

1. **Name-keyed identity.** `biomarkers.canonical_name`, `categories.name`, and framework names are UNIQUE English strings serving as both identity and display, and `GET /v1/biomarkers` looks categories up by name. LOINC ([ADR-0030](adr/0030-biomarker-identity.md)/[ADR-0032](adr/0032-biomarker-loinc-cardinality.md)) is the language-neutral identity lane, and the alias resolver ([ADR-0054](adr/0054-biomarker-name-alias-fallback.md)) already handles non-ASCII names (NFKC + casefold), so translated *input* names are alias rows — additive — provided canonical names are treated as stable opaque keys, never renamed casually. Translated *display* names would be a new concept, deferred with the rest.
2. **FTS tokenizer.** [ADR-0041](adr/0041-clinical-document-fts.md)'s `porter` stemmer is English-only and `unicode61` does not segment CJK: a non-English clinical document stores and encrypts fine but searches with degraded recall. The tokenizer is baked into the FTS DDL; ADR-0041 records the index as rebuild-reversible, which is the escape hatch.
3. **GUI strings and display formatting (Phase 6).** Qt's translation machinery (`tr()`) is nearly free at write time and a full retrofit sweep later — decide at phase start even if translation never happens. Separately, Qt defaults to *system-locale* number/date formatting, which on a comma-decimal locale would display `5,2` against a CLI and API that speak `5.2` and refuse comma-decimal input ([ADR-0059](adr/0059-cli-manual-entry-implementation-decisions.md) §2) — the GUI's display-locale policy must be decided deliberately, not inherited from Qt.
4. **Source exports are locale-dependent (Phase 7).** Adapters parse files produced by the *device's* locale: localized display names, locale number/date formats, and either unit system (CGM is mmol/L in most of the world). Disciplines: parse with explicit invariant assumptions — never bare `float()` on export text, the ADR-0059 §2 warn-don't-guess stance applied to adapters; key on the format's stable identifiers where they exist (e.g. HealthKit type identifiers) rather than display names; carry the export's declared unit through UCUM conversion rather than assuming `mg/dL`. Each per-source format investigation records the format's locale behavior as one of its questions ([development-plan.md](development-plan.md), Phase 7).
5. **English message text** in errors, CLI notices, and future notification templates ([ADR-0017](adr/0017-notification-channels.md)) — harmless while the codes-are-contract convention holds, a translation-catalog problem only if a trigger fires.

Per-phase hooks pointing back here live in [development-plan.md](development-plan.md) (Phases 4, 6, 7). **Escalation rule:** no i18n spec document or ADR exists until a trigger fires — this entry is the authoritative capture. When one does fire, the first artifact is a scoping document (or ADR) that separates *display language* from *data locale*, since the couplings above split cleanly along that line. Trigger: the first non-English source document the owner wants searchable; the first SI-default data source the conversion engine does not already absorb; any GUI translation demand; or any second-user / distribution scenario that makes display language a real variable.

**Non-loopback binding hardening ([ADR-0049](adr/0049-core-service-skeleton-implementation-decisions.md), [security.md](security.md) Network Security)**
Phase 2 WI-1 added the `[service] host` config key (default `127.0.0.1`, loopback-only). The parser *accepts* a non-loopback bind (`0.0.0.0` or a specific interface), but security.md's Network Security controls that a LAN bind requires — Host-header validation and CORS as DNS-rebinding defenses, and HTTPS for any non-loopback address — are **not implemented** in `service.py`/`_run_uvicorn`. Impact is currently bounded: the only live route is the status-word-only unauthenticated liveness endpoint. But a user who repoints `host` and later gains authenticated data routes would be exposed, so **non-loopback binding is unsupported until these controls land**. Trigger: the first authenticated data route (WI-2/WI-3), where the controls belong with the auth/middleware layer — or an explicit LAN-deployment milestone.

**Broadened by WI-4 (2026-07-17, PR #31, CodeRabbit).** The risk now also has a **client-side / outbound** face: WI-4's CLI (`cli_client.default_client`) sends `Authorization: Bearer` requests to `service.host` over `http://`, so a non-loopback `service.host` puts the token on the wire in cleartext (CWE-319) independent of what the *server* binds to — and `config._parse_service` accepts any non-empty host ([ADR-0049](adr/0049-core-service-skeleton-implementation-decisions.md) §Binding posture makes a LAN bind a deliberate, user-typed opt-in), so nothing rejects it. A related sub-vector was found and **closed** in the same PR: `default_client` sets `trust_env=False`, so an inherited `HTTP_PROXY`/`HTTPS_PROXY` cannot route even the *loopback* bearer request through an external proxy (httpx trusts those by default). The remaining deferral is therefore specifically the non-loopback-**host** controls, not the proxy angle. Candidate resolutions when taken up: **(a)** implement security.md's controls (Host-header validation, CORS, HTTPS) and keep ADR-0049's explicit LAN opt-in — honors both, no revisit; or **(b)** reject a non-loopback `service.host` in `_parse_service` (CodeRabbit's suggestion), which reverses that ADR-0049 opt-in decision — an amendment while ADR-0049 is Proposed, a superseding ADR once it is Accepted. Either is a legitimate Phase-3 action; both sit outside WI-4's client scope. **Trigger (sharpened):** resolve before the platform supports any non-loopback *authenticated* deployment — a Core Service bound beyond loopback, or a CLI `service.host` pointed at a remote host — since the parent trigger (first authenticated data route) has already fired.

## Development Workflow

**Should the gate-invocation hook run under `uv` rather than a bare `python3`?**
Every other tool in this repository is pinned — `ci.yml` pins each `uvx` version, `run_gates.py`
derives them, and the hook itself exists to stop unpinned invocations. The hook is the exception:
it runs under whatever `python3` names on `PATH`. That is not only a missing capability (no project
venv, so no third-party import is reachable — which is what forces a parser to be hand-rolled or
vendored) but a **robustness gap**: a module-level import unavailable on that interpreter exits 1
with a traceback on every matched call, outside every guard in the script. `tomllib` was one such
import and has been deferred; thirty-three module-level statements remain, and a bug in any of them
still exits 1 with a traceback on every matched call, outside the script's fail-open design —
whether the harness then blocks the call is the open question below.

`uv` is already permitted by `test_the_registered_interpreter_is_a_bare_portable_name`'s allowlist,
so this was contemplated and not taken — ADR-0077 §8's reasoning weighs `python` against `python3`
spelling and never considers `uv run`. Measured cost: `uv run --frozen --no-sync python -c pass`
against `python3 -c pass` is **~145 ms** more per call (840 ms vs 695 ms median, both inflated by
Windows process spawn; the delta is the figure). `--frozen --no-sync` is load-bearing — a plain
`uv run` may sync, and a hook that installs packages before every shell command is not acceptable.

**Two risks to measure before deciding, not after.** Whether `uv` is reliably on `PATH` wherever the
hook runs — if not, that is the same launch-failure class by another route. And how `uv run`
resolves its environment from inside a **git worktree**: this project has already recorded a bare
`uv run` in the wrong context destroying a venv, and `UV_PROJECT_ENVIRONMENT` exists precisely
because that resolution is not obvious. **Trigger:** the follow-up work item that also weighs
vendoring a real shell parser, since both change what the hook may import and both rewrite the
registered command.

**Does a PreToolUse hook that fails to launch block the tool call, or not?**
**Narrowed 2026-08-15 by external review round 2: the documentation says it does *not* block, and
the contrary observation is unreproduced.** The two sources are no longer symmetric, and the entry
stays open only for the experiment. The session that built the
[ADR-0077](adr/0077-local-invocation-hooks.md) hook registered it at a path that does not exist in a
git worktree, observed `PreToolUse:Bash hook error: … can't open file`, and reported losing every
shell call for the rest of the session — the account on which that ADR's §5 launch-failure row was
first written. Claude Code's own hooks documentation describes the opposite: a hook that cannot
start is a **non-blocking** error, and for `PreToolUse` the tool call proceeds through the normal
permission flow. The same source also contradicts that session's second claim, that hook
configuration is captured at session start and cannot be reloaded.

Both readings cannot be right, and the difference is not academic — it decides whether a broken hook
costs a session or merely prints a notice, which is the difference between "prevent at all costs"
and "prefer to avoid". A mechanism that predicts both accounts exists and is worth testing before
either source is trusted: a non-blocking hook error leaves the call to the ordinary permission flow,
where a *separate* denial (a permission prompt, an auto-mode classifier) would read to the session
as the hook having blocked it. That would make the observation real and its stated cause wrong.

Not settled here because the obvious experiment — registering a deliberately unresolvable hook on a
narrow matcher and watching what happens to that one tool — was refused twice by the permission
classifier, through the shell and through the file-edit path both, and pressing further would have
meant looking for a way around a denial rather than accepting it.

**What round 2 added.** Quoted from the hooks documentation: a hook that cannot start exits ~127,
which falls under *"Any other exit code doesn't block on its own for most hook events"*, and the
exit-code table gives `PreToolUse` a blocking row under **exit 2** specifically. The
caching claim already named above fares no better: hook edits are picked up by a file watcher, and
the documented remedy when the watcher misses one *is* restarting the session.

**An accidental event bears on the caching half, and it is weaker evidence than it first looks.**
While applying external round 2, the hook **denied one of the applying session's own Bash calls**,
emitting its own remedy text verbatim; a reviewer's tool call was denied the same way in a separate
agent session. What that establishes cleanly is narrower: the harness honours a hook's
`permissionDecision: deny` end-to-end, which nothing had verified, because every test drives the
script directly rather than through a registered hook.

The tempting further inference — *the hook was absent at that session's start, so configuration is
not frozen at start* — is **stated here rather than in the ADR, because it does not survive
inspection cleanly.** Three things weaken it. The applying session's start state is not visible in
committed history: the hooks had been removed from `.claude/settings.json` as an *uncommitted*
working-tree change, so `git show <session-start HEAD>:.claude/settings.json` still shows a hooks
key and the timeline appears to contradict the account. Only the repository-local settings files
were checked at that session's start; the user-global file was taken from an earlier session's
report rather than re-read. And the original account asserts the opposite outcome — a hook that
kept firing after removal *and* a restart — which no one has reproduced or explained.

So the honest position is that the deny event is **consistent with** a file watcher and does **not,
by itself, establish** that the caching claim is wrong — the three weaknesses above are exactly
what would have to be closed for it to. Saying otherwise would restate, as a conclusion, the
inference this paragraph has just disqualified. **Both halves of this entry still want the
contained experiment**, and it remains the only thing that would close them. The blocking half
additionally carries the prose hedge above. A route that avoids the classifier wall
was proposed and not taken: a throwaway directory outside the repository with its own
`.claude/settings.json` registering an unresolvable matcher, driven by `claude -p`, touching no
repository file and no machine-global state. It spends a nested session's tokens, so it is the
owner's call rather than a reviewer's.

ADR-0077's design does not depend on the answer: a hook that cannot start cannot fail open, cannot
report, and cannot be observed to have stopped policing, which is sufficient reason to prevent it.
What depends on the answer is only how the ADR is allowed to *describe* the failure, and §5 is
hedged accordingly. **Trigger:** the next session that can run the contained experiment (or a
version-pinned citation from the Claude Code documentation); resolution updates ADR-0077 §5 and the
`check_gate_invocation.py` docstring together, since both carry the hedge.

**Unbalanced markdown emphasis is a rendering defect no gate catches**
PyMarkdown enforces style, not inline correctness, so a paragraph that opens `**` and never closes it passes every gate green and then renders a literal `**` to the reader. Measured on the ADR-0072 branch (PR #83), twice: one broken bold span was found by a reviewer and hand-fixed, and the hunk that fixed it **introduced a second one in an adjacent paragraph of the same section**, which the next round then caught. That is a mechanism rather than bad luck — hand-editing emphasis in a long document re-triggers this class at some nonzero rate, and nothing before commit looks for it.

The check is cheap and is already specified by measurement rather than guessed at. Split each file on blank lines and flag any paragraph whose `**` count is odd — **but strip fenced blocks and inline code spans first**, which is not optional: run naively over the 122 tracked markdown files it flags **6** paragraphs and every one is a false positive, a glob such as `` `.claude/**` `` or `` `specs/*.md` `` sitting inside a code span; with code spans stripped the same corpus reports **0**. (That figure was first recorded here as 7, because the run that produced it included *this entry's own* then-unbalanced paragraph, which was rewritten immediately afterwards — a measurement taken over a corpus and then reported after editing that corpus. It is left visible rather than quietly corrected: it is a small instance of exactly why the gate is wanted, and of why a recorded number needs the state it was taken against.) So the naive form would ship a gate that fails on a clean tree and teaches its operator to ignore it. **And the stripper itself has to be CommonMark-correct, not a regex approximation**: matching `` `…` `` naively leaves one residual false positive on this corpus, a code span whose *content* is a literal triple-backtick — legal CommonMark, since a span's delimiter is a backtick **run** matched by length. A naive stripper therefore reintroduces the same false-positive-teaches-ignore failure one level down, which is the sort of thing worth knowing before writing the gate rather than after — the same failure shape as a permanently-false alarm elsewhere in this file. It belongs in the tree-walking-pytest-gate family alongside [`tests/test_except_convention.py`](../tests/test_except_convention.py) and [`tests/test_no_task_output_citations.py`](../tests/test_no_task_output_citations.py) rather than in the markdown-lint config, because it is a semantic check the linter's rule set does not model.

Deliberately not built on the branch that found it: a repo-wide gate riding a work item scoped to one ADR is how a reviewed diff grows a tail. Still open: whether single-asterisk emphasis and underscore emphasis want the same treatment (both have far higher false-positive rates in prose — an unpaired `*` is legal, and `_` appears inside identifiers), and whether the paragraph is the right unit given tables and multi-paragraph list items. Trigger: the next markdown-heavy work item, or the third recurrence.

Each of them imports the script as a module and exercises its check function against synthetic fixtures that break exactly one precondition apiece — which is what `specs/testing-strategy.md` § Unit tests obligates for pure-logic parsing over string inputs, and is the part to copy. Most of them additionally assert against the live repo and `check_spec_links.py` deliberately does not; **no count is given, and that is a correction rather than vagueness** — the sentence read "Three of them" and named them, which was a tally of the four gates that had suites at the time and went wrong the moment `check_adr_index.py` gained one (whose suite asserts against the live repo too). (The figure had already been stated three incompatible ways across four documents before that, which was the smaller version of the same lesson.) Four things the implementation established that the analysis above did not, recorded because they cost measurement. **This is not the "gaps closed" enumeration**, and the two lists must not be read as one. Items 1, 3 and 4 below *are* three of the four canonical gaps (untracked-directory collapse, `-z` quoting, tracked-but-unmodified); item 2 is an instrument choice rather than a hole, recorded under [ADR-0070](adr/0070-personal-data-containment-gate.md)'s Considered Options; and the fourth canonical gap — shallow-clone truncation — is not in this list at all, appearing unnumbered further down. The authoritative gap list lives in `scripts/check_personal_containment.py`'s docstring and is restated in ADR-0070 §6; take it from there and not from any count in this entry.

1. **A seventh hole, found by the gate's own test suite rather than by review.** `git status --porcelain` collapses an untracked *directory* to a single record naming the parent, so a personal file whose parent directory is itself untracked is reported as `?? specs/` and no prefix match ever sees the path. `--untracked-files=all` is the fix. Whether the collapse happens depends on whether some sibling directory is tracked — not a property a containment scan may rest on, and the reason the prose version's `git status --porcelain` was never sufficient even before the merge-commit and merge-base holes.
2. **`git rev-list --objects --all` is the natural-looking instrument for the history scope and is unsound.** It lists each *object* once, so files sharing content collapse to one line under one arbitrary path: measured on a repo with three identical-content files, it named one and never mentioned the personal one, while the diff walk reproduced the per-commit `ls-tree` ground truth exactly. The history scope is therefore `git log --all --diff-merges=first-parent --name-only --format= -z`, the same mechanism as the branch scope over every ref.
3. **`-z` is load-bearing on every path list, not tidiness.** Without it git *quotes* a non-ASCII path — `"specs/personal/caf\303\251.md"`, wrapped in literal double quotes — and the leading `"` defeats a prefix test anchored at the start of the path. A false negative in the one direction that matters.
4. **A tracked but unmodified containment file is invisible to both local instruments.** It is unmodified so the porcelain is silent, and its commit sits behind the merge base so the branch walk never reaches it. `git ls-files -z -- ':(icase)specs/personal'` runs in *every* scope for that reason. `scripts/review_worktree.py` already guarded this for the reviewer worktrees; `/land` did not.

**The shallow-clone gap is the one worth reading twice**, because it is item 1's class turned on the gate itself: on a `--depth 1` clone the `history` scope exited **0** announcing "620 paths examined" while holding 4 commits of roughly 80 — hole 2 reproduced *inside the mechanism built to end it*, now refused outright by a `git rev-parse --is-shallow-repository` guard. **The enumeration surface is treacherous enough that the gate replacing the prose reproduced the prose's own signature defect on its first contact with an unusual checkout.** It argues the register's third column should record not just *what* enforces a rule but whether the enforcement can fail silently — and it is why the gate now prints per-source counts and refuses preconditions it cannot satisfy rather than reporting over them.

**Harness agent-output files are empty — a gated rule resting on an observation that can expire.** The Claude Code harness writes each subagent's result pointer as a `tasks/<id>.output` file, and on this machine those files are reliably **0 bytes** — measured on three separate multi-agent review passes (two recorded in the review-handoff limitations diagnosis; on the third, all ten finder agents returned empty files and ~25 findings survived only because the orchestrating session transcribed them as they arrived). CLAUDE.md § Subagent output pointers states the working rule (capture results into your own scratchpad as they arrive), and `tests/test_no_task_output_citations.py` gates the `.claude/**` half — no skill or agent file may cite such a path, because an instruction pointing at one sends a future session to an empty file and silently loses whatever the pointer promised. Recorded here because the rule's basis is an *observation about the current harness version*, not a contract: nothing upstream promises those files stay empty, and if a future harness populates them the prohibition loses its reason. Trigger: re-evaluate if a `tasks/` directory listing after a multi-agent run shows non-zero sizes; resolution then is to decide whether the pointer files become a supported capture path, not to silently delete the gate.

A third is a design correction rather than a hole — reporting *every* index/working-tree divergence failed the whole scan on porcelain `MM`, the most common mid-session state there is, so only a divergence git actively **hides** (`skip-worktree`, `assume-unchanged`) is now a violation and the visible kind is a note.

The CI half is the **backstop, not the control**: it runs in the `gitleaks` job (which already checks out at `fetch-depth: 0`, which the scan needs and the docs-consistency job does not have), and by the time it fires the blob is already in GitHub's object store. **Classify every `AbortError` at its raise site instead of by matching its sentence**
`.claude/reviewer-isolation.md` splits exit-1 aborts into *blocking* (drop to the unisolated fallback) and *recoverable* (fix and rerun), and the document concedes in its own text that the split is tracked "by hand and by nothing else" — there are far more `raise AbortError` sites in `scripts/review_worktree.py` than the two lists have entries (**44**, AST-counted 2026-08-03, against roughly 15 classified causes — and it was 40 the day before, which is the point: the ratio is what the argument rests on, not the total, and the total moves with every fix pass), and nothing checks that a new abort site gets classified at all. This is load-bearing in the dangerous direction, because *blocking* routes to the shared-live-tree mode the 2026-07-27 phantom-finding incident came from. It has already cost a round: the held-`.git/index.lock` abort guessed "conflicted or unmergeable index state?", an orchestrator matched that string against the blocking list, and permanently degraded a round whose correct remedy was to wait a second and rerun. That fix reworded one message, so the next unclassified abort reproduces it exactly. The instrument: give `AbortError` a `blocking: bool` (or two subclasses), have `main` print it as a **field** in the error line so an orchestrator reads a value rather than pattern-matching prose, and add one AST test asserting every `raise AbortError` supplies it. Recorded rather than implemented (owner's call 2026-08-03): it touches all 44 sites and the launch procedure's triage section at once, which is a poor thing to land in the middle of a fix pass. **Trigger: the WIP-commit sweep below**, which re-slices this module and its abort sites anyway — or the first time a misclassified abort degrades a round again, whichever comes first.

**Align the tooling, agents, and skills to WIP commits before review ([ADR-0068](adr/0068-reviewer-isolation-worktrees.md))**
The session workflow commits *after* review — `/land` proposes the commit, so the reviewers' slot is between implementation and the first commit. That ordering is fine within one session and wrong for anything longer. The branch that introduced ADR-0068 ran **its whole review program — more than a dozen external and local rounds — at zero commits**, with **~5,300 lines** of new infrastructure existing nowhere but a working tree (measured 2026-08-02 across the five new files; a point-in-time figure like every count in this repo's prose, and it has only grown). Four concrete costs, all measured on that branch rather than hypothesized:

1. **The drift check cannot fire.** [`/apply-review`](../.claude/skills/apply-review/SKILL.md) step 1 compares the report's pinned `HEAD` against `git rev-parse HEAD` to warn that findings may cite moved lines. `HEAD` never moved, so reports 5 and 6 both recorded "no drift" across a tree that had gained three files and hundreds of lines between them. A live safety check reported green because it was structurally incapable of firing.
2. **ADR-0068's leading Decision Driver is self-inflicted.** "The tree under review is often the only copy of the work: a failed restore destroys content that exists nowhere in git" is true *because* nothing is committed. The 2026-07-27 incident that motivated the whole ADR would have been `git checkout .` against a commit.
3. **A large share of the launcher exists only to carry uncommitted state** — the `git stash create` snapshot, the untracked copy-in and everything hanging off it (symlink re-check, mode bits, byte fidelity, non-UTF-8 filenames), the index/worktree divergence abort, the skip-worktree and machine-local-ignore warnings, and the ephemeral-SHA caveat. Against a commit, none of it is load-bearing. The shape is the opposite of the obvious guess: roughly **28% of the module's lines** retire against roughly **56% of its test-function lines** (53 of 104 test functions and 1,208 of 2,147 lines when the estimate was taken, 2026-08-02). No current total is quoted here on purpose — three successive attempts to state one went stale inside the same review round that added the tests, which is the honest signal that this file grows faster than a number in prose can track. Treat the *ratio* as the finding and re-measure the totals when the sweep starts. The tests, not the module, are where it bites — which also means the sweep is where a large block of *proven* detection power gets deleted, and that deserves to be a deliberate act rather than a side effect.
4. **Nothing lets a later review round verify an untracked file's history.** A tracked file's content between two rounds is provable with `git diff <sha> <sha>`; an untracked file's is not, because no commit ever captured it — so "unchanged since the last round" is an assertion the next reviewer must take on trust. Round 10's reviewer could check it only because a previous round's ad-hoc mutation backups happened to survive in the shared scratch directory: reviewer hygiene, not a property of the mechanism. No amount of state-file engineering closes this while the files stay untracked (the state file records untracked *names*, and teardown deletes it by design); a commit closes it by definition.

What stays true regardless: **invariant 1 still needs worktree isolation** — two agents in one tree collide whether or not the work is committed — and mutation testing still needs a disposable copy. So this does not retire ADR-0068; it shrinks it, and moves the uncommitted-state handling from *the default path* to *a supported fallback*.

**Deferred to this sweep, and recorded here because a docstring is not a record.** Two clusters were repeatedly "deferred to the WIP-commit sweep" in review rounds without ever landing anywhere a future author would look. (a) The **efficiency items**, measured 2026-08-02 and none of them correctness bugs: the launcher spawns 3 `git diff` processes where 2 suffice, reads the worktree registry 2N+1 times per teardown, overlaps `ls-files` queries, re-`resolve()`s the same paths repeatedly, runs a per-file stat stack during the copy, re-probes conditions on worktrees 2..N that worktree 1 already settled, and spawns three keychain subprocesses in the test suite; `--agents` also defaults through a string parse in tests that could pass a list. (b) A genuinely **different mechanism for the untracked copy-in**, raised by a review round and *not* re-measured since: a throwaway `GIT_INDEX_FILE` plus `read-tree` + `update-index --add -z --stdin` + `write-tree` + `commit-tree` produces one commit carrying tracked *and* untracked state, materialized by an ordinary `git worktree add`. It was reported to leave the live `.git/index` byte-identical (stronger than the current guarantee, which admits a stat-cache rewrite) with `git status` unchanged, and to dissolve four of the six special cases including the non-UTF-8 apparatus — while still needing an explicit check for `update-index`'s silent `Ignoring path vendor/dep/` on a nested repo, and still needing `_escapes` for junctions. **Verify that measurement before acting on it**; it bears directly on how much of this sweep is worth doing at all.

Cost of adopting is close to zero: `/squash-merge` already collapses branch history, so WIP commits are free, and `scripts/review_worktree.py` **already supports the committed mode today** — `branch_has_diff` plus the base ref keep a clean tree with a non-empty `base...HEAD` reviewable, and `test_branch_diff_alone_is_enough_to_review` pins both the gate decision and that the worktrees materialize at `HEAD` carrying the diff. **A locally run agent CLI as a review lens — evaluated and tabled ([ADR-0064](adr/0064-reviewer-workflow-trust-boundary.md))**
The repository's CI-side Gemini reviewer is deliberately opt-in and **best-effort** — a posture that lives in the reviewer skills themselves ([`.claude/skills/gemini-review/SKILL.md`](../.claude/skills/gemini-review/SKILL.md), [`.claude/skills/ship/SKILL.md`](../.claude/skills/ship/SKILL.md)) and in no ADR, since ADR-0064 governs that reviewer's *trust boundary* rather than whether it is a required lens. Its free API-tier credential sustains only ≈1 successful review per day (observed for this project and model in 2026-07; the free-tier cap is project-, model-, and account-dependent and shifts without notice, so the AI Studio rate-limit dashboard is authoritative), so it can never be a required lens and no merge waits on it. That leaves an obvious question — whether a **locally run** agent CLI, authenticated by an interactive *subscription* rather than a metered API key, supplies the same second-opinion lens without the quota ceiling. Evaluated 2026-07-24 against a vendor CLI (Google's Antigravity `agy` 1.1.6, consumer OAuth) and **tabled**. Three findings, recorded because they generalize to any comparable third-party local agent and are expensive to rediscover:

1. **Scoped branch-vs-main diff review is mechanically available, in two modes with very different exposure.** The CLI has a genuine headless mode (one prompt, response on stdout, exit 0). It reviews correctly with **no repository access whatsoever** — the diff piped in as prompt text — and it also runs agentically over a checkout, reading files itself. The no-access mode was verified against a real commit diff from this repository (correctly returning clean on an already-fixed state) and against a synthetic diff carrying two planted defects, both found. Headless caveat: a tool call needing a permission the configuration does not grant is **auto-denied** — nothing can prompt for it — and the agent then burns turns retrying rather than failing fast.
2. **A `.gitignore` entry is not a containment boundary, and the vendor's allow/deny rules are a leaky blocklist.** Tested with a synthetic sentinel in a throwaway repository, never real data: the agent read a gitignored file on the first attempt. Path-scoped deny rules *do* work once written, and a blanket deny on shell execution holds — but the rules are keyed **per tool**, and a deny list naming only the obvious file-read tool was silently routed around via a search tool, which read the sentinel successfully. Incomplete enumeration fails **silently**, which is the failure class this project has repeatedly paid for. The vendor's documented pre-tool-use hook — the one mechanism that could enforce a path rule centrally — was **not loaded at all** by the CLI at the version tested, so the cleanest guard was unavailable.
3. **Subscription quota is the binding constraint, and is plausibly worse than the metered tier it would replace.** The harness carries a large fixed per-request overhead (its own system prompt and tool definitions) regardless of how small the input is; the vendor acknowledges this publicly as an open problem. The subscription tier moved from a short refresh window to a **weekly** one, so exhausting it can mean a multi-day lockout rather than a few hours, and the allowance is **shared** across the vendor's desktop app, CLI, and SDK — local reviews compete with ordinary interactive use. No usage counter is exposed to the headless path, so consumption cannot be measured before it bites.

**Why this is a containment question and not a tooling preference:** CLAUDE.md confines personal health data to `specs/personal/`, which is gitignored but **sits inside the working tree**. The repository's code is public and sending it to a third-party model changes nothing; that directory is the entire exposure, and finding (2) says the boundary protecting it is not one the vendor's configuration can be trusted to hold. Consumer terms compound it — the vendor's additional terms reserve broad use of "interactions" for product and model improvement, with a clear carve-out only for enterprise-class credentials, while a separate vendor FAQ claims paid tiers are exempt; the contradiction is an open, publicly documented vendor bug and is unresolved, so the conservative reading governs.

**This evaluation therefore carries a default posture into any future adoption decision**, so that it is inherited rather than rediscovered — a strong recommendation the adopting change would confirm, not a constraint that forecloses its own judgment: containment should hold **by construction**, never by a path blocklist — review from a throwaway worktree or clean clone, where the gitignored personal directory simply does not exist, or pipe the diff in with no repository access at all. Never point such a tool at the live working tree. **Both modes rest on one shared precondition** — that nothing under `specs/personal/` is ever *tracked* — and a `git add -f` defeats them alike: a force-added file lands in a clean clone exactly as it lands in a diff, so neither mode is the safer one on this axis (raised against the piped-diff mode alone by CodeRabbit on PR #65; the scoping was wrong, the underlying gap real). That precondition is CLAUDE.md's existing containment rule, not a new control invented here, and it is where the guarantee belongs: a *reviewer-side* path filter is the same enumerate-your-way-to-safety mechanism finding (2) watched fail silently, and a personal file that reaches a commit in this public repository is already published — an exposure strictly worse than any model reading it, and one no reviewer configuration could have prevented. This adds no platform invariant ([security.md](security.md) is untouched; the reasoning mirrors ADR-0064's "data is inert, code is not" boundary applied to the *reviewer's* inputs rather than its executable artifacts). The by-construction mode has since been confirmed and adopted for the repository's own **first-party** session reviewers ([ADR-0068](adr/0068-reviewer-isolation-worktrees.md), Proposed at adoption): `spec-reviewer` and `test-reviewer` run from stash-snapshot worktrees where the gitignored personal directory never materializes — exactly the throwaway-worktree posture this entry recommends, extended to carry uncommitted state. Two scope qualifiers keep that claim honest: it inherits this entry's shared precondition and enforces a **second, independent one** — `scripts/review_worktree.py` refuses to snapshot both when anything under `specs/personal/` is *tracked* and when anything there is no longer *ignored*, since a deleted or negated `.gitignore` rule makes the directory ordinary untracked content that lands in a clean clone and in `git diff` alike, which is the same exposure by another route; both guards match case-insensitively and both accept the bare path `specs/personal` as well as the directory prefix, because the ignore rule is directory-only and a plain file at that exact path is ignored by neither git nor a prefix test (all four holes were found by review passes, not by design) — and it covers the worktree path only — the procedure's documented fallback when isolation cannot be established is a *disclosed, read-only* pass over the live tree, not a by-construction one. The trigger below still governs the *third-party* CLI question, which this does not resolve.

Trigger: a local agent whose terms give an unambiguous no-training guarantee at a credential tier the owner actually holds; **or** a quota model that survives more than a couple of reviews a week; **or** the CI-side reviewer's economics changing enough to make the local path unnecessary. Until one fires, CodeRabbit and Copilot remain the two reliable opt-in lenses, Greptile is a third (configured in `.greptile/`, triggered and collected with `/greptile-review`), and the Gemini workflow stays opt-in best-effort.

**A sync gate for a rule restated across several documents**
The personal-data containment gate's own docstring is the authoritative list of the holes it closes, and [ADR-0070](adr/0070-personal-data-containment-gate.md) §6 and [`/land`](../.claude/skills/land/SKILL.md) step 3a restate parts of it. Keeping those copies in step has failed **every** time it has been attempted, in two distinct ways: hand-maintained inventories of *where the copies are* went wrong repeatedly (a wrong pair of extra holes; "the two skills each restate it" while `/savepoint` never had; "three further places" when it was six), and the `git grep` recipes meant to replace those inventories went wrong too — `"collapses an untracked directory"` misses `/land`, which says *collapsing*, and `"untracked directory"` misses this file, whose markdown italics split the phrase.

The pattern is not carelessness: **a list of where the copies are is itself a copy**, so it drifts by the same mechanism, and a search phrase is a copy too — broken by paraphrase and by markup rather than by arithmetic. Widening the phrase trades a miss for noise without reaching completeness.

The repo already has the mechanism precedent — `scripts/check_markdownlint_config_sync.py` pins two config copies identical — but the honest difference is that config sync compares literal text, whereas these passages deliberately say the same thing at different lengths for different audiences. So the gate here is harder than its precedent and may belong in the register's "recorded as nothing, deliberately" column rather than the mechanized one. That is the question.

**A partial answer, from a different direction ([ADR-0073](adr/0073-operator-handoff-presentation.md)).** That ADR faced this entry's problem for a different rule — one presentation contract restated across five skills — and did not gate the restatements. It **removed** them: one owning document, five citations to it, and `scripts/check_doc_citations.py` asserting the citations survive. That converts an unmechanizable content-sync problem into a trivially mechanizable citation-presence one, because there is no longer more than one copy of the rule to keep in step.

**That gate is built on exactly the thing this entry warns about — a list of where the copies are — so the warning has to be answered rather than assumed away.** It is answered for one half and not the other. Against **drift**, the registry escapes: every entry is re-verified on every CI run, so a row that stops being true fails loudly instead of rotting, which is precisely what the inventories above could not do because nothing read them. Against **completeness**, it does not escape at all. A new file that starts depending on the owning document while forgetting both the citation and its registry row passes silently — the same shape as "a wrong pair of extra holes" and "three further places when it was six". So this entry's principle survives ADR-0073 intact, narrowed to the completeness dimension; the ADR and the script's docstring both disclose that blind spot, and neither claims more.

The *restructuring* the gate depends on may also not transfer. This entry's copies "deliberately say the same thing at different lengths for different audiences", and collapsing them to a citation would cost the short-form reader the thing the short form was for. So the open question narrows rather than closes. It is no longer "can prose copies be kept in sync"; it is **"is each of these copies genuinely needed at its own length, or is it a restatement that a citation would replace?"** — answered per copy, and a copy that survives that question is one no gate will ever cover.

Trigger: the next time a restated copy is found to have drifted, or the next document that restates the list. Both would previously have been silent; the drift has so far only ever been caught by a reviewer reading every copy at once, which is exactly the enforcement the register's third column would record as *nothing*. ADR-0073's round is a data point on both halves: a stale cross-reference (`/apply-review` §5 pointing at "step 3's third item" after an insert made it the fourth) was again caught only by a reviewer reading, while the five presentation copies it replaced can no longer drift at all. **The narrowed question has a second trigger, and it is not an event to wait for**: it is answered per copy, by whoever next has reason to edit one — is this length doing work the owning statement could not, or is it a restatement a citation would replace? A copy edited without that question being asked is the failure mode; a copy that has yet to be edited is not.

**Whether the two citation gates should be one**
[`scripts/check_reviewer_agents.py`](../scripts/check_reviewer_agents.py) asserts three unrelated things about the reviewer agent files: no `isolation` frontmatter key, that they cite [`.claude/reviewer-isolation.md`](../.claude/reviewer-isolation.md), and — since [ADR-0076](adr/0076-mutation-acceptance-criterion.md) — that `test-reviewer.md` names its `Acceptance:` report field. Only the second is in scope for this entry; the third shares the gate but not the question. The second is the same assertion [`scripts/check_doc_citations.py`](../scripts/check_doc_citations.py) now generalizes for [ADR-0073](adr/0073-operator-handoff-presentation.md), and moving it there would gate callers nothing checks today — `git grep -l 'reviewer-isolation.md' -- '.claude/**'` against `scripts/check_reviewer_agents.py`'s two-entry `AGENT_FILES`, the command rather than its output for the reason the entry below gives — while [ADR-0068](adr/0068-reviewer-isolation-worktrees.md) line 67 states "the skills cite that file rather than restating it" as load-bearing.

Deferred rather than rejected, for two reasons. It changes what ADR-0068's mechanism asserts, so it needs a record against that ADR rather than a silent refactor. And the registry rows are not mechanical: deciding which of the uncovered mentions — everything that command returns beyond the two agent files — are *deferrals* rather than passing references is a judgement, and the half ADR-0073 declines to mechanize. `/review-prep` is the worked example: it cites the document for invariant 1, not for the launch procedure, so whether it belongs in a registry of launch-procedure callers is a question a search cannot answer. Note the frontmatter assertion is not an argument against the merge; it argues for keeping the frontmatter check where it is, which nobody disputes.

Trigger: the next caller added to either rule, or the next time a citation to `.claude/reviewer-isolation.md` is found dropped from a file the gate does not cover — the point at which the uncovered five stop being theoretical.

**Whether skills should declare their own tool restrictions — and why skill invocability is not the lever**
Every skill under [`.claude/skills/`](../.claude/skills/) declares exactly `name` and `description`. A harness audit (2026-08-06) proposed hardening that frontmatter along two axes; measuring both against the published field semantics on 2026-08-11 rejected one outright and redirected the other. Recorded here in full because the rejected option reads well in any audit and will be re-proposed otherwise — the same reason the audit itself kept an explicit non-items list.

**Rejected — `disable-model-invocation: true` on the side-effecting skills.** The published behaviour table is unambiguous: with the field set, Claude *cannot* invoke the skill and its description is **not loaded into context**. It is not a guard against autonomous invocation specifically; it removes the skill from the model's reach entirely, including from inside another skill's execution, which breaks three chains this repo relies on — [`/ship`](../.claude/skills/ship/SKILL.md)'s reviewer arguments, which tell the model to continue with the corresponding `*-review` skill; [`/apply-review`](../.claude/skills/apply-review/SKILL.md)'s per-batch [`/savepoint`](../.claude/skills/savepoint/SKILL.md), which that skill calls its highest-leverage checkpoint site; and [`/land`](../.claude/skills/land/SKILL.md)'s rule that a user replying "commit" is the go to run `/ship`.

The decisive argument is not the breakage but the **fallback it induces**. With the description absent from context, a session told to merge does not know [`/squash-merge`](../.claude/skills/squash-merge/SKILL.md) exists and reaches for a hand-rolled `gh pr merge` — skipping the composed message, the refusal to merge while a bot finding lacks a threaded reply, and the diff of the result against `origin/main`. A field adopted to prevent an unauthorized merge makes an *unsafe* one likelier. The mismatch is structural: the field's motivating case is a model deciding on its own to deploy, whereas nearly every invocation in this repo executes an instruction the owner just gave, and the field cannot tell those apart.

Its strongest remaining case also dissolved. The field was to be the real mechanism behind the bot re-review prompting rule; the owner corrected on 2026-08-11 that bot reviews draw against a **monthly total, not a per-run charge**, and that the hazard is *repetition* — running them in a loop — not an unprompted invocation. Prompting taxed every invocation to prevent a failure that only appears in bulk. If that bound is ever mechanized, `scripts/bot_review.py` owns every trigger and is the place to count them; that would be a new mechanism and would need its own ADR.

**Redirected — `allowed-tools` is the opposite of what the audit assumed.** It is a *pre-approval grant* that lets listed commands run without per-use approval, not a restriction confining a skill to a fixed command set; it therefore cannot narrow anything, and the session-wide permission grants it was supposed to enable narrowing of live in the gitignored machine-local settings file rather than anywhere a PR can reach. The field that restricts is **`disallowed-tools`**, which removes tools from the pool while a skill is active and does not touch invocability — so it breaks none of the chains above.

**The open question, then, is narrow:** should `/land` and `/savepoint` declare `disallowed-tools` to enforce contracts they already assert in prose — `/land` states outright that it proposes while `/ship` disposes, and `/savepoint` describes itself as local-only scaffolding, and neither claim is enforced by anything today? The value is modest and should be weighed honestly against the cost of a mechanism plus a gate. A gate here would want the closed-world shape — every skill in exactly one bucket, so a newly added skill fails until classified — which is the same completeness dimension the entry above narrows to, and the same judgement ADR-0073 declines to mechanize. Separately, the audit's third proposal — `argument-hint` on `/wi`, `/ship` and `/apply-review`, none of which declares it today — would be cosmetic autocomplete; it is not free, because it is one of the Claude Code-only fields that **hard-error** rather than being ignored on claude.ai upload, the Skills API, and `package_skill.py`, which accept six fields only. That matters not at all while these skills stay in-repo and would matter immediately if they were ever packaged.

Trigger: the first time a skill does something its own prose says it does not — `/land` pushing, `/savepoint` reaching a remote — or the next skill added under `.claude/skills/`, which is the point a closed-world registry would have to classify.

**Ordinal cross-references into renumberable lists**
Skills and ADRs cite each other by *position* — "`/apply-review` step 5", "step 3's fourth item", "§4's rule". Inserting or removing one item silently invalidates every reference to the ones after it, in files the editor never opens. **No gate can see them.** [`scripts/check_spec_links.py`](../scripts/check_spec_links.py) resolves link targets and [`scripts/check_doc_citations.py`](../scripts/check_doc_citations.py) asserts a path is present; neither reads a prose ordinal. This is a different mechanism from the restatement drift the entry above covers — nothing is restated, and the pointer is correct right up until a neighbour moves.

The incident is the one the entry above already records — an insert into `/apply-review` §3 leaving §5 pointing at the wrong item, caught only by a reviewer reading. It appears there as evidence of restatement drift; it belongs here too, under a different mechanism, and is cross-referenced rather than retold. The per-site response ([`.claude/operator-handoff.md`](../.claude/operator-handoff.md) and [ADR-0073](adr/0073-operator-handoff-presentation.md) §1 now name their callers without step numbers) fixes those sites, not the mechanism — and the same branch then added two further ordinals of its own.

Scale over `.claude/` and `specs/`, each figure with the command that produced it, because a total stated without one is not reproducible and two of the first four written here were not:

```bash
git grep -l -i -E 'step [0-9]+' -- '.claude/**' 'specs/**' | wc -l                 # how many files
git grep -l -i -E 'step [0-9]+' -- '.claude/**' 'specs/**' | grep -c '^specs/adr/' # how many are ADRs
git grep -o -i -E 'step [0-9]+'  -- '.claude/**' 'specs/**' | wc -l                # total occurrences
git grep -o -i -E 'step [0-9]+ item [0-9]+' -- '.claude/**' 'specs/**' | wc -l     # the sharpest form
```

At the time of writing the first two answered **27** and **9** — nine ADRs is where the consequence is worst, an Accepted ADR being governance-frozen, so a stale ordinal needs an errata edit rather than a correction.

**The occurrence totals are deliberately not written down, and that is the finding rather than an omission.** They count this entry's own examples, so every edit to this paragraph changes them: three successive drafts measured three different numbers, and each was correct for the tree it was measured on and wrong by the time it was read. The file and ADR counts are stable under prose edits and are safe to state; the occurrence counts are not. A bare total is also regex-dependent — sweeping `step\s+\d+` over the filesystem rather than `git grep` over tracked files gives a different answer for defensible reasons — which is the second argument for shipping the command instead of its output. Run them.

Candidate remedy: stable named items and heading anchors — "step 3's *peer-enumeration* item" — so renumbering is a no-op, optionally with `check_spec_links.py` extended to resolve anchors, which would make the reference checkable rather than merely stable. Declined for the branch that surfaced it: a class-wide edit over 27 files is not a follow-up to a prose contract.

Trigger: the next stale ordinal a reviewer finds, or the next ADR that would freeze one at acceptance — either is where the per-site fix stops being cheaper than the mechanism.

**Greptile's clean sentinel went dark, and `clean_marker` cannot be re-derived from one sample**
Measured live on PR #85 (2026-08-09): Greptile's summary arrived in a template this repository had not seen, with the `**Files Needing Attention:**` line **gone** and an `Important Files Changed` table in its place. That line is where `clean_marker` ("No files require special attention") lives, so `grep -c` for it returned **0** on a run that was genuinely clean (5/5, "no actionable defect remains", no review object, no inline comment). The count sentinel was already absent — it lives in the `fixWithAI` block the owner keeps toggled off deliberately — so **both verdict signals are dark at once**.

The consequence is not a safety hole but an ergonomic one, and it is the shape a control takes when it stops working without changing what a clean run prints. [ADR-0067](adr/0067-unrepliable-finding-acknowledgement.md) §2's `unprovable_summaries` fails closed on exactly this input, so the gate blocks and demands a PR-level acknowledgement — correct, and strictly better than the pre-PR-#85 behaviour, which reported `NOTHING OUTSTANDING: all 0 finding(s) have a reply` and cleared silently. But until `clean_marker` matches something again, **every otherwise-clean** Greptile run needs a hand-written acknowledgement — and an acknowledgement that fires on every clean run is ceremony rather than signal. The scope is worth stating exactly, because "every run" would overstate it: a findings run posts comments after its summary, and the freshness check skips this detector whenever one of those postdates it. Findings runs are unaffected; it is the clean ones that can no longer prove themselves.

**Deliberately not fixed on the branch that found it.** One observed summary cannot separate the template's findings-dependent parts from its always-present ones, and a marker guessed from a single sample fails *open* — a findings run read as clean, which is the one direction this machinery must never fail. That is the same single-shape assumption that produced the PR #81 marker defect the branch was fixing, and repeating it inside the fix would have been the third time on that branch that a remedy reintroduced its own finding. Two documents therefore now overstate, in their own words rather than a shared one: [ADR-0067](adr/0067-unrepliable-finding-acknowledgement.md) §2 says `clean_marker` is "what keeps this from being a permanent block on every clean run", and `unprovable_summaries`' docstring says it is "what makes the rule usable rather than a permanent block". Neither is presently true in practice. Both carry a caveat pointing here rather than being rewritten, since each becomes true again the moment the marker is re-derived.

The same reasoning defers a seventh bullet in `.greptile/README.md`'s observed-shapes list: a shape taxonomy written from one observation has the identical defect as a regex written from one.

Trigger: **both a findings run and a clean run observed under the new template** — one of each, because only the pair distinguishes which parts of it vary with the verdict. Resolution: re-derive `clean_marker` against both, record the template as a new observed shape in `.greptile/README.md`, and drop the caveats from the two sites above.

**Does a repeat Copilot request write a second `review_requested` event, or does GitHub deduplicate it?**
`scripts/bot_review.py`'s request confirmation snapshots the issue timeline's `review_requested` event ids before the ask and requires a **new** one afterwards. That is correct if GitHub records every request as its own event. It is wrong — and reinstates the very false negative the mechanism was built to remove, on every second `/copilot-review` run against one PR — if GitHub instead deduplicates a re-request of a reviewer who was already requested and has since cleared itself. Every observation behind the current design (PRs #81, #82, #83, #85) is of a *first* request on its PR, so the repeat case is unmeasured.

No test can settle this: the suite runs without network access by design ([testing-strategy.md](testing-strategy.md)), so a fixture asserting either behaviour asserts only what its author believed. `tests/test_bot_review.py::test_a_pre_existing_request_event_does_not_confirm_a_new_ask` pins the strict reading deliberately, and would cement the defect rather than catch it if the dedupe hypothesis holds — which is stated here rather than left for a reader to notice.

**Shipping the strict reading pending measurement is the accepted default**, for two reasons worth recording since the alternative is defensible. Accepting a pre-existing event would make the confirmation vacuous on exactly the runs that need it most — after the first, every re-request would be "confirmed" by the first run's event whether or not it took. And the cost of being wrong is now bounded in a way it was not before: an unconfirmed ask prints its floor and tells the operator to check the PR rather than to stop, so the failure mode is a redundant look at a PR, not an abandoned review.

Trigger: **the first repeat `/copilot-review` run against a PR that has already been Copilot-reviewed** — read the timeline for a second `review_requested` id. This costs nothing to collect; it happens on the first PR that takes two Copilot rounds.

Resolution if GitHub deduplicates: accept **any** `review_requested` event naming the bot — and record the trade rather than presenting it as free, because it is not. The check's *named* hazard is a configuration one: a login GitHub does not recognize returns HTTP 200 and adds nobody, and such a login produces no event on any round, so relaxing newness costs nothing against it. But requiring a *new* event also catches a second class the code comment never names, defined by its shape rather than by a list: **any** post-round-1 change that makes the ask a silent no-op while the login stays valid. Whether such a change exists on GitHub is not established here, and neither obvious candidate qualifies — revoked access and a removed bot both return an error status, which `run_cmd` raises on, so they are already loud by a different mechanism and never reach this confirmation at all. That is the point: the residue is whatever fails *quietly*, which is exactly what cannot be enumerated in advance. Against that residue the strict rule refuses and says to check the PR, while "accept any" reports success on round 1's event and gives the operator nothing to look at. So the fallback trades a guaranteed false *negative* on every repeat run for a possible false *positive* on a rarer one. That is the right trade only if dedupe is real, which is exactly what the trigger measures — do not apply the fallback before it fires.

(A qualifier tying the pre-existing event to the absence of a newer Copilot review looks like the careful middle and is not: round 1's review is necessarily newer than round 1's request, so the qualifier is false every time it would be consulted, and the rule collapses back onto the false negative above.)

**Copilot's review effort level can be chosen per review, but only in the UI — so an automated ask cannot reach it**
GitHub added a review-effort selector to the PR sidebar's reviewers section, which raised an obvious question for a repository that automates its review chain: should `/copilot-review` set the level per run? It cannot — but **not** for the reason first recorded here. This entry originally stated that the level "is neither a per-PR selector nor a per-request argument", and that is **false**, corrected 2026-08-10 after CodeRabbit challenged it on PR #86 and the GA changelog was read directly: *"When you request a Copilot code review, choose Lite for routine changes or Balanced for larger, more complex, or sensitive changes. Your choice only applies to that review and doesn't change the repository or organization default."* A per-review choice exists. What does not exist is a way to make it from code: neither the GA changelog nor the Copilot code-review docs document any REST, GraphQL or `gh` surface for the level, and `scripts/bot_review.py` asks through the `requested_reviewers` endpoint, which takes no effort parameter. Defaults remain settable at **organization** level and overridable per **repository** (Settings → Copilot → Code review). The levels are `Lite`, the standard default, and `Balanced`, which reviews more deeply and costs more Copilot AI credits *and* more Actions minutes; they were renamed from the preview's Low/Medium and went GA on 2026-08-07. A third, `Max`, was sighted in the sidebar marked "coming soon" — the GA docs enumerate two levels and use that word as a plan name, so it is a sighting to re-check, not a level.

**The gap is structural, and the point of recording it is that nobody should try to close it.** Reaching the selector would mean requesting from the web UI instead of through the script, which bypasses the floor `wait`/`fetch` depend on — the script stamps it *before* the ask precisely so no caller has to mint one — or automating a web UI, which this repository will not do. And the depth would arrive in the wrong place regardless: the iteration loop is deliberately **local and unmetered**, many free `spec-reviewer`/`test-reviewer` rounds with no push per round, so by the time a change reaches the cloud `/ship` has already collapsed the savepoints and the code has settled. A deeper cloud review cannot be inserted where depth would still change the work without pushing intermediate state that the local loop exists to keep out of the cloud. `Lite` on automated asks is therefore an accepted consequence of keeping that loop local, not an unfinished job.

The practical consequence is mild, which is why this is recorded rather than fixed: `Lite` is already the default, so a repository that has configured nothing is getting the level the owner would have chosen. What is genuinely unclosed is that **the level is a control which changes review depth and leaves no trace in any diff** — the same shape as the Greptile dashboard toggle above, and as the `fixWithAI` block before it. An agent cannot read the setting back, so [`/copilot-review`](../.claude/skills/copilot-review/SKILL.md) states the expected value for a human to confirm in the UI, which is the weakest form of control this repository accepts and is accepted here only because the alternative is nothing at all.

Trigger: **a documented API surface for the level** — at which point `scripts/bot_review.py` can assert the expected value on every request the way it asserts the ask itself, and the skill's prose expectation becomes a mechanized one; **or** `Max` actually arriving, which changes what "the default" means and makes the unasserted setting worth more than it is now.

**Which further rules earn a `PreToolUse` hook**
[ADR-0077](adr/0077-local-invocation-hooks.md) stands up the hook mechanism for one rule — refusing local gate invocations that cannot work — and its §7 names two further candidates without shipping either, because a new mechanism plus a new policy inside one change is a shape this repository has repeatedly paid for. They are recorded here so the deferral has a trigger rather than living only inside the ADR that declined them.

1. **Read-only `tests/**` while a fix is in progress.** ImpossibleBench measured Claude-family models cheating predominantly by editing the test file, and prose is not a control there (93% → 1%). This is the stronger candidate on evidence, and the weaker one on scope: "while a fix is in progress" is not a state the harness exposes, so an always-on rule would block the ordinary case of a change whose *point* is editing tests — which is most of this repository's recent history. What has to be settled first is therefore not whether the risk is real but **what signal distinguishes a test edit that is the work from one that is an escape hatch**, and no candidate signal has survived inspection yet.
2. **The CLAUDE.md PowerShell UTF-8 encoding rule.** The 2026-08-06 harness audit called this "genuinely hook-gateable" and "the real target if hooks get built" — a check on command text (`Get-Content` without `-Encoding UTF8`) rather than a judgement about meaning, which is the same class as ADR-0077's four shapes and would slot in as a row rather than a new mechanism. It is unshipped only because it is unmeasured: nobody has counted how often the rule is actually broken, and a control justified by an uncounted risk is itself an unmeasured claim.

**The boundary that governs both, and any third candidate:** ADR-0077 §7 restricts this mechanism to rules decidable from *command text*. A rule needing a judgement about *content* is ADR-0070's rejected option and does not become viable by moving into a hook — so a future candidate has to clear that bar before the trigger below is even reachable.

Trigger: for (1), **a concrete signal that separates a test edit which is the work from one which is an escape hatch** — until one exists there is nothing to implement, and an always-on rule is worse than none. For (2), **a measurement**: any instance of the encoding rule actually being broken in a session, which turns an unquantified risk into a counted one. Either firing makes its candidate a row in the mechanism ADR-0077 established, not a new decision.

**Should the gate-invocation hook police a *pinned* `uvx` spec whose distribution name cannot work? ([ADR-0077](adr/0077-local-invocation-hooks.md) §1)**
Rule 3 refuses an **unpinned** `uvx <tool>` for a tool `ci.yml` pins; a pinned spec returns early as the correct form. That leaves one shape allowed which cannot work: `uvx pymarkdown@0.9.39` — the *console-script* spelling wearing a correct-looking pin, the inverse of the package-name spelling the bare-word path was fixed for. Measured 2026-08-16: `pymarkdown` is a real but **unrelated** distribution on PyPI (`0.1.4`, depending on `toolz`), so no such version exists and uv refuses to resolve it. Its unpinned twin `uvx pymarkdown` is already denied, by rule 3, for rule 3's own reason.
This was left open rather than folded into the bare-word fix because the fact it needs is different in kind. Rule 3 asks *is this name in the derived tool set*, which `_CONSOLE_SCRIPTS` answers; this asks *is the typed name a distribution at all*, which no file in this repository records and which the hook cannot learn without a network call it must not make — and `_CONSOLE_SCRIPTS` maps one direction only, so it does not supply the answer either. The exposure is also bounded in the direction that matters: this shape fails loudly at uv's resolver rather than reporting a confident green from the wrong version, which is the harm rule 3 exists for. The cost of leaving it is a wasted resolve.
Trigger: a **second entry in `_CONSOLE_SCRIPTS`**, which doubles the surface and makes stating both directions cheap enough to be worth the copy's obligations — or any measured instance of the spelling actually being typed.

**Should the gate-invocation hook normalise a `uv run` argument before matching it? ([ADR-0077](adr/0077-local-invocation-hooks.md) §1)**
`classify` puts a bare command word through `program_name` — basename, `.exe`, lower-case — before matching it against the derived tool set. `parse_uv_run` does not; it matches the argument as typed. Measured 2026-08-16: `uv run PYMARKDOWNLNT`, `uv run ./pymarkdownlnt` and `uv run pymarkdownlnt.exe` are all **allowed**, and all fail, and the same holds for every tool in the set (`uv run RUFF` alike) — so this is a second normalisation axis, not another instance of the package-vs-console-script mapping that prompted it. Left open rather than fixed alongside that mapping because the remedy is a behaviour change for every tool rather than one, and `uv run` legitimately takes paths (`uv run ./script.py`), so what `program_name` should do to a non-tool argument needs deciding before it is applied there. Trigger: any measured instance of one of these spellings being typed, or the next change to `parse_uv_run` for any reason.

**Resolved 2026-08-23 — yes, and at the source.** The second half of the trigger fired: an external review found the same gap from the other end, that the un-normalised `executed` also bypasses the `tool == "pytest"` serial-full-suite denial, so `uv run pytest.exe` and `uv run ./pytest` escaped a rule whose own message says such a run "exceeds the 600 s command timeout and is killed". `parse_uv_run` now routes `executed` through `program_name` before `_console_name`, the same order and for the same reason as `classify`'s first line. The question above — what `program_name` should do to a *non-tool* argument — answers itself once asked here rather than at the predicate: it takes the basename, strips `.exe` and lower-cases, and nothing downstream compares a non-tool argument against anything, so a script path is normalised and then ignored exactly as before. The interpreter question had already been repaired separately inside `_is_python_program`, which is normalising at the predicate while that function's own docstring argues that past two sites you prefer one named mechanism; the source fix subsumes it. Pinned by `test_a_path_or_extension_bearing_uv_run_word_still_reaches_every_rule` and `test_the_ephemeral_comparison_sees_through_a_path_or_extension`.

**What discipline does the ADR corpus need as it grows — and what gates the `Proposed` → `Accepted` transition?**
Measured 2026-08-19: **77 ADRs** (excluding `0000-template.md`), **48 Accepted and 29 Proposed**. Five sections appear in all 77 — `## Status`, `## Context and Problem Statement`, `## Decision Drivers`, `## Decision Outcome`, `## Links` — so a stable core exists to check against; below that the set diverges (`## Considered Options` in 60, `## Pros and Cons of the Options` in 36, `## Consequences for Other Documents` in 25 — the first counted by heading prefix, since ADR-0032 spells it `## Considered Options (to be evaluated)`; an exact-heading match gives 59, and the other two have no variants at all). The corpus has conventions. Almost none of them are written down, and `scripts/check_adr_index.py` — the only ADR gate — checks the README index against each file's `## Status` and nothing else.

**The finding that prompted this, because it is a measurement rather than a worry.** Adding one `## Links` bullet to ADR-0072, this session wrote a **130-word, four-sentence** bullet. Against the corpus: **560** `## Links` bullets exist, median **12.5** words, p90 **23**, maximum **52**, and **7** contain more than one sentence — that last counting a break as `. ` followed by a capital; splitting instead on `. `, `! `, and `? ` gives 9, so it is as method-dependent as the rest. So the new bullet was roughly ten times the median and more than twice the longest anywhere — an argument written into a section that everywhere else holds pointers. **Nothing caught it**: not the markdown gates, not the link gate, not `check_adr_index.py`, and not five review rounds on the branch that introduced it. It was found only by measuring the corpus on purpose, and it was then trimmed to 42 words. A convention that exists solely as emergent practice is invisible to every reader who has not read all 77 files, which is every reader.

**Those figures are stated to a method, and the first attempt at them was wrong** — which is the entry's own argument arriving uninvited. Bullets are counted after joining soft-wrapped continuation lines (several ADRs wrap `## Links` bullets across indented lines, so a line-by-line count truncates the long ones — the very ones that matter here), the leading `- ` marker is stripped before splitting on whitespace, and the template is excluded. The first measurement kept the `-` **and** did not join the wrapped lines, so it was wrong in two independent ways rather than shifted by a constant — the new bullet came out at 43 against a true 42, and its distribution figures are not restated here, because a number that cannot be reproduced under any stated convention is worth deleting rather than preserving. Two independent re-measurements disagreed with it, and with each other, before the causes were found. A corpus statistic is not self-evident, and one quoted without its counting rule cannot be checked — which is itself an argument for writing the conventions down rather than inferring them.

**The most expensive stage is the transition.** Under CLAUDE.md's ADR governance the `Proposed` → `Accepted` edit is the single highest-consequence change in the model: it converts a freely editable document into an immutable one, after which the cheapest correction costs a superseding or extending ADR. **Nothing gates it.** No checklist exists in `CLAUDE.md`, in `specs/adr/README.md`, or in any skill or script; acceptance is a one-word edit that any session may make, and **29 ADRs are currently pending that transition**. The ADR-0072 consolidation entry under `## Testing` is one instance of the resulting gap, closed there by a hand-written backlink — a per-ADR remedy that does not generalise and that nobody is obliged to repeat.

**The scope wanted is the whole lifecycle, not the acceptance gate alone** (owner, 2026-08-19: a solution is needed for the sweep, but the discipline is wanted throughout). Three stages, each with a different failure mode and a different instrument:

**Creation.** Does a new ADR match the template? The five universal sections present, `## Status` holding a permitted value, a README index row added, `## Links` bullets shaped as pointers. All of this is mechanizable against the stable core and is the cheapest of the three — `0000-template.md` already exists to check against, and nothing currently compares anything to it.

**Modification.** This is where the 130-word bullet happened, and naming the stage is what makes that failure legible rather than a one-off embarrassment. CLAUDE.md's governance rules — Accepted content immutable, only status corrections, `## Links` navigation additions, typo and link fixes permitted in place — are **stated and enforced by nothing**. A modification-time check is feasible and would compare the diff against the target's `## Status`: an edit to an Accepted ADR that touches anything but those permitted shapes is mechanically detectable. Convention conformance belongs here too, since most bullets are added long after creation.

**Acceptance.** The urgent stage, per the sweep, and the one where the cost is unrecoverable — the edit converts a freely editable document into an immutable one. Are the ADR's open obligations discharged, is its `## Consequences for Other Documents` manifest complete, does everything it defers carry a live trigger, and do any `open-questions.md` entries gate it as ADR-0072's does? Largely judgement, so probably a checklist rather than a gate, with the mechanizable parts (a `Superseded by ADR-XXXX` status naming an ADR that exists and links back) split out.

**None of the three is cosmetic, and the middle one is the easiest to mis-file as such.** A formatting drift caught at modification time costs a trim; the same drift discovered after acceptance is frozen, because fixing it is a content edit to an immutable document.

**Survey the prior art before drafting any of this** (owner, 2026-08-19). This is not a greenfield problem: the corpus follows **MADR**, and `specs/adr/README.md` says so outright — it links the specification and states "the template follows the MADR structure". So a large part of the question is *what has that ecosystem already settled* rather than what should be designed locally. Worth reading at minimum: MADR's own conventions and whatever it says about status and lifecycle; Nygard's original formulation, which is where the Proposed/Accepted/Superseded vocabulary comes from; and the tooling built to enforce ADR structure (`adr-tools`, `log4brains` and peers), since a tool that already implements a check is cheaper than a script that reimplements it. Do the reading **before** a checklist is drafted: one invented locally that diverges from a standard the corpus already follows costs the divergence twice, once to write and once to reconcile.

**One caution about the survey, learned while writing this entry.** The MADR attribution above was first recorded here as an unverified inference from the section names, with confirming it listed as research to be done — while `specs/adr/README.md`, the document that is *already* authoritative on ADR structure, had stated it plainly all along. Reading the repository's own documents is the first step of the survey, not a substitute for it, and the gap this entry describes is partly that those documents are not where anyone thinks to look.

**Trigger: the acceptance sweep the owner has planned** — stated 2026-08-19, the 29 Proposed ADRs to be worked down deliberately rather than drifting one at a time. **That reverses part of this entry's own reasoning and the reversal is the point.** A single next-acceptance would have let a checklist be derived from one concrete case, which is why deferring looked right; a sweep instead lands many transitions close together, each closing its own edit window permanently, so a checklist that arrives after the sweep is one that missed its entire population. **The checklist is wanted before the sweep starts, not derived from its first case** — and the sweep is also the moment the 29 stop being a static measurement and become a queue with an owner. Secondary trigger: any new ADR-structure convention worth stating, since the marginal cost of writing one down is lowest while a document is already being drafted to hold them.

**This entry has the defect it describes, and that is recorded here rather than left to be discovered.** Nothing routes a session to `specs/open-questions.md` when an acceptance sweep begins — precisely the gap the paragraphs above spend their length on. Historically it has not bitten: all three batch acceptances this repository has performed were preceded by a dedicated review document rather than a bare status edit, and the 2026-07-17 review swept this file explicitly for deferral symmetry. But that convention is written down nowhere, so this entry's own reachability rests on the same unwritten habit as everything else it criticizes. Naming that is not a fix; it is the difference between a known limitation and an ambush.

Acceptance for any remedy: a checklist alone is not evidence, so whatever lands must be demonstrated against the corpus as it stands — the structural checks run over all 77 ADRs reporting which pass, and the transition checklist walked against real acceptances from the sweep rather than in the abstract. A check that has never been run against the existing corpus is a claim about it, and this entry exists because exactly that class of claim went unmeasured across 77 files.

**Does the local smoke loop want an ADR of its own?**
The `spec-reviewer`/`test-reviewer` loop inside `/apply-review` step 5 is governed in slices by three ADRs and owned by none of them. [ADR-0068](adr/0068-reviewer-isolation-worktrees.md) owns its isolation mechanism; [ADR-0069](adr/0069-local-checkpoint-commits.md) owns the `[x<N>s<M>]` savepoint tag and the review/smoke vocabulary split; [ADR-0072](adr/0072-review-pipeline-and-ledgers.md) owns its briefing (§1) and its exclusion from the ledger's counts (§7 — cited as evidence, never counted). Each reaches the smoke loop downstream of its own subject. None says how a round is conducted, and none says when the loop **stops** — which is why the two termination bullets added to `/apply-review` step 5 on 2026-08-24 have no owning record, and are filed here rather than as a fourth slice.

**The gap has a measured cost, and most of that measurement can no longer be re-derived.** The apply on the `mark-1` branch (PR #100) ran ten smoke rounds and ten edits without ever producing a clean round: it stopped on the operator's judgement, not on the rule, which says to stop when a round produces no substantive edit. Both reviewers said stop, in writing and unprompted, at round 9; the loop ran to 10 because nothing had asked them and the rule said to continue. Rounds 6–10 found no production defect and closed five gaps with no live occurrence, and were recorded during the apply at roughly 42% of that loop's subagent spend. **Their output was then abandoned outright**: once the rounds were read back and judged to be gilding, the operator had the branch reset from round 10 to round 5. `tests/test_git_runners.py`, the file those rounds kept enlarging, had gone from 361 lines at the loop's start to 1,105 by round 10 and merged at 541 — the round-5 state. So the strongest form of the finding is not that five rounds were expensive but that **roughly 560 lines of analysis code were written, reviewed, and thrown away, while the stopping rule as written said to keep going** — the 1,105 lines standing at round 10, less the 541 that merged. What is checkable in git today is only the endpoint: PR #100 merged 6,220 insertions across 37 files with that file at 541 lines. The 42% split, the intermediate 1,105, and the ten-rounds-never-clean sequence are session measurements — the discarded rounds are not in the branch at all, and the `[x<N>s<M>]` savepoints that would otherwise have carried the churn did not reach `main` either, which is exactly the loss ADR-0072's remedy-churn section warns of ("write it at the end of the apply, or it is gone"). A figure recorded in a session and nowhere else is the shape [ADR-0076](adr/0076-mutation-acceptance-criterion.md) opens by conceding about its own evidence; this entry writes down what it still can.

**Why no round threshold was adopted, since that is the obvious control and it was rejected.** Smoke-loop lengths recorded across this repository's branches run 2, 2, 2, 3, 3, 3, 3, 4, 4, 5, 6 and 7 rounds. **That list is a session measurement on the same footing as the figures above, not a checkable one**: it was counted from the `[x<N>s<M>]` tags while they were still readable, and no savepoint tag reaches `main` — `/ship` collapses them before a branch's first push, and a branch already on the remote is never reset, so any that survive ride into the PR and are squashed away by `/squash-merge`'s `gh pr merge --squash --delete-branch`. Either path leaves the tags for those twelve loops out of current history. Any fixed trigger therefore both fires on a healthy loop that merely runs long *and* stays silent through the wasted rounds of one that ends early; a dormant control is also an untested and forgotten one. What landed instead is a consequence test — does the finding say the mechanism *fails at its stated job*, or that its *coverage could be finer* — plus a materiality question asked of each reviewer every round, so the control is a standing input rather than one that fires on a number.

**What deciding either way costs.** A fourth ADR joins the 23 Proposed and 6 stub ADRs that nothing currently drains (the entry above), and would have to state its boundary against the other three in four places, all of them still Proposed and still moving. **`scripts/ledger.py` holds a second markdown model, and it did not move with the first**
[ADR-0072](adr/0072-review-pipeline-and-ledgers.md) §8 binds the review-ledger composer's markdown model — what opens a fence, what closes it, what counts as a heading — to `scripts/check_spec_links.py`, "the repository's other parser over the same corpus", and records what their last disagreement cost: a fragment whose top heading was demoted wrongly, accepted by the composer and rejected by PyMarkdown, at the moment `/squash-merge` was merging the PR. On 2026-08-22 `check_spec_links.py` moved to a real CommonMark parser ([ADR-0061](adr/0061-markdown-link-check-gate.md) §1, revised) and `ledger.py` kept its `FENCE_RE`, so the pair is no longer two spellings of one rule.

**Measured at the time of the move, so this is a known gap rather than a suspicion.** Over every markdown file git considers part of the repository, the two models' fence verdicts agree **line for line on 130 of 130** — there is no fence disagreement in the corpus at all.

**The interesting part is which divergence is dangerous, because the obvious answer is wrong and was written down as fact before it was checked.** Three shapes the corpus does not currently contain — a fence indented under a list item, a tab-led fence, and an indented code block — are code to the gate and prose to the composer. That reads like the costly direction (the composer demotes headings in what it thinks is prose, so a `# comment` inside a list-indented fence would be rewritten inside a code block) and it is not: `ATX_HEADING_RE` admits `{0,3}` leading spaces and no tab, so the very indent that makes those shapes code is what stops the demoter matching a `#` inside them. Measured — `demote_headings` returns a `# comment` in all three **unchanged**. The three-shape framing survived several review rounds as the statement of this gap; it names real divergences with no reachable consequence.

**The shape that does rewrite a heading inside code is an HTML block**, which the gate masks and the composer does not model at all. Measured: `<!--` / `# comment` / `-->` composes to `## comment`. Unlike the three above, this shape is **present in the corpus today** — 7 lines, all in `specs/adr/0000-template.md`, none of them a heading. So the guarantee is "live and currently harmless", which is weaker than "absent" and is the reason this entry is open rather than a note.

**Trigger: the first review-ledger fragment that puts a `#`-led line inside an HTML block** — a `<details>` fold around a quoted transcript is the ordinary way that happens, and fragments quote tool output routinely. The three indent-based shapes are *not* a trigger on their own; they become one only if `ATX_HEADING_RE` is ever widened to admit deeper indents or tabs, which would make all three live at once. Deliberately not fixed on the change that surfaced it: moving the composer is a change to `/squash-merge` machinery, with its own blast radius, and it was not what that change was for. Candidate remedy, and the substitution it is **not**: the direction is right — one model rather than two — but `ledger.py` cannot simply consume `check_spec_links.code_masked_lines` in place of `scan_fences`. The two answer different questions. `code_masked_lines` answers *is this code*, as one masked line per source line; `demote_headings` and `validate_digest` need *is this line inside a fence*, plus an unclosed-fence flag, and neither survives the mask. Measured on 2026-08-23 over five shapes, all five disagreeing and each for its own reason: a heading carrying an inline code span reads as fenced (the mask blanks spans too, and fragments write such headings routinely); an indented code block reads as fenced (the gate masks it, the composer does not model it); a **blank** line inside a fence reads as unfenced, because a blank line masks to itself; an unclosed fence has no counterpart at all, since markdown-it closes it at EOF — and that flag is what raises the refusal whose own message records a round that survived only as text inside a code block; and the HTML-block shape this entry is about reads as fenced across the whole block, which is the agreement wanted but arrives inseparable from the other four. So a real remedy is `code_masked_lines` growing a second, explicit return — the per-line block classification the parser already has and currently discards — or the composer taking its own markdown-it parse. Recording the dead end rather than deleting it: a reader who tries the substitution finds all five of these, and the reason the direction is still right is not obvious from the failure. Acceptance for any remedy: the composer's verdict and the gate's must be shown equal over the HTML-block shape **and** the three indent shapes, not merely over the current corpus — the current corpus is what makes the gap invisible, and the corpus already contains the one shape that bites.

The `refs/`-namespaced alternative is real and was measured — a branch-derived path does not name one file on Windows but a different file depending on which API resolves it, and a `refs/` blob fails closed where a plain path does not — but it is declined on size, not on doubt — and the recipe carries a caveat worth keeping with it: `git rev-parse --git-dir` resolves to a *linked* worktree's gitdir inside [ADR-0068](adr/0068-reviewer-isolation-worktrees.md)'s reviewer worktrees, so a `refs/` spelling owes `--git-common-dir`. The size argument: detection already closed the failure, and the message carrier is load-bearing only between `/land` and the **first** `/ship`, since the checkpoint collapse puts the message into the branch's first commit and `/squash-merge` reads it from there afterwards. A carrier lost outside that window costs nothing; one lost inside it costs a `/land` re-run. Recorded with the decision: that sizing was taken under sequential, single-session work, and parallel PRs raise the rate at which a `/ship` runs in a different session than its `/land` — if that rate rises, take the `refs/` spelling, and move both carriers or neither. This does not reopen the checkpoint collapse, whose rejection of a repo-scoped message rests on visibility as well as durability. Resolved 2026-08-09 by the trigger this entry named — the brief → prep → handoff pipeline rewrite. See [ADR-0072](adr/0072-review-pipeline-and-ledgers.md) §9.

- **Parallelize the CI test job under xdist** → The `windows-latest` matrix leg runs `pytest -n auto`; `ubuntu-latest`/`macos-latest` keep the serial invocation untouched. Windows was the ~3× wall-clock outlier (subprocess-spawn cost, heaviest there) and, since the legs run concurrently, the standing CI pole — the trigger this entry named. The canary-coupling that kept CI serial is reworked, not bypassed: under xdist a worker's stdout is the execnet channel, so the Windows leg scans two sources — the controller stream tee'd like the serial legs (tracebacks, node ids, warnings, crash relays) plus a per-worker sink (`tests/conftest.py`, active only under `CANARY_CAPTURE_DIR`, fed by **fd-level capture**) that recovers the per-test output xdist suppresses. Together they scan a superset of the serial stream, with a fail-closed scan (lazy worker files, so a dead sink leaves the glob empty). Only the outlier is parallelized because the no-health-values-in-logs prohibition is platform-independent: the two untouched serial legs are a full backstop, confining the change's risk. A planted-leak run confirmed the gate still fails under xdist. Measured CI-representative payoff `-n 4` ≈ 3.4× (372.8 s → 110.9 s). Resolved 2026-07-21. See [ADR-0063](adr/0063-parallel-ci-test-execution.md).

The paired stale-prose fix landed in the same PR — testing-strategy.md's "Workflow provenance" paragraph no longer claims the non-index gates are "deliberately not yet wired". Blocking, not report-only, which is why it warranted the extension ADR rather than riding §8's report-only-coverage no-ADR precedent. Surfaced by the PR-#38 relocation's `/code-review high` and resolved the same day (2026-07-19). **Since widened (2026-08-08, ADR-0061 revised in place):** the crawl now covers every markdown file git considers part of the repo — tracked plus untracked-but-not-ignored, no longer `specs/` only — with `specs/personal/` still excluded; the "under `specs/`" description above is the gate as first landed. **Since widened again (2026-08-22, ADR-0061 revised in place):** two more clauses above are now the gate as it *was*. - **Biomarker molar-mass persistence** → A nullable `biomarkers.molar_mass REAL CHECK (molar_mass IS NULL OR molar_mass > 0)` column (migration 0005, Phase 3 WI-3), added by a plain `ALTER TABLE … ADD COLUMN` — not a rebuild, so the `legacy_alter_table` FK-repointing hazard migration 0004 documents never arises. The catalog is the natural home: molar mass is per-biomarker reference data sitting beside `canonical_unit`, the other column the comparison path reads for the same purpose. [ADR-0056](adr/0056-units-module-api-and-molar-context.md) §3's decision that `units.convert` takes molar mass as an **explicit argument** is unchanged — the units module stays a pure function of its arguments with no catalog dependency; this resolves only where the *caller* reads it from. `NULL` means "not applicable, or not curated" and stays safe: a molar conversion against it raises `MissingMolarContextError` and surfaces as a named `error` flag, never a scalar fallback. Nineteen biomarkers seeded from PubChem, each cross-checked against an independently published clinical conversion factor; three carry recorded subtleties (BUN is the **urea-nitrogen equivalent** 28.014, not urea's 60.06 — BUN measures nitrogen mass and each urea carries two N, so urea's own mass cancels out of the conventional 0.357 factor; Triglycerides 885.4 and Folate 441.4 are assay-calibration proxies, not the physiologically dominant species). - **Biomarker category taxonomy** → First-class `categories` catalog table with a `category_id` FK on `biomarkers` (migration 0004, Phase 3 WI-2), replacing the free-text `category` column. `category_id` is `NOT NULL DEFAULT 0` pointing at a reserved `not_assigned` row (id 0, delete-guarded, display-renamable) — "not assigned" is a spec-defined concept in the data, not a NULL whose meaning lives in client code; this also keeps naive joins and by-category aggregations correct. Primary axis is **physiological system**; a theme earns a category only when its members have no system home (`environmental_toxins`, `screening`), else it is a future tag. Nineteen-category system-axis seed (`autoimmunity`, `allergy`, `body_composition`, `electrolytes`, `environmental_toxins`, `heart`, `hematology`, `hormones`, `immune`, `inflammation`, `kidney`, `liver`, `lipoproteins`, `metabolic`, `nutrients`, `pancreas`, `screening`, `thyroid`, `urine`) + the reserved default, owner-editable data forever after. - **Biomarker alias table** → Add it: `biomarker_aliases` (migration 0004, Phase 3 WI-2) — alias display form plus a normalized form (`NFKC → casefold → trim → collapse whitespace`) that is the resolver key, with provenance. Resolution is a single Core Service capability over the union of normalized canonical names and aliases: exact match on the normalized form only, fail-loud on unknowns, no fuzzy auto-matching on any non-interactive path (fuzzy is permitted only as interactive *suggestion*, confirmed by a human and recorded as a new alias). Namespace ambiguity is prevented at write time (schema `UNIQUE` on the normalized alias; app-level normalized checks across aliases ↔ canonical names). `POST /v1/import` `lab_results` rows accept exactly one of `biomarker_id`/`biomarker_name`, resolved before conflict detection. - **Longitudinal data correction** → `superseded_by` self-FK on every data table (option a). Value corrections insert the corrected row and point the original at it — never mutate in place; current state is `WHERE superseded_by IS NULL` via per-table `*_current` views. Carve-out: designated metadata repairs (the timezone correction workflow) update in place, fully audited. Deletes are hard deletes with a mandatory audit row preserving the full row image; clients flag the request and offer a backup first; supersession-chain rows are not deletable. - **Timezone storage convention** → UTC as ground truth (ISO 8601). Every timestamp table carries four columns: `*_utc` (UTC, ground truth), `*_local_recorded` (original value from source, immutable), `*_local_tz` (IANA timezone name, best guess), `*_tz_inferred` (boolean — 1 if timezone was assumed not known). Correction workflow: update `local_tz`, recompute `*_utc` from `local_recorded`, clear `tz_inferred`. See [design-rationale.md](design-rationale.md) for the full convention.

- **Intervention dose history** → `intervention_dose_history` child table with FK to `interventions`. Key fields: `change_type` enum (`initiation`, `increase`, `decrease`, `hold`, `resumption`, `discontinuation`), `authority_type` enum (`prescribing_physician`, `supervising_clinician`, `self`, `protocol`), `ordered_by` free text (NULL when self), `reason` enum (`scheduled_titration`, `lab_result`, `symptom_response`, `side_effect`, `cost_or_availability`, `physician_directed`, `protocol_change`, `other`). `authority_type` and `reason` are orthogonal — a lab-result-driven change can be either physician-directed or self-adjusted. See [data-model.md](data-model.md).

- **Cloud backup strategy** → Cloud backup of the encrypted SQLite file is explicitly safe and recommended — but only the output of `healthspan db backup`, never the live database file. The database is AES-256 ciphertext (SQLCipher, ADR-0013), so the cloud provider cannot read it, and the provider is in the "do not trust" tier for storage — the encryption model handles confidentiality correctly. That is a separate question from consistency: the live file runs in WAL mode, so a sync client snapshotting it mid-write can capture a torn, unrecoverable copy — encryption makes a torn copy worse, not better, since it can't be partially salvaged. `healthspan db backup` produces a checkpointed, self-consistent, encrypted snapshot; that snapshot — and only that snapshot — is safe to sync continuously to Dropbox, iCloud Drive, OneDrive, Backblaze, or any similar service. See [ADR-0019](adr/0019-multi-device-sync.md) for the single-writer + backup-only-sync pattern.
